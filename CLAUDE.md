# ШІ-Репетитор — інструкція для Claude Code

## Про проєкт
Веб-застосунок (PWA) з ШІ-агентами, який працює як персональний репетитор для доньки власника проєкту.
Повний опис: `docs/00-product-brief.md` — читай його перед будь-якою роботою.

## Хто замовник
Алекс — власник продукту (Product Owner), бізнес-аналітик за фахом. **Код не пише.**
- Спілкуйся з ним українською, пояснюй технічні рішення простими словами.
- Будь-які дії, які потребують від нього кроків (створити акаунт, отримати ключ, натиснути кнопку в консолі) — описуй покроково, як інструкцію.
- Перед тим як витрачати гроші (платні тарифи, платні API-виклики у великих обсягах) або робити незворотні дії (видалення даних, продакшн-деплой) — питай підтвердження.

## Команда агентів (.claude/agents/)
| Агент | Роль | Результат |
|---|---|---|
| `product-manager` | Вимоги, user stories, обсяг MVP | `docs/01-requirements.md`, `docs/05-backlog.md` |
| `architect` | Архітектура, стек, ресурси, вартість | `docs/02-architecture.md`, `docs/03-resources-and-costs.md`, `docs/adr/` |
| `designer` | Дизайн-система, макети екранів | `docs/04-design-system.md`, `docs/design/*.html` |
| `developer` | Реалізація, міграції, деплой | код у `app/` (або структура від архітектора) |
| `qa-tester` | Тест-план, автотести, баг-репорти | `docs/06-test-plan.md`, `tests/`, `docs/bugs/` |

Головна сесія Claude Code — це **оркестратор**: вона запускає агентів, передає результати між ними
і **сама ставить питання Алексу** (субагенти не можуть говорити з ним напряму — вони повертають
відкриті питання у своїх документах, а оркестратор їх озвучує).

## Процес (з воротами затвердження)
1. **Фаза 0 — Вимоги.** `product-manager` готує вимоги → оркестратор ставить Алексу відкриті питання → ітерації → ✅ Алекс затверджує.
2. **Фаза 1 — Архітектура.** `architect` → схема, стек, список акаунтів/ключів, кошторис → ✅ затвердження.
3. **Фаза 2 — Дизайн.** `designer` → дизайн-система + HTML-макети ключових екранів (Алекс дивиться на планшеті) → ✅ затвердження.
4. **Фаза 3 — Розробка ітераціями.** Для кожного зрізу з `docs/05-backlog.md`:
   `developer` реалізує → `qa-tester` тестує й пише баги → `developer` виправляє → деплой на preview → демо Алексу → ✅ → production.
5. Після кожної фази онови `docs/STATUS.md`: що зроблено, що далі, які рішення прийняті.

## Незмінні правила
- **Секрети:** жодних API-ключів у коді чи git. Лише `.env.local` (у `.gitignore`) і змінні середовища на хостингу. Усі виклики ШІ-провайдерів — тільки з сервера.
- **Мова:** інтерфейс і спілкування з дитиною — українською. Код, назви змінних, коміти — англійською.
- **Дитячі дані:** мінімум персональних даних у запитах до моделей (ім'я дитини моделям не передавати), лише платні API без використання даних для навчання.
- **Маленькі кроки:** кожна зміна — робочий стан, коміт з зрозумілим описом.
- **Документи — джерело правди:** якщо рішення змінилось, спершу онови документ, потім код.
