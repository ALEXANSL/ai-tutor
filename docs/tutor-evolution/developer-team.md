# Codex, Claude Code у браузері та Gemini: одна команда

## Рекомендована організація

Один координатор веде задачі GitHub; один відповідальний виконавець змінює гілку; незалежний рецензент перевіряє конкретний commit SHA; інтегратор серіалізує merge й перевіряє deployment. Ролі переносні між моделями. Власнику не потрібно вручну переносити код між чатами.

Не призначати переможця між моделями наперед. Порівнювати на однакових задачах: точність, завершеність, регресії, витрати, час, кількість виправлень. Розбіжність трьох моделей вирішують докази й перевірки, а не голосування. Не запускати всі моделі на кожну дрібну зміну.

| Роль | Обов’язок | Початкове призначення |
|---|---|---|
| Координатор / BA | Спільний backlog, критерії приймання, залежності, звіт татові | Поточна сесія Codex |
| Архітектор | Контракти, міграції, бюджет і межі даних | За потреби Codex або Claude, інший рецензує |
| Розробник | Одна задача / гілка, код і перевірки | Codex або наявний Claude Code |
| UX/UI | Прості сценарії планшета й тата, прототип і критерії | Окрема роль у межах задачі, не обов’язково постійний процес |
| QA / незалежний reviewer | Помилки, точний SHA, відтворення й доказ тестування | Gemini для redacted diff; для ризикових змін ще executable QA |
| Педагог / предметний експерт | Маніфест, вікова доречність, коректність задач/історії/мов | Окремий рецензент перед педагогічними змінами |
| Інтегратор | Rebase/conflicts, перевірки фінального SHA, merge, prod health/rollback | Один призначений worker |

Роль «предметний експерт» сама по собі не підтверджує правильність відповіді: потрібні першоджерела й педагогічна рубрика. Майбутній експерт із візуалізації працює з перевіреним сценарієм уроку й контрактом матеріалу, а не незалежно переписує програму.

## Що доступно зараз

У репозиторії вже шість Claude-ролей у `.claude/agents/`. Це корисні описи, але їхній формат і `model: sonnet` не є спільним протоколом Codex/Gemini. У поточному checkout не виявлено спільного оркестратора чи checked-in GitHub Actions workflow. У цьому executor є Codex/gh; executable `claude` і `gemini` не знайдено. Наявність доступів користувача до зовнішніх сервісів це не заперечує.

Почати зі спільної задачі/PR й контрактів [task](templates/task.schema.json), [result](templates/result.schema.json). У прикладі budget = 0 означає заборону платних API-викликів і не є оцінкою вартості реалізації; приклад не поставлений у чергу. Перед реальним запуском координатор призначає бюджет і перевіряє базовий SHA. Облік subscription quota окремий від відомого API cost. JSON Schema перевіряє форму, а авторизацію, SHA, lease, область файлів і ліміти забезпечує executor.

Спільні правила можна винести в окремий repo-файл і підключити з CLAUDE.md / AGENTS.md / GEMINI.md; це наступний implementation slice. Цей план **не додає активні інструкції чи автоматизацію** без їх реалізації й перевірки.

## Як використати саме наявний Claude на claude.ai

Офіційний [Claude Code on the web](https://code.claude.com/docs/en/claude-code-on-the-web.md) описує передавання follow-up у наявну хмарну сесію:

```bash
claude -p "Виконай задачу за посиланням GitHub, дотримуйся її scope і acceptance criteria" --cloud SESSION_ID_OR_URL --output-format json
```

Це приклад майбутнього bridge, тут не запускався. Для реального prompt з багатьма рядками використовувати stdin/безпечний structured аргумент, не shell-інтерполяцію тексту задачі.

Необхідно: перевірена версія CLI; вхід **у ту саму Claude-обліковку** через `claude auth login`; доступність cloud sessions / `allow_remote_sessions` для обліковки/організації; ID/URL конкретної сесії. Сам Anthropic API key не дає керування вебсесією. `--resume` для локальної історії й `--teleport` для перенесення не замінюють цей follow-up механізм.

Відповідь `{ok, session_id, url}` означає **поставлено в чергу**, а не «код готовий». Координатор чекає PR/result на потрібному SHA, має deadline, не надсилає повторне завдання без перевірки idempotency. При втраченому acknowledgment перевіряє job/PR перед retry. Якщо CLI не дає надійно скасувати вже queued повідомлення, позначає задачу superseded, закриває інтеграційний lease й не допускає пізній результат до merge.

Якщо bridge недоступний, наявний Claude у браузері може взяти ту саму задачу GitHub через один handoff. Це резерв, а не вимога постійно копіювати повідомлення. Окремий headless Claude worker через API/Agent SDK — інший шлях, він створює власну сесію й не видається за керування старою браузерною.

Для окремого API-authenticated headless worker документація описує scripted `--bare`, який пропускає автоматичне читання CLAUDE.md, skills, hooks/MCP та subagents. Він також пропускає OAuth/subscription credentials і потребує API-key auth: не додавати його до same-account `--cloud` bridge. Якщо обрати його для headless API-worker, передати спільні правила явно; не втратити їх непомітно. `--allowedTools` — дозвіл інструментам, не заміна OS sandbox. Не використовувати bypass-permissions як спосіб інтеграції. Cloud agent teams — Claude-only, не готова мультивендорна команда.

## Як додати Gemini

Перший крок — **read-only reviewer через платний Gemini API**: задача, redacted diff, критерії, результати перевірок. Вихід — зауваження з файлами/рядками, ризиком, відтворенням і статусом `pass / changes_requested / blocked`. Жодних production-записів, дитячих журналів або ключів.

API-модель не стає агентом-розробником автоматично. Для write-задач потрібні tool executor, ізольований checkout, команди/таймаути, policy і результат. Можна використати Gemini CLI чи власний обмежений адаптер, але спочатку перевірити актуальний спосіб автентифікації й доступність для тарифу. Поточна документація CLI має окреме попередження про перехід unpaid/Google One на Antigravity CLI; не встановлювати застарілий шлях навмання.

Gemini Developer API має суттєве обмеження щодо застосунків для осіб до 18 років; платний тариф його не прибирає. У цьому плані Gemini — **внутрішній інструмент дорослої команди розробки**, а не постачальник дитячого репетитора. Не передавати йому персональні дані дитини. Перевірка іншого продукту Google/інших умов була б окремою роботою, не автоматичним винятком. Деталі: [джерела](sources-and-decisions.md).

## Надійний контракт виконання

Задача має ID, базовий SHA, власника, дозволені файли/дії, заборонені дані, acceptance criteria, залежності, бюджет/deadline, стратегію відкату. Результат — статус, branch/commit/PR, що змінено, які тести **фактично** виконано, обмеження, використаний бюджет, blockers. Приклад першої задачі: [T-01](templates/task-example.json).

Життєвий цикл: `queued → claimed → running → review → ready_to_merge → merged → verified`; окремо `blocked / failed / cancelled`. Lease/heartbeat виконавця, унікальний attempt ID, bounded retry, dead-letter після ліміту. Не запускати двох авторів тієї самої задачі через timeout доставки. Для read-only reviewer `commit_sha` означає перевірений SHA, нового коміту він не створює. Branch із task contract є призначеною робочою/цільовою гілкою; executor перевіряє `git check-ref-format` і забороняє прямий запис у захищені гілки.

Результат іншого SHA або після cancellation не приймається автоматично. Зміна SHA після review анулює review.

GitHub Issue/PR — довготривала історія, але не достатній атомарний lock. Автоматизований orchestrator мусить мати compare-and-set lease у durable store або concurrency control workflow; коментар «я взяв» не захищає від гонок.

Окремий ізольований clone/container для кожного write-worker. Не спільний mutable checkout. Окремі гілки без force push чужої роботи. Перетин дозволених файлів — залежність задач або серійна інтеграція. Документи/API-контракти спочатку, код після узгодження контракту.

Інтегратор перевіряє точний фінальний SHA, випускає тільки в потрібний Vercel-проєкт `ai-tutor-8zmb` команди `ai-tutor18`, звіряючи ID через API/config, а не лише схожу назву. Попередня згода PO на production зберігається; повторно не вимагати preview чи загального підтвердження. Нова незворотна операція/велика неузгоджена витрата розглядається окремо. Готовність review не є дозволом довільному worker деплоїти.

## Де працює оркестратор

Початково поточна координуюча сесія + GitHub, із ручним запуском конкретної задачі. Для автономної роботи — довірений cloud worker або maintainer-dispatched GitHub Actions із журналом і stop-кнопкою. Не корпоративний ноутбук тата й не довгий процес усередині Vercel request.

Secrets зберігаються в secret manager/Actions Secrets і потрапляють лише в потрібний adapter. Не пропонувати татові вставляти їх у чат. Для Claude web bridge перевірити підтримувану account-login сесію в довіреному worker; не експортувати browser cookies. Headless API-worker може бути простішим для CI, але використовує іншу авторизацію.

У CI не виконувати недовірений PR-код із privileged `pull_request_target`; мінімальні GitHub permissions, захищена merge-операція, redacted logs, bounded CPU/time/network. Секрети/production DB недоступні code-review моделі. Для тестів — синтетичні дані. Запровадити загальний і per-task budget, ліміт ітерацій та аварійну зупинку, а не три нескінченні взаємні review.

## Перевірка перед оголошенням «команда працює»

1. Визначити й зафіксувати adapter versions/auth modes; перевірити доступ до правильного repo без показу ключів.
2. Claude bridge доставляє маленьку документаційну задачу в **наявну** вебсесію; окремо зафіксувати delivery ack і фактичний PR.
3. Gemini повертає валідний структурований review синтетичного diff; негативний кейс знаходить навмисну помилку.
4. Уточнити роль інтегратора, запустити маленький повний цикл на тестовій гілці без deployment.
5. Перевірити duplicate delivery, timeout, cancellation, конфлікт файлів, зміну SHA й заборону доступу до секретів/дитячих даних.
6. Лише після цього автоматизувати routine tasks. Наразі ці інтеграційні перевірки ще не виконувалися.
