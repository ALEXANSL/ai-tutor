# Один ZIP для всіх предметів

Нове уточнення PO, 2026-10-21: архів уже підготовленого курсу містить JSON і медіа; користувач не повинен розбирати його на сім файлів і ще два архіви. Ця вимога замінює попередню перевагу окремих полів завантаження, але зберігає необов’язковість медіа й сумісність даних.

## Користувацький сценарій

Одна основна форма: **предмет → готовий ZIP → перевірка → завантаження**. Книга PDF/EPUB залишається іншим типом матеріалу, оскільки сама книга не є готовим курсом. Старі ручні поля тимчасово доступні в «Старі способи імпорту» як резерв під час переходу, згодом прибираються з основного екрана.

Після вибору ZIP система показує знайдений формат, назву курсу, кількість уроків/задач/малюнків/PDF, що буде додано чи оновлено, і попередження. Тато не обирає «математика v2» або «література v3». Предмет не визначає парсер. Не запускати AI для читання готового JSON.

Приклад бажаного пакета (одна зовнішня папка дозволена):

```text
Geography/
  package.json
  public/course.json
  public/readings.json
  private/teacher.json
  catalog/assets.json
  catalog/pages.json
  catalog/task_tables.json
  assets/                 # необов’язково, зображення та інші медіа
  lessons/                # необов’язково, PDF уроків
```

Це упаковка наявного спільного формату, не нова предметна схема. Для підтримуваних старих пакетів використовуються їхні власні контракти. Якщо каталоги потрібні відповідній версії, вони містять валідний порожній `items: []`; відсутність медіапапок не означає некоректність JSON. Для нового єдиного входу допустимо нормалізувати відсутні необов’язкові каталоги до порожніх об’єктів **лише коли немає залежних посилань і це визначено версією адаптера**. Обов’язкові course/teacher/readings не вигадувати.

Завантажений `package.json` є маніфестом контенту, а не npm-проєктом. Не виконувати скрипти, README, інструкції чи код з архіву.

## Сумісність без переписування всіх імпортерів

| Сімейство | Сигнатура | Наявний адаптер у `app/src/server/lessons/` |
|---|---|---|
| S34 | `manifest.json`, дані уроків/тестів | `courseImport.ts`, `coursePersist.ts` |
| Старий markdown | `lessons/NN.md`, `tests/NN.json` | `literatureImport.ts` |
| Math V2 | `package_schema_version`, student/teacher_server, screens/questions/exercises | `mathCourseV2Import.ts`, `mathCourseV2Persist.ts` |
| Literature V2 | lessons/tasks, відкриті відповіді, каталоги-масиви | `literatureV2Import.ts`, `literatureV2Persist.ts` |
| Спільний chapter V3 | Маніфест `*-tutor-package`, lessons.flow, readings, каталоги-об’єкти `{items}` | `literatureV3Import.ts`, `literatureV3Persist.ts` |

Історичний S33 markdown-імпорт потребує вже наявного прив’язаного підручника/material і вибору цілі: ZIP сам по собі не створює Drive-backed книгу. Preflight має запитати або перевірити цю прив’язку, а не вгадати книгу за назвою предмета.

На сторінці чотири панелі, але перша має ще історичний fallback. Визначення: валідний explicit manifest/version → structural signature. Розпізнаний, але некоректний формат не можна «спробувати прочитати іншим парсером» і видати сторонню помилку. Невідома версія — окрема помилка. Два повні пакети в одному ZIP — повідомити про неоднозначність, не імпортувати довільний.

Різниця `task_tables.json` V2 (масив) і V3 (об’єкт) має відображатися як пояснення версії. `tsk_table.json` не перейменовувати мовчки: показати точне очікуване ім’я й знайдений файл. Діагностика має містити шлях JSON/поле, а не голе «помилка task_tables».

## Потік обробки й великі архіви

1. Авторизований тато отримує signed upload для приватного staging; браузер передає ZIP прямо у Supabase Storage. Не пересилати 300 MiB через body Vercel-функції.
2. Сервер інспектує архів до повного розпакування; визначає корінь, версію й адаптер, перевіряє JSON та всі посилання. Використати наявний `courseAssetFiles.ts` для шляхів, обгорток і `lessons`/`lesson_pdfs`.
3. Зберегти імпорт-операцію з hash архіву, сім’єю, цільовим курсом, версією адаптера й результатом preflight. Повторне натискання не створює дубль.
4. Довантажити дозволені медіа за незмінними hash-шляхами; підготувати запис даних. Публікувати лише після перевірки готовності обов’язкового контенту.
5. Повернути підсумок `success / success_with_warnings / failed / retryable`, не називати частковий запис повним успіхом. Оновити індекс уроку/задач і revision кешів.

Поточне обмеження стисненого ZIP — 300 MiB (`upload-limits.ts` і bucket). Воно не захищає від ZIP bomb. Перед релізом визначити та протестувати ліміти числа entries, розпакованого обсягу, одного файлу, JSON, compression ratio, часу й пам’яті. Поточне `unzipSync` розгортає архів у пам’ять: потрібне bounded/streaming читання або нижчі доведено безпечні ліміти. Перевіряти дубль entries до перетворення на object map; заборонити traversal, абсолютні шляхи, NUL, symlink, колізії нормалізованих шляхів. Не приховувати різні файли за збігом basename.

300 секунд `maxDuration` не гарантують завершення великого імпорту. За вимірами обрати обмежену синхронну обробку чи durable job з checkpoint і worker; статус на екрані має переживати refresh. Не тримати всю надійність у відкритій вкладці тата.

## Медіа, повторний імпорт і цілісність

- Немає `assets/` і `lessons/` та посилань на медіа → нормальний текстовий імпорт без вимоги ZIP-заглушки.
- Є посилання, але немає бінарного файлу → конкретне попередження; текст доступний, відсутній файл не має удавати робочу кнопку. Не видаляти раніше імпортований файл.
- Невалідний обов’язковий JSON/конфлікт ID → не починати запис нового курсу. Відсутній teacher key для оцінюваного питання — не «необов’язкове медіа», а помилка контенту.
- Повторне завантаження зі стабільними IDs оновлює матеріал, зберігає прогрес. Відсутність старого уроку в новому архіві не дає дозволу видалити історію. Несумісні зміни ID — окремий план зіставлення, не здогадка.

**Відоме обмеження:** наявні persistence-функції виконують послідовні REST upsert, це не одна SQL-транзакція. Storage та SQL також не мають спільної транзакції. Один preflight цього не виправляє.

Для I1 основний початковий шлях — новий пакет. Оновлення вже активного курсу допускати лише після доказу non-destructive поведінки на fault-injection тестах; якщо проміжні upsert можуть змішати чинні версії, відкласти такий reimport до I2 або заблокувати публікацію нової revision. Самого повідомлення про часткову помилку недостатньо для захисту активного уроку.

Зріз I1 може повторно використати адаптери лише з видимим станом часткового збою, idempotent retry й збереженням старих медіа; не обіцяти atomic import. Зріз I2 додає SQL/RPC-транзакцію для bounded payload або staging revision і короткий atomic publish для кожної сім’ї даних. Після збою стара опублікована версія доступна, нова незавершена — ні. Окремо прибираються orphan-медіа.

Нині V3 action видаляє staging у `finally`, у тому числі після невдачі. Для retry залишати failed job/ZIP на обмежений TTL, видаляти після успіху або завершення TTL. Точний строк задати в конфігурації, показати татові й перевірити cleanup; не зберігати архіви безстроково.

## Приймання

Повний ZIP географії; той самий з однією обгорткою; пакет без медіа; тільки assets; тільки lessons; alias lesson_pdfs; усі старі формати; V2/V3 task_tables; файл, що має тільки схоже ім’я; невідома версія; два пакети; дубль entries; ZIP bomb; traversal; обрив upload; timeout після кількох записів; повторна спроба; незмінний прогрес і старі медіа; чужа сім’я; відсутність teacher keys у дитячій відповіді й логах.

Додаткове обов’язкове уточнення PO: у новому промпті явно написати «Не використовуй Codex і не передавай йому завдання; обробляй підручник власними доступними інструментами ChatGPT». Це вимога до наступної публікації промпта разом з одним ZIP, не обмеження інструментів розробки застосунку.

Оновити [промпт підготовки контенту](../../app/public/content-package-prompt.md) разом із формою: результат — один готовий ZIP, стабільні IDs, посилання відповідають реальним файлам, catalogs валідні, assets/lessons необов’язкові. Без зміни змісту й місця ілюстрацій у вже чинних уроках.
