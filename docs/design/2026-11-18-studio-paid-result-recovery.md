# Відновлення оплаченої відповіді Майстерні

STUDIO-CONTENT раніше приховував усі post-provider помилки: schema/content, помилку цитати, обмеження note storage та помилку читання/збереження джерел. Raw відповідь після оплати не зберігалася; retry викликав модель заново без конкретної причини попередньої невдачі. Новий скриншот і список ролей доводять зупинку studio.source після assess, але не конкретний код помилки. Старий втрачений raw результат без provider/DB доступу не відновлюється.

Перед викликом CAS зберігає callId/phase/cursor/inputHash/reserved/billed=false. Provider success спочатку записує immutable scoped studio.model_result. CAS потім рівно один раз переводить reserved у фактичний spent та billed=true. Лише після цього застосовуємо відповідь. При локальній помилці зберігаються receipt і safe diagnostic(code/phase/paths/category), а retry повторно застосовує receipt без нового providercall/резерву. Успішний apply очищує pendingpointer, сам receipt не видаляється. Semantic inputHash не залежить від cap, але захищає від replay іншої теми/джерел/етапу. Pause і CAS fencing не дозволяють пізньому результату просунути інший стан. Вікно provider success→receipt write залишається невизначеним: held не можна називати фактичним списанням; за відсутності receipt новий виклик тільки після явного батьківського повтору зі збереженням попереднього резерву.

Непідтверджені optional quotes вилучаються тільки з доказових пар, з явним попередженням для автора/рецензента; summary не оголошується перевіреним чи дослівним. Raw джерела й платна відповідь зберігаються. Суттєві помилки уроку як раніше блокують публікацію. Note-only storage cap100KB узгоджено з допустимим schema-результатом і дублюванням quote evidence; rawsourcepart cap60KB не змінюється. Reduction bytebounded і може стиснути один великий note. План отримує percall exactcount/source enums; не підставляємо вигадані прив’язки лише заради валідації.

Явна нова платна генерація не плутається з повторною перевіркою збереженої відповіді. Вона отримує конкретну safe причину й попередній candidate; бюджет не збільшується, forcepass немає. Private receipt/body не передається в parent payload; безпечний стан доступності й diagnostic можна переглянути/скопіювати. Реальні production відповіді минулого збою та billing у середовищі недоступні.
