# Diary topic recognition by work, curriculum and actual content

Reported reproduction: teacher's extended topic «Михайло Ткач. “Моя Україна”. Коротко про письменника…» fails to focus ready lesson «Михайло Ткач. “Моя Україна”: країна в близьких образах» because navigation originally accepted only whole normalized titles or single explicit paragraph numbers.

## Resolution

First use the owned visible-ready-topic resolver: manual binding, exact titles, paragraph references, named literary work + author and distinctive topic words. Preserve abstention for conflicting authors, different named works, multiple paragraphs, generic wording and duplicate parts (then use the contextual stage). A recognized topic gets a direct open button as well as existing highlighting/scrolling; use the same publication/revision href as its catalogue card.

For an unresolved entry the client starts a server action and shows visible progress. The action re-derives family/child, checks entry→subject ownership and subject visibility, and offers only ready base topics (no hidden derivative topics). Two bounded OpenAI calls: (1) semantically shortlist up to four lessons from the subject catalogue plus relevant indexed textbook snippets/section titles/pages; (2) compare teacher topic/homework with sampled actual lesson blocks and those textbook passages. High-confidence (>=.88) single selection also needs a verbatim quote of >=20 characters from the supplied lesson body. A theme spanning several lessons returns up to four grounded matches (>=.75 each) with direct links, without auto-selecting one. Validate every returned ID against the offered own candidates; no model-provided URLs. A low-confidence/ungrounded result remains unresolved with guidance; nothing is persisted as a parent's manual mapping. Existing mapping remains authoritative. Subject aliases (mixed Ukraine/world history, abbreviated first/second foreign-language names, integrated nature) resolve old unbound records at read time as well as new imports. Exact/manual subject mapping wins; ambiguous subject aliases offer choices. Child links expose active owned subjects only; action/focus authorization checks the same candidate set. The subject link remains available beside a direct lesson link.

Retrieval reuses family/subject-scoped hybrid textbook search (embeddings, text-only fallback). No student identity, grades, credentials or quiz answer keys are included in prompts. Actual lesson text uses the existing five-format source loader; bounded excerpts can miss information, so confidence is not a correctness guarantee. If unavailable or too large, do not invent source content. Catalogue limit 300; each model prompt <=100k characters, teacher task remains complete within the current 16k input contract, <=4 lessons, <=8k characters each, <=12 textbook hits of <=1400 characters.

## Idempotency, latency, cost

Durable family/child/subject/task/catalogue hash stored in `jobs` as non-queued `eschool.context.v1`. Claim by unique ID BEFORE embedding/model calls; simultaneous views share pending state. Cache positives, negatives and failures. A daily key invalidates stable-ID body edits at most the next day; new task/catalogue/reader IDs invalidate immediately. Preserve parent manual binding. Pending requests older than three minutes show failure without automatically retrying a possibly billed call. Client polling is finite; server failures leave the lesson catalogue usable.

Role `school.context_match`: default OpenAI GPT-4.1 mini, <=1200 output tokens (owner override bounded <=1600), <=30s per model request, no fallback model, existing family budget and AI cost accounting. Insert defaults without replacing configured prices/routes. Reuse the exact validated route/rates. Typical input smaller than hard limits; costs depend on existing embeddings/model overrides. No paid call from SSR; the unresolved client action starts automatically once, with durable deduplication across reloads. No new migration or original-material copy.

## Validation

Exact screenshot reproduction; different quotation marks/authors/works/parts; contextual paraphrase (heated ball/ring → thermal expansion); forged IDs; fabricated quote; low confidence; unavailable lesson; failure cache; family/child/task/catalogue separation; route/rate bounds; visibility/ownership and ready-only action checks; progress/error/cached-result UI. Tests mock paid models and private storage; no private pupil session/model quality guarantee. Browser tests exercise actual matching/highlighting on mobile and desktop, alongside full unit/build/type/lint/bundle checks.
