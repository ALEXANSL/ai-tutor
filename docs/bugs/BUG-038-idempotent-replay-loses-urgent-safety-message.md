# BUG-038 — Повторна (ідемпотентна) відправка відповіді втрачає безпекове повідомлення `URGENT_REPLY_UK`

| Поле | Значення |
|---|---|
| Статус | **Open — блокує production-реліз** (виявлено QA під час перевірки US-6.15/ADR-028, передує цьому зрізу) |
| Серйозність | **Critical (безпека дитини)** |
| Пов'язано з | `app/src/server/lessons/orchestrator.ts` (`submitStepAnswer`), BUG-013 |

## Опис
Незалежний QA під час прискіпливої перевірки нового ремедіаційного циклу (US-6.15) знайшов, що ЦЕЙ баг існував і ДО зрізу ADR-028 (git-діф підтверджує рядок незмінним) — але прямо в коді, який щойно активно рецензувався на безпеку, тож фіксується негайно, а не відкладається.

Офлайн-черга застосунку (`flushQueue`, збудована саме для цього сценарію — втрата з'єднання одразу після відповіді дитини) повторно надсилає ту саму відповідь з тим самим `idempotencyKey`. На такому «ідемпотентному повторі» код бере:
```ts
let { verdict, explanation } = existing ? { verdict: existing.verdict, explanation: "" } : await evaluateAnswer(...);
```
`moderationPromise` (модерація, що визначає `severity: "urgent"` і вмикає BUG-013 override) обчислюється лише коли `!existing` — тобто **на повторі модерація НІКОЛИ не перераховується**, і `moderationForcedUrgent` лишається `false`, а `explanation` — порожній рядок.

Якщо ОРИГІНАЛЬНА відповідь (та, що вже збережена в БД) була саме тією, що викликала `severity: "urgent"` (тривожний сигнал — дитина написала щось, що вимагає негайного `URGENT_REPLY_UK`, «йди до тата»), то повтор ТІЄЇ Ж САМОЇ відповіді (типовий сценарій — обірвався інтернет одразу після відправки тривожного повідомлення) покаже дитині **порожнє пояснення поруч із «Майже!»** замість фрази-містка до дорослого. `verdict` («правильно/неправильно») зберігається коректно з БД (тож оцінка не «перекручується» на «правильно»), але сама безпекова фраза зникає безслідно.

## Чому це критично
Це саме той клас сценарію, заради якого написано BUG-013: дитина в тривожному стані пише повідомлення → з'єднання рветься (реальна, нередкісна подія на мобільному інтернеті) → офлайн-черга сама, автоматично, без відома дитини, повторює відправку → і саме в цей момент безпековий механізм мовчки вимикається. Жодного існуючого тесту (ні старого, ні нового з ADR-028) на це немає.

## Завдання для developer (терміново, перед production-релізом)
1. У `submitStepAnswer` (`orchestrator.ts`) прибрати залежність `moderationForcedUrgent`/безпекової фрази від `existing`/повтору: якщо оригінальний запис у БД (`existing`) сам має `severity: "urgent"` (чи еквівалентне поле, що фіксує це рішення при першій обробці) — повторна відправка має так само повернути `URGENT_REPLY_UK`, а не порожнє пояснення. Найпростіший і найнадійніший шлях — зберігати сам факт «це був urgent-кейс» разом із записом відповіді при першій, неідемпотентній обробці, і на повторі читати це збережене рішення, а не перераховувати модерацію заново (яка й так вимкнена на повторі навмисно, щоб не подвоювати виклик ШІ).
2. Новий регресійний тест: викликати `submitStepAnswer` двічі з одним і тим самим `idempotencyKey`, де перший виклик оцінено модерацією як `urgent` — переконатись, що ОБИДВА виклики повертають `URGENT_REPLY_UK`, не лише перший.
3. Прогнати `npm run typecheck`, `npm test`, `npm run build` перед комітом.

## Не блокує
Preview-деплой ADR-028/US-6.15 для демо — цей баг не новий і не зроблений гіршим цим зрізом. Але **виправити до production-релізу**, за рекомендацією QA.
