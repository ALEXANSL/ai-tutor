# BUG-033 — Завантаження файлу падає з 413 (Content Too Large) через платформне обмеження Vercel, не наш ліміт 50 МБ

| Поле | Значення |
|---|---|
| Статус | **Fixed** (2026-09-27) — перероблено на резюмоване завантаження, деталі нижче |
| Серйозність | **Critical** — «Завантажити файл» (ADR-024) не працює взагалі для реальних файлів підручників |
| Зріз | ADR-024 (завантаження книги з браузера), архітектурна помилка проєктування |
| Пов'язано з | `app/src/app/api/parent/books/upload/route.ts`, `app/src/server/drive/upload.ts`, `app/src/components/parent/books/UploadBookButton.tsx` |

## Кроки відтворення
1. Кабінет тата → «Мої книги» → «Завантажити файл».
2. Обрати PDF/EPUB — за словами Алекса, файл менший за 50 МБ (заявлений ліміт застосунку).
3. П'ять спроб поспіль — жодна не спрацювала.

## Корінна причина (знайдено через Console браузера, F12, оскільки в серверних логах Vercel НЕ БУЛО ЖОДНОГО запиту на `/api/parent/books/upload` — сам факт, що свідчив про клієнтську, а не серверну проблему)
```
POST https://ai-tutor-8zmb.vercel.app/api/parent/books/upload 413 (Content Too Large)
```
**Vercel Serverless Functions мають платформне обмеження розміру тіла запиту — 4.5 МБ.** Це обмеження застосовується на рівні маршрутизації/edge Vercel, ДО того, як запит взагалі доходить до нашого коду (`route.ts`) — тому наш власний ліміт 50 МБ (`MAX_UPLOAD_BYTES`, `boundedUploadStream`) і весь механізм стрімінгу в межах функції ніколи не встигають спрацювати: Vercel обриває запит на своєму рівні для будь-якого файлу більшого за ~4.5 МБ, незалежно від `runtime: "nodejs"` чи стрімінгового читання тіла всередині функції.

Це пояснює одразу все спостережене:
- Чому немає жодного логу на сервері (Vercel відхиляє запит РАНІШЕ виклику функції — `console.error` в нашому коді просто не встигає спрацювати).
- Чому помилка стається для «файлу меншого за 50 МБ» — заявлений у застосунку ліміт (50 МБ) ніколи не був реальним технічним лімітом Vercel-функцій; це помилкове архітектурне припущення при проєктуванні ADR-024 (стрімінг у межах Node.js Serverless Function НЕ обходить платформний ліміт тіла запиту — це поширена й добре задокументована особливість Vercel, яку не врахували при плануванні).

## Правильний фікс (не точкове налаштування — зміна архітектури завантаження)
Файл не повинен проходити через наш сервер як тіло HTTP-запиту взагалі. Правильний патерн для завантаження великих файлів у Google Drive з браузера:
1. Клієнт запитує в нашого сервера (легкий запит, без файлу) **сесію резюмованого завантаження** (`resumable upload session`) — сервер звертається до Google Drive API (`files.create` з `uploadType=resumable`), отримує від Google тимчасовий **session URI**, і повертає цей URI клієнту (сам refresh-токен і клієнтський секрет НІКОЛИ не потрапляють у браузер — лише одноразовий, обмежений за часом і файлом session URI).
2. Браузер **сам, напряму** надсилає байти файлу на цей `session URI` Google (можна частинами/chunks) — обходячи наш сервер і, відповідно, ліміт Vercel Functions повністю.
3. Після завершення завантаження браузер повідомляє наш сервер (легкий запит із `drive_file_id`), і сервер продовжує з `ingestUploadedMaterial`/`kickJobs()`, як і зараз.

Це стандартний, задокументований підхід Google Drive API саме для файлів, більших за кілька мегабайт, і єдиний спосіб обійти обмеження serverless-платформ (Vercel, AWS Lambda тощо) на розмір тіла запиту.

## Завдання для developer
1. Переробити `app/src/app/api/parent/books/upload/route.ts` на два легких ендпойнти: (а) створення сесії резюмованого завантаження (без файлу в тілі), (б) підтвердження завершення завантаження (легкий JSON, без файлу).
2. Переробити `UploadBookButton.tsx`: замість одного `fetch` з файлом як тілом — отримати session URI від нашого сервера, потім надіслати файл (одним запитом чи частинами) напряму на `session URI` Google з браузера.
3. Видалити/спростити `boundedUploadStream`/стрімінгову логіку в `app/src/server/drive/upload.ts` — вона більше не потрібна в такому вигляді (файл більше не проходить через нашу функцію).
4. Перевірити реальним файлом 10-40 МБ (не лише юніт-тестами) — це саме той клас помилки, який unit/e2e тести з мокованими об'єктами не ловлять (BUG-028 клас прогалини — реальна поведінка платформи, не логіки коду).
5. Оновити `docs/adr/024-book-upload-from-browser-shared-drive-file-connector.md` цим уточненням (платформне обмеження Vercel 4.5 МБ, чому обраний резюмований підхід).

## Рішення PO
Терміново — основна фіча ADR-024 (заради якої і затівалось сьогоднішнє налаштування Google Drive) не працює для реальних файлів підручників.

## Фікс (2026-09-27)

Реалізовано саме той підхід, що описаний у «Правильний фікс» вище — файл більше **ніколи** не проходить через наш сервер як тіло HTTP-запиту:

1. **`POST /api/parent/books/upload`** (`app/src/app/api/parent/books/upload/route.ts`) — легкий JSON-запит (`{ fileName, mimeType, size }`, без файлу). Сервер відкриває сесію резюмованого завантаження в Google Drive (`initResumableUpload` у `app/src/server/drive/upload.ts`: `files.create?uploadType=resumable`, метадані-only) і повертає браузеру `{ sessionUrl }` — тимчасовий, специфічний для одного файлу `session URI` з заголовка `Location` Google.
2. **`UploadBookButton.tsx`** (`app/src/components/parent/books/UploadBookButton.tsx`) сам, напряму з браузера, робить `PUT` усього файлу одним запитом на цей `sessionUrl` — прямо на `googleapis.com`, повз наш сервер і, відповідно, повз ліміт Vercel. Google повертає в відповідь метадані щойно створеного файлу, включно з `id`.
3. **`POST /api/parent/books/upload/complete`** (новий ендпойнт, `app/src/app/api/parent/books/upload/complete/route.ts`) — знову легкий JSON-запит (лише `{ driveFileId }`). Сервер (`confirmUpload` у `upload.ts`) повторно запитує метадані файлу напряму в Drive API за цим id (ніколи не довіряючи client-side імені/MIME/розміру), перевіряє, що файл дійсно лежить у `GOOGLE_DRIVE_UPLOADS_FOLDER_ID` (захист від confused-deputy) і що реальний розмір ≤ 50 МБ, і лише тоді викликає `ingestUploadedMaterial` + `kickJobs()` — як і раніше.

`boundedUploadStream` прибрано повністю з `server/drive/upload.ts` — вона вирішувала проблему («не буферизувати файл у пам'яті нашої функції»), яка з новою архітектурою більше не існує: файл більше не тече через нашу функцію в жодному вигляді.

**Ліміт 50 МБ лишається продуктовим рішенням** (не платформним): перевіряється (а) на клієнті одразу при виборі файлу (`File.size`, для миттєвого фідбеку), (б) на сервері при відкритті сесії за заявленим розміром (рання відмова, без звернення до Drive), і (в) знову на сервері в `confirmUpload` — за **реальним** розміром, який повідомляє сам Drive після завершення завантаження (заявлений розмір із кроку «б» неможливо перевірити на правдивість, доки файл не залито).

**Безпека:** `session URI` безпечно передавати в браузер — це не OAuth-токен і не client secret (які як і раніше формуються й лишаються виключно на сервері, `getUserAccessToken`), а одноразовий, обмежений часом і конкретним файлом токен, яким сам Google керує. Перевірено `npm run check:bundle` після рефакторингу — 0 leaks, жоден секрет (client secret, повний OAuth токен) не потрапляє в клієнтський бандл.

**Тести:** `app/src/server/drive/upload.test.ts` переписано під нову пару функцій `initResumableUpload`/`confirmUpload` — перевіряють, що (1) відкриття сесії ніколи не відправляє файлові байти (лише JSON-метадані), (2) валідація (тип/розмір/конфігурація) відбувається до будь-якого звернення до Drive, (3) `confirmUpload` відхиляє файл не з тієї папки (confused-deputy), непідтримуваний тип чи розмір понад ліміт — усе за метаданими, отриманими від Drive, а не від клієнта. `tests/e2e/specs/s1-books-surface.spec.ts` доповнено перевіркою, що обидва нові ендпойнти (`/upload` і `/upload/complete`) без сесії ведуть на `/login`, а не витікають секрет.

**Прогони перед комітом:** `NODE_USE_ENV_PROXY=1 npm run typecheck` ✅, `npm run lint` ✅, `npm test` (657/657 юніт-тестів) ✅, `npm run build` ✅, `npm run check:bundle` (0 leaks) ✅, `npm run test:e2e` (66/66) ✅.

**Що НЕ перевірено в цій сесії (потребує ручної перевірки Алекса на реальному застосунку):** у пісочниці немає реального Google-акаунта з підключеним `drive.file`-конектором, тож наскрізний прогін «обрати справжній PDF/EPUB 10–40 МБ → дійсно долетів у Drive → з'явився в «Мої книги» й проіндексувався» не був відтворений насправді. Юніт-тести підтверджують саму механіку (правильні виклики Drive API, відсутність файлових байтів у запитах до нашого сервера, відхилення підробленого/чужого `drive_file_id`), а e2e — що нові ендпойнти захищені сесією. Але єдиний спосіб дійсно підтвердити фікс — саме той крок, що й виявив баг: реальний файл у реальному браузері на preview-деплої. **Прохання до Алекса:** після деплою на preview повторити ті самі п'ять спроб із BUG-033 (той самий файл, якщо можливо) і підтвердити, що завантаження проходить і книга з'являється в «Мої книги».
