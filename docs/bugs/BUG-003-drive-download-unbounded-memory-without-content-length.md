# BUG-003 — Завантаження файлу з Drive не обмежує пам'ять, якщо сервер не надішле `Content-Length`

| Поле | Значення |
|---|---|
| Серйозність | **Minor** |
| Зріз | S1 |
| Пов'язані критерії | US-2.6 КП-5 («кабінет показує статус і орієнтовну вартість»), NFR-PLAT (стійкість); дослідницький сценарій QA «великі PDF/EPUB» (задача оркестратора) |
| Статус | **Fixed** (S2, 2026-09-25): `downloadFile` тепер читає тіло потоково (`res.body.getReader()`) з лічильником байтів і перериває завантаження (`reader.cancel()`) одразу після перевищення `MAX_FILE_BYTES`, не чекаючи `arrayBuffer()`. Юніт-тест `drive.test.ts` («BUG-003: aborts a streamed download…») симулює потік без заголовка `content-length`, не виділяючи реальних 150+ МБ. |

## Кроки відтворення (код-рев'ю, без реального Drive)
1. `app/src/server/drive/google.ts` → `downloadFile(fileId, token)`.
2. Файл читається так:
   ```ts
   const res = await driveGet(`${DRIVE_API}/files/${fileId}?alt=media&supportsAllDrives=true`, token, fetchImpl, 120_000);
   const length = Number(res.headers.get("content-length") ?? 0);
   if (length > MAX_FILE_BYTES) throw new DriveError("file too large", 413, "too_large");
   const buf = new Uint8Array(await res.arrayBuffer());   // <-- увесь файл у пам'ять ДО другої перевірки
   if (buf.byteLength > MAX_FILE_BYTES) throw new DriveError("file too large", 413, "too_large");
   return buf;
   ```
3. Якщо відповідь Google Drive не містить заголовка `Content-Length` (`length` стає `0`,
   перша перевірка не спрацьовує ні для якого розміру файлу), функція одразу викликає
   `res.arrayBuffer()` — це буферизує **весь** файл у пам'яті serverless-функції, і лише
   після цього перевіряє фактичний розмір.

Юніт-тест `drive.test.ts` («refuses oversized files») перевіряє лише випадок, коли
`Content-Length` присутній і великий — не перевіряє випадок відсутнього заголовка з реально
величезним тілом відповіді.

## Очікуваний результат
Ліміт `MAX_FILE_BYTES = 150 МБ` (US-2.6 КП-5, R-20 «книги… можуть бути великими (дорога
індексація)») має захищати serverless-функцію (Vercel, обмежена пам'ять) від файлу, який тато
випадково поклав у папку (наприклад, відсканований у високій роздільності підручник на
500 МБ–1 ГБ, або взагалі не PDF/EPUB, перейменований під потрібне розширення) — незалежно від
того, чи Drive повернув `Content-Length`.

## Фактичний результат
За відсутності заголовка (нетиповий, але можливий випадок — залежить від того, як Google Drive
API віддає бінарні дані для конкретного файлу/диска) файл повністю завантажується в пам'ять
**до** того, як спрацює перевірка розміру. Для дуже великого файлу це може вичерпати пам'ять
Vercel-функції (обвал з незрозумілою помилкою замість чіткого `too_large`) ще до того, як
парний PDF/EPUB-парсер взагалі побачить файл.

## Чому не Major/Critical
- Не стосується безпеки дитини чи приватності.
- Typical-кейс (Drive зазвичай надсилає `Content-Length` для `alt=media`) уже захищений.
- Помилка (`OOM`/crash функції) все одно не призводить до пошкодження даних чи витоку —
  наслідок лише «індексація впаде з незрозумілою помилкою», що потрапить під `retryable`
  (генеричний `catch` у `errorCodeOf` → `failed`) і піде на повторну спробу без нескінченного
  циклу (обмежено `max_attempts`).

## Завдання для `developer`
1. У `downloadFile` (`app/src/server/drive/google.ts`) не покладатись лише на
   пост-перевірку `buf.byteLength`: читати тіло відповіді потоково (`res.body` як
   `ReadableStream`, або `for await (const chunk of res.body)`, залежно від рантайму) з
   лічильником отриманих байтів і перервати завантаження (`reader.cancel()` /
   `AbortController`), щойно накопичена кількість перевищить `MAX_FILE_BYTES`, — і кинути
   `DriveError("file too large", 413, "too_large")` без повного буферизування файлу.
2. Додати юніт-тест: мок `fetch`, що повертає відповідь **без** заголовка `content-length`,
   але з тілом, яке симулює потік значно більший за `MAX_FILE_BYTES` (наприклад,
   `ReadableStream`, що видає чанки, рахуючи їх, без реального виділення 150+ МБ у тесті) —
   перевірити, що функція кидає `too_large`, не намагаючись матеріалізувати весь буфер.
3. Переконатися, що зміна не ламає існуючий тест «refuses oversized files»
   (`app/src/server/drive/drive.test.ts`).
