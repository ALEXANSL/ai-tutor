# BUG-005 — Збереження PIN дає загальне «Щось пішло не так», коли `PIN_PEPPER` не налаштовано

| Поле | Значення |
|---|---|
| Серйозність | **Major** |
| Зріз | S0/S1 (виявлено на демо Алекса, виправлено в S2) |
| Пов'язані критерії | US-1.5 КП-5 (тато задає PIN), NFR-PLAT (зрозумілі помилки налаштування) |
| Статус | **Fixed** (S2, 2026-09-25) |

## Кроки відтворення
1. На Vercel (або локально) змінна середовища `PIN_PEPPER` не задана, або задана, але коротша за
   16 символів (`getPinPepper()` у `app/src/server/env.ts` повертає `null` в обох випадках).
2. Тато заходить у **Налаштування → PIN режиму тата** і намагається задати PIN.
3. `setPinAction` (`app/src/app/actions/parent.ts`) викликає `setParentPin`, яка повертає
   `{ ok: false, error: "unavailable" }` (`app/src/server/auth/parent-mode.ts`).
4. `setPinAction` мапить `"unavailable"` на `uk.common.error` — те саме загальне «Щось пішло не
   так. Спробуйте ще раз.», що й для звичайної помилки бази даних.

## Очікуваний результат
Для тата — конкретне, дієве повідомлення, яке пояснює **причину** (без розкриття значення
змінної): «Сервер не налаштовано: змінна `PIN_PEPPER` відсутня або коротша за 16 символів — див.
інструкцію (`app/README.md`)». Сервер додатково пише в лог (без значення) причину — щоб було видно
в логах Vercel, не лише в інтерфейсі.

## Фактичний результат (до фіксу)
Тато бачив «Щось пішло не так. Спробуйте ще раз.» — невідмінне від тимчасового збою бази — і не
міг здогадатися, що проблема в конфігурації сервера, а не в тому, що він щось неправильно ввів;
повторні спроби нічого не змінювали. Жодного лог-запису про причину не було.

## Причина
`SetPinError`/`EnterParentModeError` мали спільне значення `"unavailable"` для «нема сервісу» й
«нема конфігурації», а виклики на стороні `actions/*.ts` мапили його на загальний
`uk.common.error`, не розрізняючи причину.

## Виправлення (S2)
1. `app/src/server/env.ts`: нова `pinPepperIssue(): "missing" | "too_short" | null` — чиста
   перевірка без побічних ефектів; `getPinPepper()` використовує її й лишається без змін ззовні.
2. `setParentPin` і `enterParentMode` (`app/src/server/auth/parent-mode.ts`) пишуть
   `console.error` із причиною (`PIN_PEPPER ${issue}`, без значення) при поверненні
   `"unavailable"`.
3. `setPinAction` (`app/src/app/actions/parent.ts`): `"unavailable"` тепер мапиться на нове
   `uk.parent.settings.pinUnavailable` — конкретне повідомлення з назвою змінної й посиланням на
   інструкцію, а не на `uk.common.error`.
4. Звірено інші місця з `"unavailable"`/відсутньою конфігурацією (Drive, ШІ-провайдери, папка) —
   вони вже мають конкретні повідомлення з S1 (`drive_not_configured`, `ai_not_configured`,
   `access.unknownBody` — назва змінної й дія). Новий випадок був лише в `setPinAction`.

## Тести
- `app/src/server/env.test.ts`: `pinPepperIssue()` — `"missing"` (відсутня/порожня), `"too_short"`
  (< 16 символів), `null` (валідна); `getPinPepper()` узгоджено повертає `null`/значення.
- `app/src/lib/pin-errors.test.ts`: `pinSaveErrorMessage("unavailable")` містить назву змінної й
  посилання на інструкцію та **не дорівнює** загальному `uk.common.error`; `"mismatch"`/`"format"`
  мапляться на власні повідомлення. Текст навмисно не покладено в спільний словник `uk.ts`
  (`app/scripts/check-client-bundle.mjs` вважає саму НАЗВУ секретної змінної витоком, не лише
  значення) — `pin-errors.ts` позначено `import "server-only"`, щоб клієнтський код узагалі не міг
  його імпортувати; перевірено повторним `npm run check:bundle`.
