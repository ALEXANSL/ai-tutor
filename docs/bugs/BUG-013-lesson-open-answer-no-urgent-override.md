# BUG-013 — Відкрита відповідь уроку з `severity: "urgent"` НЕ отримує детерміновану фразу «йди до тата» — дитина бачить звичайну педагогічну відповідь

| Поле | Значення |
|---|---|
| Серйозність | **Critical** |
| Зріз | S4 (безпека в розмові, ADR-009) |
| Пов'язані критерії | NFR-SAFE-4 («у категорії «терміново» — **завжди** просить піти до тата зараз»); US-12.1 КП-2; docs/STATUS.md S4, буквальний текст: «для severity = 'urgent' відповідь дитині **завжди** детермінована... **незалежно від того, що згенерувала модель репетитора** (це перевірено кодом, не лише промптом — жодна модель не може «забути» цю фразу)» |
| Статус | **Відкрито** |

## Кроки відтворення (код-рев'ю + новий регресійний тест)
1. `app/src/server/lessons/chat.ts` (`askTopicChat`) і `app/src/server/lessons/friendChat.ts`
   (`askFriendChat`) обидва мають однаковий, коректний патерн (рядки коментовані буквально
   «NFR-SAFE-4, US-12.1 КП-2»):
   ```ts
   const answerText =
     moderationResult.severity === "urgent"
       ? "Це звучить дуже серйозно. Будь ласка, зараз піди й скажи про це тату — він удома і допоможе."
       : (answerOutcome ?? "Зараз не вдалося відповісти...");
   ```
2. `app/src/server/lessons/orchestrator.ts` → `submitStepAnswer` (відкрита відповідь кроку уроку,
   `step.type === "open"`) **не має цього патерну взагалі**. Після модерації (рядки 298–311) код
   лише викликає `recordSafetyEvent(...)` (записує подію тату — це працює правильно) і одразу йде
   далі з `verdict`/`explanation`, що повернув **окремий** виклик `evaluateAnswer` (роль
   `answer_evaluation`) — жодного перезапису на детерміновану фразу немає:
   ```ts
   const { verdict, explanation } = existing ? { verdict: existing.verdict, explanation: "" } : await evaluateAnswer(...);
   if (moderationPromise) {
     const moderation = await moderationPromise;
     await recordSafetyEvent(familyId, session.child_profile_id, "lesson", openText!, moderation, { sessionId });
     // <-- нічого не робить з `moderation.severity` для `explanation`/`verdict`
   }
   ...
   return { verdict, explanation, formatChangeSuggested, next }; // explanation завжди від evaluateAnswer
   ```
3. Новий регресійний тест (цей прогін QA), що документує саме цю поведінку:
   `app/src/server/lessons/orchestrator.test.ts` →
   `describe("submitStepAnswer + moderation (NFR-SAFE-4, US-12.1 КП-2) — QA finding, see docs/bugs/BUG-013")`
   — мокує `moderateMessage` так, щоб повернути `severity: "urgent"`, і показує, що
   `result.explanation` дорівнює тому, що написала модель-оцінювач («Гарна спроба, продовжуй!»),
   а не детермінованій фразі — тест **проходить**, тобто фіксує саме поточну, помилкову поведінку.
4. Контрастні тести того самого прогону — `app/src/server/lessons/chat.test.ts` і
   `app/src/server/lessons/friendChat.test.ts` (нові, раніше цих файлів не існувало) — показують,
   що для чату теми й «ШІ-друга» той самий сценарій **коректно** повертає детерміновану фразу.

## Очікуваний результат
Дитина пише у відкритій відповіді уроку щось, що модератор класифікував як `severity: "urgent"`
(наприклад «я хочу собі зашкодити», розкриття насильства вдома, контакт з незнайомцем) →
екран одразу показує детерміновану фразу «Це звучить дуже серйозно… зараз піди й скажи про це
тату», **а не** педагогічний фідбек на кшталт «Гарна спроба, продовжуй!» чи «Частково правильно».
Точнісінько так само, як уже реалізовано в `chat.ts`/`friendChat.ts`.

## Фактичний результат
Дитина, яка написала щось «терміново» тривожне як відповідь на відкрите питання уроку, бачить
звичайний педагогічний фідбек від `answer_evaluation` і урок продовжується як зазвичай (наступний
крок/блок) — **жодного видимого сигналу дитині**, що щось не так. Тато сповіщення все ж отримує
(в кабінеті й — якщо дійде до `enqueueUrgentDelivery`, а ця частина коду в orchestrator.ts
викликається через `recordSafetyEvent`, тобто працює правильно — e-mail/Telegram), але дитина в
цю саму мить лишається сам на сам з проблемою й уроком, що йде далі, без жодної репліки-«місточка»
до тата.

## Чому Critical
- Це прямий Must-критерій безпеки дитини (NFR-SAFE-4), і саме та поведінка, яку
  `docs/STATUS.md` явно стверджує як «перевірено кодом» для **усіх** місць модерації S4 — але
  насправді перевірено (і працює) лише у 2 з 3 місць (чат теми, «ШІ-друг»); третє (відкрита
  відповідь уроку) — найімовірніше місце, де дитина розкриє щось важке, бо це вільний текст у
  контексті уроку, а не окремий чат.
- Наслідок — не «трохи гірший UX», а саме відсутність негайної, зрозумілої дитині вказівки піти
  до тата в момент реальної тривоги; покладатися доводиться лише на те, що дитина сама здогадається
  піти до тата, побачивши нейтральний педагогічний коментар.
- Легко пропустити на демо: рецензент-модель (`answer_evaluation`) з високою ймовірністю сама
  напише щось тепле й нейтральне на тривожну відповідь (промпт має загальну «преамбулу безпеки»),
  тому візуально це може виглядати «не зовсім погано» — але це саме той сценарій, для якого
  ADR-009 нарочито ввів детермінований код-рівень захисту («жодна модель не може «забути» цю
  фразу»), а тут цей захист відсутній.

## Завдання для `developer`
1. У `submitStepAnswer` (`app/src/server/lessons/orchestrator.ts`), одразу після
   `await recordSafetyEvent(...)`, якщо `moderation.severity === "urgent"` — замінити
   `explanation` (і, якщо потрібно для UI/анімації, `verdict`, наприклад на `"partial"`, щоб не
   показувати «неправильно» в тон тривозі) на ту саму детерміновану фразу, що вже
   використовується в `chat.ts`/`friendChat.ts` (варто винести в спільну константу/функцію,
   напр. `server/safety/urgentReplyUk.ts`, і використати в усіх трьох місцях — зараз рядок
   продубльований у двох файлах і його ще предстоїть додати в третє; спільна константа також
   унеможливить майбутнє розходження формулювання).
2. Переконатися, що `branch`/`next` (перехід до наступного кроку/блоку) при цьому поводиться
   безпечно — наприклад, не форсувати автоматичний перехід далі уроком одразу після термінового
   сигналу без хоча б проміжного екрана (дизайн-рішення для `developer`/PO, мінімум — не
   погіршувати поточну поведінку).
3. Додати регресійний тест (наявний новий тест у `orchestrator.test.ts` вже документує очікуваний
   рядок — після фіксу просто змінити очікування в тесті QA на `toBe("Це звучить дуже серйозно...")`
   і прибрати позначку "QA finding").
