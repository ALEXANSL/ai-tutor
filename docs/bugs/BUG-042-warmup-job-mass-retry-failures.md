# BUG-042 — три причини масових зайвих ретраїв `library.warm_topic` (продакшн, 2026-09-28)

| Поле | Значення |
|---|---|
| Статус | **Fixed** (усі три причини) |
| Серйозність | **Critical** — реальний, поточний вплив на продакшн: багато джобів на спробі 8–11 із 20, зайві витрати на ШІ-виклики через повторні plan→generate→review цикли |
| Пов'язано з | `app/src/server/lessons/schema.ts`, `app/src/server/lessons/pipeline.ts`, `app/prompts/lesson_generation.md`, `app/src/server/ai/providers/anthropic.ts`, `app/src/server/lessons/generate.ts`, `app/src/server/lessons/warmup.ts` |

## Опис
Алекс прогнав діагностичний запит до `jobs` (`type='library.warm_topic'`) під час реального масового прогріву й знайшов три різні причини провалів.

### Причина 1 (найдорожча): `misconceptionUk` іноді порожній рядок → провал ВСЬОГО блоку
Схема (`choiceStep.options[].misconceptionUk`) вимагала `.min(1)` для присутнього поля. Модель регулярно повертала `misconceptionUk: ""` для одного з неправильних варіантів (підтверджено на РІЗНИХ предметах — математика, міфологія, література — це загальна проблема надійності промпту, не тема-специфічна), і Zod-валідація відхиляла ВЕСЬ блок, витрачаючи повний цикл plan+generate+review на повторну спробу.

**Виправлення:**
1. (основне) `prompts/lesson_generation.md`, п. 11 — вимога до `misconceptionUk` для КОЖНОГО неправильного варіанту тепер сформульована як обов'язкова (не побажання), з конкретним прикладом.
2. (захист) `schema.ts` — `.min(1)` знято, поле лишається `.optional()` з `.max(300)`: порожній рядок так само прийнятний, як і відсутнє поле.
3. (захист) `pipeline.ts`'s `fillMissingMisconceptions` — після кожної генерації підставляє нейтральний фолбек-текст для будь-якого неправильного варіанту з порожнім/відсутнім `misconceptionUk`, замість падіння валідації.

### Причина 2: голий `anthropic request error 400` без деталей
`jobs.last_error` обрізає до 500 символів, але деталей не було взагалі — тіло відповіді API (`e.error`) ніколи не логувалося. `anthropic.ts` тепер логує повне тіло помилки (`console.error`) для будь-якого `BadRequestError`/`NotFoundError`/`APIError` ще ДО того, як повідомлення обрізається на шляху до БД.

Досліджено, чи це той самий корінь, що й причина 1 (Anthropic відхиляє сам запит через форму схеми `misconceptionUk`) — переконливих доказів у коді не знайдено (форма поля звичайна, `zodOutputFormat` не мала б її відхиляти на рівні запиту); з новим логуванням наступний реальний `400` дасть остаточну відповідь.

### Причина 3: теми без жодного індексованого фрагмента ретраяться до 20 разів даремно
`generateOneBlock` кидав звичайний `Error` для теми без індексованих `chunks` (підтверджені реальні теми української міфології: «Лісовик», «Дажбог і Жива», «Сокіл-Род», «Дерево Життя») — умова, яка НІКОЛИ не виправиться повторною спробою. `registerLibraryWarmJobs` (`warmup.ts`) уже мав такий механізм для `ReviewerUnavailableError` (`__warmupGiveUp`), але не для цього випадку.

**Виправлення:** новий клас `NoIndexedFragmentsError` (`generate.ts`, той самий текст помилки, що й раніше — `startLessonAction` продовжує матчити на нього), підключений до того самого `__warmupGiveUp`-механізму в `warmup.ts`.

## Окремо (не блокує, для довідки)
Алекс окремо повідомив, що теми на кшталт «Лісовик»/«Дажбог і Жива»/«Сокіл-Род» видно ДВІЧІ в списку масового прогріву на `/parent/subjects/[id]`. За інспекцією коду (`ingest/pipeline.ts`'s `runStructure`, `mergeByTitle`) дедуплікація тем виконується per-`material_id` (`oldTopics` вибирається `.eq("material_id", materialId)`), а НЕ по всьому предмету — тож якщо до одного предмета прикріплено два різні `materials`-рядки з міфологічним змістом, кожен незалежно породжує свій набір тем з однаковими назвами, і вони ніколи не зливаються між собою. Це підтверджує підозру Алекса на рівні коду; чи дійсно на цьому предметі є дублікат `materials`-рядка — не перевірялося (потрібен прямий запит до БД). Виправлення не входило до цього зрізу.
