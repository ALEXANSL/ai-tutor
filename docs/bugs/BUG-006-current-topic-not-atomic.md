# BUG-006 — Вибір «поточної теми» не атомарний: обрив мережі/подвійний сабміт може залишити 0 або 2 поточні теми

| Поле | Значення |
|---|---|
| Серйозність | **Major** |
| Зріз | S2 |
| Пов'язані критерії | US-3.1 КП-1 («тема збережена й позначена «поточна»», а вибір теми активує предмет); DoD п.1 (стійкість — задача оркестратора: обрив зв'язку/повторна дія) |
| Статус | **Open** (знайдено QA S2, регресійний тест доданий) |

## Кроки відтворення (код-рев'ю + DB-тест)
1. `setCurrentTopicAction` (`app/src/app/actions/subjects.ts`) виконує **три послідовні,
   не об'єднані в транзакцію** виклики PostgREST через `forFamily(...).update(...)`:
   1. `update topics set is_current = false where subject_id = X and is_current = true`
   2. `update topics set is_current = true where id = <нова тема>`
   3. `update subjects set active = true where id = X`
2. У схемі (`supabase/migrations/20260926100100_s1_materials_search.sql`, таблиця `topics`)
   немає обмеження, яке гарантує «не більше однієї поточної теми на предмет» — ні
   частковий унікальний індекс (`unique index … where is_current`), ні тригер.
3. Новий регресійний DB-тест `app/tests/db/s2-subjects.test.ts`
   («BUG-006: the schema does NOT prevent two topics of the same subject from both being
   current») підтверджує це напряму на рівні бази: після ручного `UPDATE` другої теми на
   `is_current = true` (без скидання першої) обидві теми лишаються «поточними» — база це
   дозволяє.

## Очікуваний результат
- Якщо крок 1 (`clear`) виконався, а крок 2 (`set`) не встиг (обрив мережі, тайм-аут,
  падіння serverless-функції між двома окремими HTTP-запитами до PostgREST) — предмет
  повинен або зберегти попередню поточну тему (відкат), або дати татові чітку помилку
  «не вдалося зберегти, спробуйте ще раз» без втрати попереднього стану — **не** тихо
  залишитися без жодної поточної теми.
- Подвійний сабміт форми (тато двічі швидко тисне «Зберегти» на двох різних темах,
  напр. через повільну мережу на планшеті — сценарій прямо з чеклісту стійкості) не
  повинен мати можливості залишити дві теми одночасно позначеними `is_current = true`.
- Бажано: сама база (партціальний унікальний індекс) не дозволяє інваріанту порушитися,
  незалежно від того, скільки окремих HTTP-запитів робить сервер — це і є «джерело
  правди», а не лише порядок викликів у server action.

## Фактичний результат
- Крок 1 і крок 2 — окремі HTTP-запити до Supabase (немає `BEGIN…COMMIT`,
  `forFamily` не підтримує транзакцій — рев'ю `app/src/server/db/family-scope.ts`).
  Обрив з'єднання/падіння функції між ними залишає предмет **без жодної поточної теми**
  (гірше, ніж було до спроби), хоча тато міг щойно бачити на екрані, що предмет активний
  з іншою темою.
- Якщо крок 2 виконався, а крок 3 (`activate subject`) не встиг — тема позначена
  `is_current = true`, але `subjects.active = false`; сторінка «Предмети» показує бейдж
  «Неактивовано», хоча тема нібито вибрана (суперечність між екраном списку й екраном
  предмета — `getSubjectDetail` бере `active` окремо від `currentTopicId`).
- Схема БД не має нічого, що завадило б двом рядкам `topics` одного `subject_id` мати
  `is_current = true` одночасно (продемонстровано регресійним тестом вище) — навіть якщо
  серверний код завжди коректний, будь-яка майбутня зміна (нова RPC, ручний SQL, скрипт
  міграції даних) може мовчки порушити інваріант без жодного попередження на рівні бази.

## Чому Major, не Critical
- Не стосується безпеки дитини чи витоку даних.
- Не блокує використання назавжди: повторне відкриття сторінки предмета й повторний
  вибір теми виправляє стан.
- Але прямо порушує явний критерій прийняття US-3.1 КП-1 («тема збережена») під час
  звичайного, реалістичного мережевого збою на планшеті — саме той клас сценаріїв
  («обрив інтернету посеред дії», «повторна дія після збою»), який задача QA прямо
  вимагає перевірити для кожного зрізу.

## Завдання для `developer`
1. Зробити вибір поточної теми **атомарним на рівні бази**: одна SQL-функція/RPC
   (`service_role`, за зразком `record_ai_call`/`register_app_user` з S0/S1), що в межах
   однієї транзакції: перевіряє готовий підручник → знімає `is_current` з усіх тем
   предмета → ставить нову → активує предмет; повертає помилку без часткового запису,
   якщо будь-який крок не пройшов.
2. Додати **частковий унікальний індекс** на рівні схеми
   (`create unique index on topics (subject_id) where is_current`) як «страховку»
   незалежно від того, хто й як пише в таблицю в майбутньому (нові RPC, ручні виправлення,
   скрипти) — це перетворить регресійний тест `s2-subjects.test.ts` на такий, що
   **падає**, якщо інваріант колись порушиться; після фіксу оновити цей тест (прибрати
   `expect(rows).toHaveLength(2)` — перевірити, що другий `UPDATE` або сам відкидається
   унікальним індексом, або перший рядок скидається тригером/RPC).
3. Перевірити на UI: подвійний сабміт форми `CurrentTopicPicker` (швидкий подвійний тап
   по «Зберегти» на двох різних темах) — після фіксу кнопка має блокуватися на час
   `pending` (уже є `disabled={pending || !selectedId}` — переконатися, що це справді
   не дає відправити другий запит до завершення першого; регресія в `plan.test.ts` чи
   окремий компонентний тест).

## Тести

  поточну відсутність інваріанту на рівні бази; після фіксу цей тест має бути
