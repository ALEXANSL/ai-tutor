# BUG-009 — Один і той самий блок бібліотеки може повторитися двічі в одному уроці

| Поле | Значення |
|---|---|
| Серйозність | **Major** |
| Зріз | S3 |
| Пов'язані критерії | US-16.1 КП-1 (варіативність активностей, щоб не нудьгувати), US-16.6 КП-1 (2–3 різні блоки на вибір), US-6.4 (урок з коротких блоків 5–10 хв — мається на увазі різних), непрямо US-6.7 КП-2 (урок 30/45 хв складається з кількох блоків) |
| Статус | **Open** |

## Кроки відтворення (код-рев'ю з точними числами)

Сценарій — саме той, що `docs/STATUS.md` описує як типовий для **першого** уроку теми:
«урок 30 хв ≈ 3–4 блоки, з яких зазвичай лише 1–2 нові (решта — повтор із бібліотеки)».

1. `getOrGenerateLessonBlocks` (`generate.ts`) тримає в бібліотеці теми **2–3** активних
   блоки (`CANDIDATE_TARGET = 3`, `MIN_CANDIDATES_BEFORE_GENERATING = 2`) — незалежно від
   того, скільки блоків потрібно на урок.
2. `startLessonSession` пропонує дитині вибір з цих 2–3 блоків (US-16.6): припустимо є
   рівно 3 — `[A, B, C]` (порядок — `created_at asc`, завжди той самий на кожен виклик
   `loadCandidates`).
3. Дитина обирає `A` (`chooseStartBlock`) → блок A активний.
4. Блок A завершено → `advanceAfterStep` (`orchestrator.ts`, рядки 290–325):
   ```ts
   const more = await getOrGenerateLessonBlocks(...);     // знову [A, B, C] — той самий список
   const alreadyUsed = new Set([blockRow?.library_item_id].filter(Boolean));  // {A}
   const nextBlockId = more.find((m) => !alreadyUsed.has(m.id))?.id ?? more[0]?.id;  // B
   ```
   — обирається `B`. Поки що правильно.
5. Блок B завершено (урок ще не вичерпав час — типовий 30-хв урок потребує 3–4 блоки, а
   бібліотека має лише 3) → знову `advanceAfterStep`:
   ```ts
   const more = [A, B, C];                                 // той самий список знову
   const alreadyUsed = new Set([B]);                        // враховує ЛИШЕ щойно завершений блок
   const nextBlockId = more.find((m) => !alreadyUsed.has(m.id))?.id ?? more[0]?.id;  // A !!
   ```
   `alreadyUsed` містить **лише блок, що щойно завершився** (`blockRow?.library_item_id`),
   а не всі блоки, вже пройдені в цій сесії (`session_blocks` з `status = 'done'` для
   `session_id`) — тому наступним для дитини знову стає **блок A**, який вона щойно
   пройшла на початку цього самого уроку.

## Очікуваний результат
У межах одного уроку (однієї `lesson_sessions`) дитина не повинна отримати той самий
`library_item_id` двічі — вибір наступного блоку має враховувати **всю історію сесії**
(`session_blocks` зі статусом `done`/`active` для цієї сесії), а не лише щойно завершений
блок.

## Фактичний результат
Для теми з рівно 2–3 збереженими блоками (типова ситуація на початку роботи з темою,
за оцінкою самого `docs/STATUS.md`) третій блок 30-хвилинного уроку з високою ймовірністю
повторює перший блок цього ж уроку слово в слово (той самий текст пояснення, ті самі
питання з еталонними відповідями, яких дитина вже щойно відповіла правильно чи
неправильно) — псує відчуття «справжнього» уроку, суперечить меті E-16 (варіативність,
не нудьгувати) і робить бали за другий прохід того самого блоку по суті «безкоштовними»
(дитина вже знає відповіді).

## Чому Major
- Не стосується безпеки дитини чи витоку даних.
- Але це **не рідкісний крайній випадок** — за власною оцінкою вартості в
  `docs/STATUS.md` це саме типовий сценарій першого проходження теми (2–3 збережені
  блоки, урок потребує 3–4), тобто дефект спрацює в переважній більшості перших уроків
  теми, що прямо суперечить духу US-16.1/US-16.6 і буде помітний Алексу й доньці на
  найпершому ж демо-уроці, що йде довше двох блоків.

## Завдання для `developer`
1. У `advanceAfterStep` заповнювати `alreadyUsed` з **усіх** `session_blocks.library_item_id`
   цієї сесії (простий додатковий запит `select library_item_id from session_blocks where
   session_id = $1`), а не лише з щойно завершеного блоку.
2. Якщо всі наявні кандидати теми вже використані в цій сесії (бібліотека вичерпана,
   а часу ще лишилось) — або згенерувати новий блок понад `CANDIDATE_TARGET` (окремий
   виклик `generateOneBlock` з явним прапорцем «потрібен ще один, усі наявні вже
   використані в сесії»), або свідомо повторити блок **з явним попередженням у UI**
   («Ти вже проходила це раніше, повторимо для закріплення» — це прийнятна, але свідома
   поведінка US-8-подібного повторення, не мовчазний збіг), або завершити урок раніше
   часу замість мовчазного повтору — рішення на розсуд `developer`/PO, головне — не
   мовчазний непозначений повтор.
3. Регресійний тест (db- або integration-рівня): топік з рівно 2 збереженими блоками,
   45-хвилинна сесія, що потребує ≥ 3 блоків → перевірити, що жоден `library_item_id` не
   зустрічається в `session_blocks` цієї сесії двічі **без явної позначки «повторення»**.
