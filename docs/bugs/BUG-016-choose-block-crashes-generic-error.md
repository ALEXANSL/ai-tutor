# BUG-016 — Вибір запропонованого блоку урока показує технічну сторінку Next.js замість уроку

| Поле | Значення |
|---|---|
| Серйозність | **Critical** (блокує старт будь-якого реального уроку) |
| Зріз | S3/S4 (педагогічний конвеєр, `chooseStartBlockAction`/`chooseStartBlock`) |
| Знайдено | Живе демо 2026-09-26: генерація вже працює («З чого почнемо?» показує 2 реальні блоки — «Відсотки: як знайти відсотки від числа», «Детектив знижок…»), але клік на будь-який із них видає загальну сторінку Next.js «This page couldn't load / A server error occurred». |
| Статус | **Fixed** (2026-09-26) |

## Що сталося

1. `startLessonSession` уже відпрацьовує коректно (окрема проблема — див. нижче, «пов'язаний фікс»).
2. `LessonPicker` викликає `chooseStartBlockAction(sessionId, id)`, ловить помилку самого виклику
   (`try { await chooseStartBlockAction(...) } catch { setError(...) }`) — це **вже** було
   захищено. Але після успішного виклику компонент лише робить `router.refresh()`, який
   заново рендерить `/lesson/[sessionId]` (Server Component) — і **цей рендер** ловитись
   клієнтським `try/catch` не може: будь-який виняток тут стає необробленим RSC-винятком,
   і саме тому дитина бачить загальну сторінку Next.js, а не помилку у формі.
3. Код-рев'ю `activateBlock` (`orchestrator.ts`) показав два незахищені записи в БД —
   `insert` у `session_blocks` і `update` `lesson_sessions` — жодна з яких не перевіряла
   `error` з відповіді Supabase. Відхилений запис (наприклад, повторний клік/подвійний
   сабміт, що спричиняє конфлікт унікального індексу `(session_id, sort_order)`) раніше
   **мовчки** ігнорувався: сесія лишалась у стані, де `current_step_id` вказує на крок, для
   якого немає відповідного рядка `session_blocks` — і саме на цю невідповідність далі
   натикався рендер (`getLessonView` не знаходить `session_blocks` за
   `session.current_block_order` → повертає `step: null`, але це саме по собі безпечно;
   реальний ризик — будь-яка МАЙБУТНЯ зміна цієї функції, що покладається на «запис завжди
   вдався», тепер отримає явний виняток одразу, а не тиху розбіжність даних).

## Виправлення

1. **`activateBlock` (`orchestrator.ts`):** обидва записи тепер перевіряють `error` і кидають
   конкретний `Error("activating lesson block failed: …")` замість мовчазного ігнорування.
   Заразом прибрано мертвий тернарник `session.mode === "choosing" ? 1 : 1` (завжди `+1`) —
   поведінка та сама, код чесніший.
2. **`chooseStartBlockAction` (`app/actions/lesson.ts`):** обгорнуто в `try/catch`, як і
   `startLessonAction` — повертає `{status: "error", message: uk.common.error}` замість кидка
   через межу Server Action. `LessonPicker` оновлено під нову форму відповіді.
3. **`app/(child)/lesson/[sessionId]/error.tsx` (новий, головний фікс):** route-segment
   `error.tsx` — Next.js-межа помилки для цього маршруту. Дитина **ніколи** не побачить технічну
   сторінку: замість неї — «Щось пішло не так» + «Спробувати ще раз» (`reset()`) + «← До
   «Сьогодні»». Це працює незалежно від того, **де саме** в рендері `/lesson/[sessionId]`
   стався виняток — сьогоднішній чи будь-який майбутній, поки корінь конкретної причини (якщо
   вона ще лишиться) не знайдено.
4. **Тест:** `orchestrator.test.ts` → `describe("chooseStartBlock (BUG-016…)")` — реалістичний
   багатокроковий блок (slide + choice + open + interactive/drag_sort, кожен із реальними
   `sourceRefs`, на відміну від спрощених фікстур решти файлу) підтверджує, що
   `chooseStartBlock` не кидає для нормального кейсу, і що відхилений запис тепер кидає
   конкретну, перехоплювану помилку замість тихого збою.

## Залишковий ризик

Джерела `error.tsx` не покривають: якщо причина крашу — щось за межами цього route-сегмента
(наприклад, глобальний layout), warning лишається в консолі сервера (`console.error` у
`error.tsx`) для подальшого діагностування за логами Vercel. Ручна перевірка на реальному
демо (клік на кожен із двох запропонованих блоків, підтвердження екрана кроку) — у чеклисті
`docs/STATUS.md`.
