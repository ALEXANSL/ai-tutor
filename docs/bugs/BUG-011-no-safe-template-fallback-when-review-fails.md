# BUG-011 — Немає «безпечного спрощеного шаблону», коли жоден блок теми не пройшов рецензію (US-6.11)

| Поле | Значення |
|---|---|
| Серйозність | **Major** |
| Зріз | S3 (педагогічний конвеєр, D-55/ADR-022) |
| Пов'язані критерії | US-6.11 (Must): «блок, що не пройшов рецензію (і доопрацювання), дитині не показується — **заміняється безпечним спрощеним шаблоном**»; `docs/05-backlog.md` («інакше — безпечний спрощений шаблон») |
| Статус | **Fixed** (2026-09-30, друга хвиля QA) |

## Кроки відтворення (код-рев'ю + новий регресійний тест)

1. `runPedagogicalPipeline` (`app/src/server/lessons/pipeline.ts`) коректно позначає блок
   `needs_review`, якщо жодна з `MAX_REVISIONS + 1` спроб не отримала вердикт `approved` —
   такий блок ніколи не потрапляє в `library_items.status = 'active'`, тож дитина його не
   бачить (це працює правильно, покрито `pipeline.test.ts`).
2. Але `getOrGenerateLessonBlocks` (`app/src/server/lessons/generate.ts`) у цьому випадку
   просто не додає жодного нового кандидата — цикл `while (candidates.length <
   MIN_CANDIDATES_BEFORE_GENERATING)` виходить достроково (`if (candidates.length <= before)
   break`), і функція повертає **порожній масив**, якщо в бібліотеці теми взагалі не було
   активних блоків раніше.
3. `startLessonSession` (`app/src/server/lessons/orchestrator.ts`, рядок 86):
   ```ts
   const candidates = await getOrGenerateLessonBlocks(...);
   if (candidates.length === 0) throw new Error("could not prepare any lesson block for this topic");
   ```
   — кидає звичайний `Error` без коду/тексту для UI.
4. `startLessonAction` (`app/src/app/actions/lesson.ts`) не перехоплює цей виняток і не
   підміняє його безпечним шаблоном — помилка йде як є до клієнта.
5. `StartLessonButton.tsx` ловить будь-яку помилку й показує лише загальне
   `uk.common.error` («Щось пішло не так») — тато натискає «Почати урок» і замість уроку
   (нехай навіть спрощеного) бачить загальну помилку; урок узагалі не створюється
   (`lesson_sessions` не отримує рядка).
6. Новий регресійний тест, доданий цим прогоном:
   `app/src/server/lessons/orchestrator.test.ts` → `describe("startLessonSession — BUG-011 …")`
   — явно документує, що `startLessonSession` кидає генеричну помилку замість fallback-шаблону,
   коли `getOrGenerateLessonBlocks` повертає `[]` (сценарій «жоден блок теми не пройшов
   рецензію», напр. через `AiNotConfiguredError` рецензента, якщо `OPENAI_API_KEY` не задано —
   саме той сценарій, який `docs/STATUS.md` прямо називає ймовірним на першому демо).

## Очікуваний результат (US-6.11)
Якщо жоден блок теми не пройшов рецензію (навіть після доопрацювань), урок усе одно
**запускається** з безпечним спрощеним шаблоном (наприклад, детермінований, заздалегідь
написаний і не згенерований ШІ блок-заглушка на кшталт «повторимо приклад із підручника» —
без переказу підручника «в лоб», але без ризику непроревізованого контенту) — а не відмовою
запустити урок узагалі.

## Фактичний результат
Тато (у S3 — лише режим тата) натискає «Почати урок» → бачить загальну помилку «Щось пішло не
так» → урок не створюється взагалі. Немає жодного шляху отримати «безпечний спрощений шаблон» —
цієї сутності в коді не існує (`grep -rn "simplified\|fallback.*template\|спрощен" app/src/server/lessons/`
— 0 збігів, крім самого тексту вимоги в документах).

## Чому Major, не Critical
- Не стосується безпеки дитини чи витоку даних.
- На реальному демо з коректно виданим `OPENAI_API_KEY` рецензія, найімовірніше, пройде з
  першого-другого разу для більшості блоків — тому цей дефект може не спрацювати на
  найпершому демо Алексу.
- Але це явний **Must**-критерій (US-6.11, буквально прописаний текст «безпечний спрощений
  шаблон» і в `docs/01-requirements.md`, і в `docs/05-backlog.md`), і саме `docs/STATUS.md`
  сам попереджає про реалістичний сценарій (не заданий `OPENAI_API_KEY` → кожен блок падає в
  `needs_review`), у якому цей дефект **гарантовано** спрацює — і тоді жоден урок узагалі не
  запуститься, поки Алекс не задасть ключ, замість деградованого, але робочого уроку.

## Завдання для `developer`
1. Визначити (можна разом з PO/`architect`, якщо потрібне рішення в межах документів) вміст
   «безпечного спрощеного шаблону» — мінімум: 1 блок без ШІ-генерації (статичний слайд +
   1 просте питання за фрагментом підручника, без `drag_sort`/складних компонентів), який
   попередньо схвалений (не потребує рецензії, бо не згенерований) і зберігається як звичайний
   `library_items` з окремим `status` (напр. `"fallback"`) або окремим прапорцем, щоб
   відрізнявся від згенерованих активних блоків в UI тата (методичний паспорт відсутній,
   бібліотека показує «резервний блок»).
2. `getOrGenerateLessonBlocks`/`startLessonSession`: якщо після спроб генерації кандидатів
   усе ще 0 — використати цей резервний блок замість кидання винятку; урок стартує з ним,
   тату — сповіщення в центр сповіщень («Урок запущено зі спрощеним резервним блоком: жоден
   згенерований блок не пройшов рецензію — перевірте налаштування ролі `lesson_review`»).
3. Оновити `pipeline.ts`/`generate.ts` коментарі й `docs/STATUS.md`, щоб точно відображати
   нову поведінку (наразі `docs/STATUS.md` каже «урок при цьому не зламається» — це правда
   лише в тому сенсі, що немає необробленого винятку на клієнті (`StartLessonButton` ловить
   помилку), але урок дійсно **не стартує взагалі**, а не «не зламається» в сенсі «дитина
   отримає урок»).

## Виправлення (2026-09-30)
- `app/src/server/lessons/pipeline.ts`: `AiNotConfiguredError` з `lesson_review` (наприклад,
  `OPENAI_API_KEY` не задано) тепер загорнута в новий `ReviewerUnavailableError` з перекладеною
  причиною («рецензент недоступний: не налаштовано OPENAI_API_KEY»).
- `app/src/server/lessons/generate.ts`: `getOrGenerateLessonBlocks` більше не дає необробленому
  винятку вийти назовні — ловить `ReviewerUnavailableError`, повертає `{ candidates: [],
  failureReasonUk }` замість порожнього масиву без причини. Новий `getOrCreateFallbackBlock` —
  детермінований, без ШІ, блок (дослівний уривок підручника + питання «так/ні» на його основі),
  зберігається як `library_items.status = 'fallback'` (окремий статус, не бере участі в звичайній
  вибірці активних кандидатів, без методичного паспорта, перевикористовується, а не генерується
  щоразу заново).
- `app/src/server/lessons/orchestrator.ts`: `startLessonSession` при порожніх кандидатах створює/
  перевикористовує резервний блок і **стартує сесію з ним**, замість кидати виняток; шле тату подію
  `lesson_started_with_fallback` з точною причиною.
- `app/src/app/actions/lesson.ts`/`StartLessonButton.tsx`: замість кидання винятку клієнту —
  `startLessonAction` повертає `{status: "error", message}` з конкретним поясненням (немає
  проіндексованого підручника / загальна помилка), кабінет тата більше не показує лише «Щось пішло
  не так» для цих випадків.
- Нова міграція `supabase/migrations/20260930110000_bug011_fallback_status.sql`: додає
  `library_items.status = 'fallback'` до перевірки, дозволяє дитині бачити `fallback` через RLS
  (`needs_review` лишається прихованим).
- `app/src/i18n/uk.ts`, `LibraryCardsList.tsx`, `app/parent/notifications/page.tsx`: тексти для
  нового статусу «Резервний блок (без ШІ)» і нового типу сповіщення.
- Тести: `orchestrator.test.ts` (BUG-011 — фолбек стартує урок + подія тату; звичайний шлях без
  фолбека), `pipeline.test.ts` (`ReviewerUnavailableError`).
