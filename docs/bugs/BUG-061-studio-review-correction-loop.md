# BUG-061 — суперечливі рецензії й повторне написання замість доопрацювання

## Докази

Власник надав рецензію уроку за сторінками 70–80: вимога третьої схеми, width/height для порівнянь, перетворення markdown-таблиці на visual, уточнення інтерпретації емоджі. У коді дизайнер мав максимум дві схеми; width/height є фізичними вимірами лише dimensions, для інших типів промпт прямо вимагав null. Автор на revise не отримував попередній урок, дизайнер — попередні схеми. Зауваження були тільки рядками, без адресата/дії/умови приймання.

Це встановлені суперечності контракту та передачі контексту. Приватний production-проєкт і платні генерації не читалися/не запускалися; не стверджуємо, що конкретний урок уже перегенерований або схвалений.

## Зміна

- Спільний для автора/дизайнера/рецензента контракт. Немає обов’язкового мінімуму схем чи педагогічної квоти «1–2». Технічний запобіжник розміру відповіді — 16 схем, не ціль генерації. Предметні знання та вибір доречного подання заохочуються; таблиця є допустимим завершеним поданням. Поточний renderer усе ще підтримує тільки sequence/comparison/timeline/dimensions.
- Нові рецензії обов’язково повертають corrections: role, blockIndex/visualIndex, problem, action, acceptance. По одному завданню на блокувальне зауваження; посилання на наявні елементи перевіряються сервером. Застарілі рецензії без corrections читаються, передаються на доопрацювання за новими правилами.
- Author отримує попередній повний candidate; designer — зміст без приватних ключів квізів і попередні visuals. Правильні частини зберігаються за інструкцією, нова повна відповідь перевіряється чинною схемою. Під час author-stage попередні visuals зберігаються для наступного дизайнера.
- Виключно дизайнерські corrections без додаткових побажань тата запускають design → review; текст не переписується. Інші й старі рецензії — author → design → review.
- Reviewer бачить оновлений candidate, перевіряє старі зауваження за актуальним контрактом; старий verdict не передається як оцінка нового результату. Немає автоматичного схвалення/необмеженого платного циклу.
- Явне позначення навчальних вигаданих прикладів/неоднозначної інтерпретації емоджі. Косметичні побажання не є підставою блокувати коректний урок.
- Parent preview показує конкретний план виправлень з виконавцем, місцем і критерієм перевірки.

Нові default routes design/review мають 5000/6000 output tokens для повніших відповідей. Збережені маршрути/бюджети власника не перезаписуються; попередній резерв і ліміт проєкту діють. Провайдер не змінюється: OpenAI. Gemini/Claude і генерація довільних зображень не підключалися.

## Перевірка та межі

Unit: сценарій третьої схеми, null розміри для comparison, точковий design-only repair зі збереженням тексту, попередній candidate автору, попередні схеми дизайнеру, старі рецензії, відхилення неадресних/неповних corrections і неправильних індексів. Повний набір 2066 tests; додаткова регресія педагогічних правил; typecheck, lint (0 errors / 8 baseline warnings), production build. Browser: справжній StudioPreview, mocked result, 320/390/768/1440 × light/dark, видимі виконавець/дія/критерій без overflow.

Методична самооцінка: конкретний критерій приймання скорочує довільні повтори; markdown-таблиця не гірша за схему сама по собі; незалежна перевірка фактажу збережена. Це кодова й промптова правка, а не гарантія безпомилковості ШІ. Повноцінна творча майстерня з діалоговою історією, довільними типами оформлення та image-generation потребує окремого розширення UI, матеріального контракту, renderer і провайдерів. Не видавати нинішні чотири типи схем за необмежений дизайн.

Уточнення власника: підручник — орієнтир програми, не стеля змісту. Спільний маніфест прямо вимагає викладання теми з причинними зв’язками, сучасними прикладами, предметними знаннями ШІ, практикою, віковою адаптацією та виправленням застарілих тверджень. Рецензент оцінює фактаж і педагогічну якість, не буквальну тотожність сторінкам. Збагачення явно відділене від джерела; вигадані цитати, фальшиві посилання й упевнені недостовірні твердження не дозволені.
