# BUG-045 — покинутий (dangling) виклик `continueAfterBlock`, що все ще генерує блок у фоні, міг «воскресити» сесію, яку дитина вже покинула через «Вийти з уроку»

| Поле | Значення |
|---|---|
| Статус | **Fixed** |
| Серйозність | Major — не той самий клас, що BUG-034 (кнопка виходу тепер завжди клікабельна й коректно працює), але суміжна тиха race condition на сервері, яка може непомітно скасувати вихід дитини з уроку |
| Пов'язано з | `app/src/server/lessons/orchestrator.ts` (`continueAfterBlock`, `activateBlock`), `app/src/app/actions/lesson.ts` (`continueAfterBlockAction`, `pauseLessonAction`) |
| Знайдено під час | повторної перевірки скарги Алекса «Вийти з уроку» на екрані «Блок завершено!» нібито знову не працює (той самий клас, що BUG-034) |

## Контекст розслідування

Алекс повідомив: на «Блок завершено!» під час busy-стану «Готуємо наступний крок…» кнопка «Вийти з уроку» **нічого не робить** — тільки браузерна кнопка «Назад» рятує. Це дослівний опис оригінального BUG-034.

Перевірено код (`LessonRunner.tsx`, `BlockCompleteScreen`, рядки ~1104-1122) і наявний регресійний тест (`LessonRunner.test.tsx`, `describe("BUG-034: ...")`) — фікс BUG-034 **на місці й коректний**:
- кнопка «Вийти з уроку» рендериться БЕЗ `disabled` — не залежить від `busy` жодним чином (на відміну від кнопки «Далі», яка коректно `disabled={busy}`, окремо);
- `onClick={onExit}` викликає той самий `exitLesson` (`pauseLessonAction(sessionId, "manual_exit")` → `router.push("/today")`), що і скрізь в цьому файлі;
- клік не чекає на проміс `continueAfterBlockAction` — той лишається «висіти» (deliberately not awaited);
- unit-тест деферить `continueAfterBlockAction` назавжди (`new Promise(() => {})`), клікає «Вийти з уроку» поки «Далі» ще `disabled`, і підтверджує `pauseLessonAction("s1", "manual_exit")` + `router.push("/today")` — тест **проходить**.

Гіпотеза з завдання («одна спільна `busy`-змінна вимикає обидві кнопки») **спростована**: `busy` вимикає лише кнопку «Далі»; кнопка виходу ніколи не отримує `disabled`. Комміт `2b90e7a` (BUG-034) підтверджено є предком `origin/main` — фікс не «загублений» при мерджі.

Далі, за прямою вказівкою пункту 4 завдання («перевір, чи не «пізній» результат `continueAfterBlockAction`, що прийшов після виходу, тихо не наступає на стан навігації»), перевірено серверний шлях `continueAfterBlock` → `nextSessionBlock` → (якщо холодно) `generateOneBlock` (1-5 хв) → **`activateBlock`**.

## Корінна причина (підтверджено читанням коду)

`continueAfterBlock` (`orchestrator.ts`) завантажує `session` **один раз, на самому початку**:

```ts
export async function continueAfterBlock(familyId: string, sessionId: string): Promise<AnswerResult["next"]> {
  const session = await loadSession(familyId, sessionId);
  ...
  const next = await nextSessionBlock(...); // може тривати 1-5 хв (planning→generating→reviewing→revising)
  ...
  const nextItem = await activateBlock(familyId, session, next.id); // <-- використовує СТАРИЙ `session`
  return { kind: "advance", step: stepView(nextItem, nextItem.steps[0]!, 1) };
}
```

`activateBlock` **безумовно** пише в `lesson_sessions`:

```ts
await scope.update("lesson_sessions", {
  mode: "lesson",
  status: "active",           // <-- завжди "active", незалежно від поточного реального статусу
  current_block_order: nextOrder,
  current_step_id: item.steps[0]!.id,
}).eq("id", session.id);
```

Якщо дитина натискає «Вийти з уроку» **поки** `nextSessionBlock` усе ще генерує блок (саме той 1-5-хвилинний busy-стан з BUG-034), окремий, паралельний виклик `pauseLessonAction` → `pauseLessonSession` успішно записує `status: "paused", pause_reason: "manual_exit"` — і клієнт коректно переходить на `/today` (BUG-034 працює як задокументовано).

Але сам виклик `continueAfterBlockAction`, запущений раніше, **ніхто не скасовує** — фетч не абортується (це клієнтська client-side навігація, не повне перезавантаження сторінки), і сервер продовжує виконувати вже запущений `continueAfterBlock` до кінця. Коли він нарешті завершується (за кілька хвилин, коли дитина вже давно на `/today`), `activateBlock` тихо **перезаписує** щойно виставлену паузу назад на `status: "active"` з новим `current_step_id`/`current_block_order` — сесія «воскресає» сама по собі, без відома дитини чи тата. Наступного разу, коли хтось відкриє цей предмет, стан бекенду не відповідатиме тому, що дитина насправді зробила (вийшла з уроку) — тихе, важко відтворюване неузгодження стану, а не видима поломка кнопки.

**Це не той самий корінь, що BUG-034** (кнопка виходу сама по собі непошкоджена й ніколи не була недоступна в поточному коді) — це суміжна, окрема race condition у покинутому фоновому промісі, саме того класу, що прямо попереджувався в коментарі до фіксу BUG-034 («проміс, що вирішиться пізніше, вже нікого не цікавить» — виявилось, що це вірно тільки для КЛІЄНТА; сервер продовжував писати).

## Найімовірніше пояснення скарги Алекса

Схоже на службовий службовий воркер (PWA, `app/src/app/sw.ts`, `serwist`) з `skipWaiting`/`clientsClaim` і `NetworkOnly` для навігацій — старий JS-бандл малоймовірний як причина за такої конфігурації. Правдоподібніше: Алекс міг спостерігати саме цей ефект опосередковано (сесія, яку він вважав закритою, за кілька хвилин "ожила" знову як активна) або дійсно зіткнувся з BUG-034 до того, як фікс дійшов до продакшна — це варто уточнити в нього окремо (див. «Питання Алексу» нижче). У будь-якому разі знайдена і виправлена race condition — реальний, підтверджений тестом баг, незалежно від того, чи це саме те, що він бачив.

## Виправлення

`continueAfterBlock` тепер **перечитує** свіжий стан сесії безпосередньо перед `activateBlock` (після потенційно багатохвилинного `nextSessionBlock`) і, якщо сесія вже не `status: "active"` (тобто її призупинили/з неї вийшли, поки блок генерувався), **не пише нічого** в `lesson_sessions`/`session_blocks` — повертає безпечний no-op (`{ kind: "advance", step: null }`, який клієнт, якщо він взагалі ще змонтований, трактує як «нічого не робити», без падіння). Згенерований блок при цьому **не витрачається намарно** — він уже збережений у бібліотеці (`library_items`) і буде запропонований пізніше звичайним шляхом `nextSessionBlock`.

Залишкове вікно гонки (між повторним читанням і записом) звужено з 1-5 хвилин до мілісекунд — той самий патерн read-then-write, що вже використовується в інших місцях цього файлу (`recordChildFeedback`, `tickLessonActivity`); повна атомарність вимагала б транзакції/RPC на рівні БД, що лишається за межами цього фіксу як непропорційно велика робота для звуженого до мілісекунд вікна.

## Тести

`app/src/server/lessons/orchestrator.test.ts`, новий `describe("continueAfterBlock — BUG-045 ...")`:
1. звичайний шлях (сесія все ще `active`, коли генерація завершується) — блок активується як і раніше;
2. `nextSessionBlock`'s мок імітує реальну гонку: **під час** його виконання сесія переходить у `paused`/`manual_exit` (так, як це зробив би паралельний `pauseLessonAction`) — підтверджено: жодного запису `status: "active"` в `lesson_sessions` після цього, пауза лишається на місці, повертається безпечний no-op.

`npm run typecheck`, `npm test` (852 passed, включно з наявним BUG-034 тестом), `npm run build` — усі пройшли.

## Питання Алексу

Щоб підтвердити/спростувати, чи саме BUG-045 (а не досі-недеплойнутий BUG-034) є тим, що він бачив: чи це сталось на щойно оновленому preview/production, чи вкладка/PWA була відкрита довго до цього (можливо, ще з до-BUG-034 деплою)? Якщо повториться після цього фіксу — важливо якомога точніше зняти скріншот консолі браузера (Network-таб, чи справді пішов запит при кліку «Вийти з уроку»).
