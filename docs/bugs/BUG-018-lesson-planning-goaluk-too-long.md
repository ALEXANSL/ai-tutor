# BUG-018 — `startLessonAction` падає: `goalUk` довший за 200 символів валить усю генерацію уроку

| Поле | Значення |
|---|---|
| Серйозність | **Major** (перший урок теми може не згенеруватись узагалі) |
| Зріз | S3/S4 (ADR-022 крок 1, роль `lesson_planning`, `planSchema` у `src/server/lessons/schema.ts`) |
| Знайдено | Продакшн-логи Vercel: `startLessonAction failed: anthropic call failed: Failed to parse structured output ... goalUk: Too big: expected string to have <=200 characters` |
| Статус | **Fixed** (2026-09-26) |

## Що сталося

`prompts/lesson_planning.md` просив модель написати `goalUk` — «мету блоку одним реченням».
Схема (`planSchema`) обмежувала це поле `z.string().min(1).max(200)`. Anthropic SDK валідує
відповідь моделі проти цієї Zod-схеми ще ДО того, як код проєкту її побачить
(`zodOutputFormat(schema)` у `src/server/ai/providers/anthropic.ts`) — якщо модель написала
змістовно правильне, але задовге речення (реальне українське речення з підрядним реченням
регулярно виходить за 200 символів), SDK кидає помилку валідації, вона долітає до
`runStructured`'s generic catch (`anthropic call failed: ${e.message}`), і — оскільки другого
провайдера для `lesson_planning` немає/фолбек теж може повторити ту саму помилку — уся
генерація першого блоку теми падає з технічною помилкою замість того, щоб дитина побачила
урок.

Це суто **косметичне** обмеження (довжина рядка), а не проблема змісту — воно не мало права
валити весь педагогічний конвеєр.

## Виправлення

Комбінація (a) + (b) з опису бага:

1. **Схема (`schema.ts`):** ліміт `goalUk` піднято з 200 до **400** символів — достатній запас
   для трохи задовгого, але змістовно правильного речення, і водночас все ще відхиляє справді
   роздутий текст (цілий абзац/кілька речень).
2. **Промпт (`prompts/lesson_planning.md`):** явно додано жорсткий бюджет символів і приклад
   доречної довжини:
   > «мету блоку **одним коротким реченням, не довше ~150 символів**... Приклад доречної
   > довжини: «Дитина навчиться порівнювати звичайні дроби з однаковим знаменником.»
   Це саме по собі має різко зменшити частоту випадків, коли межа 400 узагалі спрацьовує —
   решта відхилень (< 400) лишає модель у межах реалістичної одноречникової мети без обрізання
   чи повторного запиту, що ускладнило б конвеєр заради суто форматної дрібниці.

Варіант (в) — автоматичне обрізання/повторний запит — свідомо не робили: `zodOutputFormat`
передає JSON-схему моделі напряму через Anthropic API (структуровані виведення), тож
Zod-препроцесинг/`transform` для «тихого» обрізання рядка до валідації ризикує зламати саму
конвертацію схеми в JSON Schema, яку бачить модель (складніший і крихкіший шлях, ніж просте
підняття ліміту — а результат для дитини той самий: жоден змістовно правильний `goalUk`
більше не валить генерацію).

## Тести (`src/server/lessons/schema.test.ts`)

- `goalUk` рівно **201 символ** (найкоротший рядок, що падав під старим лімітом `<=200`) —
  тепер `planSchema.safeParse(...).success === true`.
- Явно роздутий `goalUk` (~900 символів, імітація цілого абзацу) все ще відхиляється —
  верхня межа не знята повністю.
- Порожній `goalUk` все ще відхиляється (`min(1)` не займали).
