# BUG-032 — Натискання на теми без готового уроку показує загальну помилку «перевірте налаштування ШІ»

| Поле | Значення |
|---|---|
| Статус | **Fixed** (2026-09-27) |
| Серйозність | **Critical** — блокує проходження уроку для тем, які ще не прогріті/згенеровані |
| Зріз | S27 (фоновий прогрів, ADR-023) — можливо регресія від щойно змерженої фічі, потребує перевірки |
| Пов'язано з | `startLessonAction` (`app/src/app/actions/lesson.ts`), `getOrGenerateLessonBlocks`/`ensureActiveLibraryBlock` (`generate.ts`/`warmup.ts`) |

## Контекст (зі слів Алекса)
«те про що ми говорили, складання плану та генерація уроків — хоч вибрати все, хоч одна тема, у нас зараз декілька уроків згенеровані, натискання на інші просить перевірити налаштування ШІ, тобто урок не згенеровано або не генерується». Скріншот показує екран батьківського кабінету «Математика» → «Поточна тема» (одиничний автокомпліт + «Зберегти поточну тему», успішно — «Збережено. Прогноз-план оновлено.») зі списком тем підручника.

## Аналіз коду (зроблено оркестратором перед делегуванням, НЕ підтверджено на живих логах)
`startLessonAction` (`app/src/app/actions/lesson.ts:69-89`) ловить БУДЬ-ЯКУ помилку з `startLessonSession` і, якщо це не конкретно рядок `"no indexed textbook fragments"`, показує загальний `uk.parent.subjects.errors.startLessonFailed` — «Не вдалося підготувати урок. Спробуйте ще раз за кілька хвилин або перевірте налаштування ШІ.» Це загальний catch-all, який ховає РЕАЛЬНУ причину помилки від і батька, і від нас (видно лише `console.error` в серверних логах Vercel, не в браузері).

Прочитав `getOrGenerateLessonBlocks`/`startLessonSession` (щойно оновлені для ADR-023, S27) — сам код виглядає коректно спроєктованим для випадку «немає готових блоків»: (а) якщо прогрів ще не завершився — повертає `warmJobId`, і сесія коректно переходить у режим `"warming"` (не помилка); (б) якщо денний бюджет прогріву вичерпано — повертає `failureReasonUk` (теж не помилка, просто інформативний текст); (в) якщо `ensureActiveLibraryBlock` кидає РЕАЛЬНИЙ виняток (напр. помилка виклику ШІ-провайдера, неправильно налаштований `model_routes`, вичерпаний місячний бюджет — `hard_stop`, чи щось інше) — ось це і потрапляє в generic catch і показується як розпливчасте «перевірте налаштування ШІ».

**Висновок:** сам текст помилки, який побачив Алекс, — це саме той самий generic fallback, тобто десь дійсно стається СПРАВЖНЯ помилка при спробі згенерувати/прогріти блок для конкретної теми, і ми не знаємо точної причини без реальних серверних логів.

## Гіпотези (не підтверджено, потребують логів)
1. Реальна помилка виклику ШІ-провайдера для цієї конкретної теми (напр. немає проіндексованого фрагмента підручника саме для цієї теми, і повідомлення про це не збігається рядок-в-рядок з очікуваним `"no indexed textbook fragments"`, тому потрапляє в generic гілку замість специфічної).
2. Проблема з новою конфігурацією `model_routes` (щойно доданою для `passive_narration`/`step_reinforcement`, S5/S27) — можлива помилка сидіння ролей для цієї конкретної сім'ї.
3. Бюджетний стан `hard_stop`/помилка API-ключа — щось, що справді потребує уваги Алекса, і повідомлення в принципі не помилкове по суті, лише занадто розпливчасте.
4. Регресія від паралельної одночасної роботи кількох розробників сьогодні над `orchestrator.ts`/`generate.ts` (навігація назад, оцінювач BUG-030) — можливий побічний ефект об'єднання змін.

## Завдання для developer
1. **Терміново:** покращити `console.error` в `startLessonAction`, щоб реальна причина (повне повідомлення помилки, не лише generic текст користувачу) точно потрапляла в Vercel Runtime Logs — якщо там уже є достатньо деталей, попросити в Алекса свіжий експорт логів саме з моменту цього кліку для остаточної діагностики.
2. Відтворити на реальному прикладі: узяти тему з підручника, яка НЕ прогріта/не має активних блоків, і викликати `startLessonAction` — подивитись, яка САМЕ помилка кидається (не здогадуватись).
3. Виправити корінну причину (не просто показати кращий текст користувачу) — якщо причина №1 (неспівпадіння тексту помилки "no indexed textbook fragments"), розширити перевірку; якщо причина №2/३ — виправити конфігурацію чи обробку; якщо причина №4 — виправити регресію.
4. Незалежно від кореневої причини: розглянути, чи `startLessonFailed`-повідомлення варто зробити конкретнішим (напр. розрізняти "ще прогрівається, зачекайте" від "реальна технічна помилка, зверніться до розробника" від "бюджет вичерпано") — за патерном BUG-005 (конкретне повідомлення замість загального).

## Рішення PO
Терміново — блокує реальне використання застосунку прямо зараз для тем, які ще не встигли прогрітись/згенеруватись.

## Фікс (2026-09-27)
Алекс надав свіжий експорт логів Vercel — точна причина знайшлась одразу, без гіпотез:
```
startLessonAction failed: enqueueing library.warm_topic failed: new row for relation "jobs" violates
check constraint "jobs_max_attempts_check"
```
`app/src/server/lessons/warmup.ts` вставляв `max_attempts: 30` при створенні job'и прогріву, а таблиця `jobs` (S1, `20260926100000_s1_ai_router_costs_jobs.sql:286`) має `check (max_attempts between 1 and 20)`. Кожна спроба поставити тему в чергу прогріву падала на рівні БД ще ДО того, як щось реально викликало ШІ-провайдера — тому жодна не прогріта тема ніколи не могла навіть почати генеруватись, і generic catch у `startLessonAction` показував розпливчасте «перевірте налаштування ШІ» для КОЖНОЇ такої теми.

**Фікс:** `max_attempts: 30` → `max_attempts: 20` (максимально допустиме значення за схемою; і так значно більше за дефолтні 5). Жодної міграції БД не потрібно — обмеження вже існувало правильно, помилка була лише в коді застосунку.

Прогнано: `NODE_USE_ENV_PROXY=1 npx vitest run src/server/lessons/warmup.test.ts` (6/6 ✅), `tsc --noEmit` (чисто). Жодного нового тесту не додано — існуючі тести не перевіряли конкретне числове значення `max_attempts`, і сама межа вже задокументована в схемі БД; регресію такого класу (значення поза CHECK-обмеженням) варто ловити системно, а не точковим тестом — див. BUG-028 (пропозиція покрити нові/існуючі констрейнти `tests/db/*`).
