# BUG-007 — Відповідь, дана під час обриву мережі, не буферизується й не надсилається автоматично

| Поле | Значення |
|---|---|
| Серйозність | **Major** |
| Зріз | S3 |
| Пов'язані критерії | US-6.5 КП-2 («відповідь, дана під час обриву мережі, буферизується на пристрої й надсилається автоматично після відновлення зв'язку»); NFR-RES-1 («Прогрес зберігається після кожного кроку; відповідь, дана під час обриву, буферизується на пристрої й доставляється після відновлення мережі»); DoD п.1 (стійкість — «обрив інтернету посеред уроку» — сценарій, який QA зобов'язана перевіряти для кожного зрізу) |
| Статус | **Open** |

## Кроки відтворення (код-рев'ю)

1. `LessonRunner.submit()` (`app/src/components/lesson/LessonRunner.tsx`, рядки 112–127) викликає
   `submitStepAnswerAction` (Server Action, тобто звичайний мережевий запит) напряму:
   ```ts
   try {
     const result = await submitStepAnswerAction(sessionId, step.stepId, idempotencyKey, { channel, answer, latencyMs });
     …
   } catch {
     router.refresh();   // <-- єдина реакція на будь-яку помилку, зокрема offline
   }
   ```
2. Немає жодного клієнтського сховища черги невідправлених відповідей: перевірено
   (`grep -rn "indexedDB|localStorage|sessionStorage|background.?sync|offline.*queue" src/components/lesson/ src/server/lessons/`)
   — жодного збігу.
3. Service worker (`app/src/sw.ts`) кешує лише статичні файли (`CacheFirst` для
   `/_next/static/`, `/icons/`); для решти запитів — `NetworkOnly()`, без `Background Sync`
   API чи будь-якого механізму відкладеної повторної відправки POST-запитів.
4. Отже: якщо мережа зникає **точно в момент**, коли дитина натискає «Перевірити»/«Далі»
   (а не раніше — раніший обрив ловиться подією `offline` й лише ставить урок на паузу,
   що працює коректно), запит `submitStepAnswerAction` впаде з мережевою помилкою,
   `catch` виконає `router.refresh()`, і відповідь дитини **ніде не збережена** —
   ні на сервері (запит не дійшов), ні на пристрої (немає черги).

## Очікуваний результат (за US-6.5 КП-2, NFR-RES-1)
- Відповідь, дана під час обриву мережі, зберігається на пристрої (IndexedDB/localStorage
  чи Background Sync) і **автоматично** надсилається, щойно мережа відновилася — без дії
  дитини, без повторного набору відповіді.
- `idempotencyKey`, який уже генерується клієнтом (`crypto.randomUUID()`), — правильна
  основа для цього: серверна частина (унікальний індекс на `step_attempts.idempotency_key`,
  перевірено `s3-lessons.test.ts`) уже готова приймати безпечний повтор; бракує лише
  клієнтської черги, яка цей ключ використовує для відкладеної відправки.

## Фактичний результат
- Відповідь під час фактичного обриву (а не лише «додаток був закритий/вимкнений
  планшет», що коректно покривається «Продовжити з кроку N» після перезавантаження
  сторінки) губиться; дитина після відновлення зв'язку бачить `router.refresh()` →
  переможе консистентний стан (крок N без збереженої відповіді), але сама відповідь,
  яку вона щойно дала, зникла і повинна бути введена знову.
- Для `open`-кроку текст відповіді залишається в полі `openAnswer` (локальний React-стан),
  тож у **цьому конкретному випадку** дитина може натиснути кнопку ще раз вручну — але це
  не «автоматично надсилається після відновлення зв'язку» (КП-2 вимагає саме
  автоматичності), і для `choice`/`interactive`-кроків навіть цього немає: після помилки
  вибір/розкладка карток не зберігається в стані компонента для повторної спроби одним
  дотиком.

## Чому Major, не Critical
- Не стосується безпеки дитини чи витоку даних.
- Не ламає застосунок — після відновлення зв'язку дитина може повторити дію вручну (з
  можливим повторним читанням завдання).
- Але прямо порушує явний критерій прийняття Must-історії (US-6.5 КП-2) і однойменну
  NFR (NFR-RES-1), і це саме той клас сценарію стійкості («обрив інтернету посеред
  уроку»), який `qa-tester` зобов'язана перевіряти для кожного зрізу — гірше за втрачений
  крок це виглядає для дитини як «я щось зробила, а воно не зарахувалось», що суперечить
  духу «нічого не втрачено» з US-14.6.

## Завдання для `developer`
1. У `LessonRunner.submit()`: перед мережевим викликом зберігати намір відповіді
   (`{ sessionId, stepId, idempotencyKey, channel, answer, latencyMs }`) у стійке клієнтське
   сховище (IndexedDB просто через невеликий helper, або `Cache Storage`/Background Sync,
   якщо `developer` хоче richer offline-підтримку); прибирати запис лише після
   підтвердженого успіху сервера.
2. При відновленні мережі (подія `online`, або на монтуванні компонента) — перевірити
   чергу й автоматично повторно відправити будь-які незавершені записи, у порядку їх
   створення, використовуючи вже наявний `idempotencyKey` (безпечно за конструкцією —
   `step_attempts.idempotency_key` унікальний).
3. Для `choice`/`interactive`-кроків — зберігати вибір дитини в React-стані компонента
   (а не лише в намірі до відправки), щоб після невдалої спроби дитина бачила свій вибір
   і могла або дочекатися авто-відправки, або натиснути «Спробувати ще раз» без
   повторного проходження кроку заново.
4. Юніт/компонентний тест на чергу (замокати `fetch`/Server Action, що кидає помилку,
   потім дозволити успіх і перевірити один виклик з тим самим `idempotencyKey`) —
   `qa-tester` розширить існуючий `s3-lessons.test.ts`/новий компонентний тест після
   фіксу.

## Тести
Наразі не автоматизовано (вимагає клієнтської черги, якої не існує) — задокументовано
код-рев'ю вище (`grep` для офлайн-черги — 0 збігів, рев'ю `sw.ts` — `NetworkOnly`).
