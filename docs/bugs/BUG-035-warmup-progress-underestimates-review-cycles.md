# BUG-035 — Прогрес-екран прогріву уроку обіцяє «~1 хвилину», але нормальний цикл перевірки якості може тривати 3+ хвилини й виглядає як «зациклення»

| Поле | Значення |
|---|---|
| Статус | **Open** |
| Серйозність | Major (UX) — не ламає функціонал, але виглядає як баг і демотивує/лякає дитину/батька |
| Пов'язано з | `app/src/components/lesson/LibraryWarmProgress.tsx`, `app/src/server/lessons/pipeline.ts` (`MAX_REVISIONS`), `app/src/server/lessons/warmup.ts` |

## Слова Алекса (дослівно)
> 3 хв вже і перескакує на перевірку якості і так по кругу вже 4 рази чи 3, трохи незрозуміла логіка

## Розслідування (диференціація від BUG-034)
Спочатку підозрював баг у механізмі повторних спроб job-черги (`runner.ts`/`warmup.ts`): що генерація падає з помилкою, і система тихо перезапускає весь конвеєр з нуля (до 20 спроб), а це і виглядає як «перескакування по колу». Попросив Алекса виконати SQL-запит проти `public.jobs`. Результат для щойно відпрацьованої задачі (`type='library.warm_topic'`):

```
status=done, attempts=1, last_error=null
```

**Жодного retry не було** — конвеєр відпрацював з першої спроби. Це спростовує гіпотезу про приховану помилку/retry-цикл.

Реальна причина: `runPedagogicalPipeline` (`pipeline.ts`) має власний, коректно обмежений внутрішній цикл ревізій — `MAX_REVISIONS = 2`, тобто до **3 повних проходів** «generating → reviewing» (перший прохід + до 2 ревізій), кожен з яких викликає реального AI-провайдера (генерація + окрема рецензія іншим провайдером, ADR-022). Кожен такий прохід репортує стадії через `onStage`: «Пишемо урок» (generating) → «Перевіряємо якість» (reviewing) → якщо рецензент попросив доопрацювання — «Допрацьовуємо» (revising) → знову «Перевіряємо якість» — і так до 3 разів, перш ніж або затвердити урок, або зберегти як `needs_review`.

Тобто **3-4 «проходи» по стадіях «Перевіряємо якість»/«Допрацьовуємо» — це очікувана, штатна поведінка конвеєра якості (ADR-022)**, а не зациклення. Проблема суто в UX-комунікації:
1. Текст «~1 хвилину» в `LibraryWarmProgress.tsx` — надто оптимістична оцінка, яка не враховує сценарій із кількома реальними AI-викликами (планування + до 3× (генерація + рецензія)) — це легко може зайняти 2-5 хвилин залежно від провайдера.
2. Дитина/батько бачить, як екран «повертається» на «Перевіряємо якість» кілька разів підряд, і сприймає це як зациклення/поломку, бо ніщо на екрані не пояснює, що це нормальний, обмежений процес перевірки якості (наприклад, лічильник «Перевірка 2 з 3»).

## Завдання для developer
1. У `LibraryWarmProgress.tsx` прибрати фіксовану обіцянку «~1 хвилину»; замінити на реалістичніший діапазон (наприклад, «зазвичай 1-3 хвилини, іноді довше») або взагалі прибрати конкретну оцінку часу, залишивши лише стадії.
2. Якщо `onStage`/job payload вже має доступ до номера поточної ревізії (чи легко його туди додати з `pipeline.ts`), показати лічильник проходу («Перевірка 1 з 3») замість голого повторення однакового напису — це прямо пояснює дитині/батьку, що це не зациклення, а покроковий процес з обмеженою кількістю кроків.
3. Якщо очікування триває довше, скажімо, 90 секунд — показати додаткове заспокійливе повідомлення («Ще трохи — перевіряємо, щоб урок був якісним»), без зміни самої логіки конвеєра.
4. Не займатись перебудовою логіки ревізій (`MAX_REVISIONS`) — вона вже коректно обмежена й перевірена раніше; це суто завдання на текст/індикацію прогресу.
5. Прогнати `npm run typecheck`, `npm test`, `npm run build` перед комітом.

## Примітка
Окремо: `runner.ts`'s retryable-failure path (рядки ~87-99) досі не робить `console.error` при кожній повторній спробі job — лише пише в `jobs.last_error`. Хоча в ЦЬОМУ конкретному випадку retry не траплявся, цей пробіл лишається реальним систематичним недоліком спостережуваності (майбутній retry-баг буде так само невидимий у Vercel-логах). Варто додати `console.error` і на retryable-гілку (не тільки на `onGiveUp`) — окремим дрібним фіксом, за нагоди, не обов'язково в цій ітерації.
