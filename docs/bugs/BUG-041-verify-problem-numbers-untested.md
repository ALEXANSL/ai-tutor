# BUG-041 — `verifyProblemNumbers` (захист від вигаданих номерів задач у кроках уроку) не покритий жодним реальним тестом

| Поле | Значення |
|---|---|
| Статус | **Fixed** — `verifyProblemNumbers` експортовано з `pipeline.ts` і покрито прямими юніт-тестами в `pipeline.test.ts` (варіант (а) із завдання): fake `scope.select().in().returns()` повертає реальний `material_problems`-рядок, і тест перевіряє (1) незбіжний `problemNumber` обнуляється, (2) точно збіжний (`material_id`+`page`+`number`) — зберігається, (3) степ без жодного `problemNumber` узагалі не звертається до БД (`fakeScope`, як і раніше). Стара фікстура `fakeScope`/`baseInput` не чіпалась. `npm run typecheck`, `npm test`, `npm run build` — усі проходять. |
| Серйозність | **Major (цілісність тестування безпеко-критичної функції)** |
| Пов'язано з | `app/src/server/lessons/pipeline.ts` (`verifyProblemNumbers`), `app/src/server/lessons/pipeline.test.ts` |

## Опис
`verifyProblemNumbers` (`pipeline.ts:177`, викликається до `reviewDraft`, `pipeline.ts:336`) — це основний захист від того, щоб крок уроку показав дитині вигаданий номер вправи: звіряє кожен `sourceRefs[].problemNumber`, який ЗІР згенерувала модель, проти реальних рядків `material_problems` (точний збіг `material_id+page+number`), і мовчки обнуляє невідповідні. За інспекцією коду логіка виглядає правильною.

Але **жодного реального тесту на цю логіку немає**. Єдина пов'язана зміна в `pipeline.test.ts` — `fakeScope`, чий `select()` навмисно **кидає помилку**, якщо його взагалі викликають, із коментарем «кожна фікстура нижче лишає sourceRefs без problemNumber, тож цей fake ніколи не має відповідати на реальний запит». Тобто жодна фікстура ніколи не встановлює `problemNumber`, і гілка «звірка з БД + обнулення» функції `verifyProblemNumbers` **ніколи не виконується жодним тестом у наборі**. Функція також не експортована для прямого юніт-тестування.

Це саме та функція, яку було explicитно доручено прискіпливо перевірити (анти-галюцинаційний захист), і зараз вона працює лише «за інспекцією коду», без жодного автоматичного доказу.

## Завдання для developer
Або (а) експортувати `verifyProblemNumbers` і написати прямий юніт-тест: підготувати крок із `sourceRefs[].problemNumber`, що НЕ відповідає жодному рядку `material_problems` → перевірити, що поле обнулюється; і окремий кейс, де відповідність Є → перевірити, що поле зберігається. Або (б) розширити існуючу інтеграційну фікстуру в `pipeline.test.ts` так, щоб реальний `material_problems`-подібний набір даних (через `fakeScope`) дійсно проходив крізь цю гілку в обох напрямках (збіг/незбіг), а не обходив її навмисним кидання помилки.

Прогнати `npm run typecheck`, `npm test`, `npm run build` перед комітом.
