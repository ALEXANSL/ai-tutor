# BUG-046 — окремі українські літери (і, ї) розпізнаються як `³`/`¿` у частині PDF-підручників (CP1251-байт-у-Latin1 mojibake, шрифтовий дефект, D-110-scope)

- **Серйозність:** Major (видима, непрофесійна помилка у тексті уроку — але вузько-текстова: решта абзацу читається правильно), не блокер
- **Пов'язана story / ADR:** ADR-008 (PDF-екстракція, `unpdf`/pdf.js), D-110 (`docs/01-requirements.md` 12.29 — якість розпізнавання друкованого PDF, уже визнана PO проблема, ADR-031 як обхідний шлях через ручний DOCX-імпорт)
- **Файли:** `app/src/server/ingest/extract-pdf.ts`, `app/src/server/ingest/text.ts` (`normalizeText`) — **прочитано, конкретної причини в НАШОМУ коді не знайдено**
- **Джерело:** скриншот PO з живого уроку, книга «Зарубіжна література» (`6-klas-zarlit-kovbasenko-2023.pdf` — файл не знайдено у репозиторії/фікстурах для прямої перевірки), розділ «Запрошення до літературної мандрівки», стор. 4 (за футером)

## Факт зі скриншота

Заголовок відображається як:
> «Запрошення до л³тературно¿ мандр³вки»

замість правильного:
> «Запрошення до літературної мандрівки»

Конкретні заміни:
- `і` (U+0456) → `³` (U+00B3, «верхній індекс 3»), двічі: «л**³**тературно¿», «мандр**³**вки»
- `ї` (U+0457) → `¿` (U+00BF, «перевернутий знак питання»), один раз: «літературно**¿**»

Це НЕ вже виправлений баг обрізання (truncation, `truncateAtSentenceBoundary`, commit 97cc8bb) — рядок повний, не обірваний. Решта абзацу (за словами PO) читається нормально — отже це не загальний збій екстракції (як у фіксі CMap, commit 241a763, де сторінки взагалі не давали тексту), а точкова, послідовна підміна конкретних символів.

## Аналіз коду (що перевірено й виключено)

Прочитано `extract-pdf.ts` і `text.ts` повністю:
- `extractPdf` викликає `unpdf`'s `extractText(pdf, { mergePages: false })` і одразу передає результат у `normalizeText` — жодної посимвольної підміни між ними немає.
- `normalizeText` (text.ts:25-39) робить лише: видалення `\u0000`, видалення м'якого дефісу (U+00AD), нормалізацію переносів рядків, злиття слів, розбитих дефісом на кінці рядка, і стиснення пробілів. Жоден з цих кроків не зачіпає `і`/`ї`, `³`/`¿`, і жоден regex у файлі не використовує unicode-діапазони, що могли б випадково зачепити ці символи (перевірено весь `.replace`/regex-ланцюжок рядок за рядком).

**Висновок: підміна відбувається ДО того, як текст потрапляє в наш код — усередині самого виклику `unpdf`'s `extractText`, тобто на рівні pdf.js-парсингу гліфів шрифту цього конкретного PDF.** Це не наша регресія і не наш баг нормалізації.

## Гіпотеза причини (підтверджена аналізом кодових точок, не самим файлом)

Перевірено обчислювально (`python3 -c "bytes([0xb3]).decode('cp1251')"` та `0xbf`):

| Байт (CP1251) | Символ CP1251 | Unicode CP1251 | Той самий байт, прочитаний як Latin-1/WinAnsi |
|---|---|---|---|
| `0xB3` | `і` | U+0456 | U+00B3 = **`³`** |
| `0xBF` | `ї` | U+0457 | U+00BF = **`¿`** |

Це **точний, класичний патерн mojibake**: символ, закодований одним байтом у кодовій сторінці Windows-1251 (де українські `і`/`ї` сидять саме на байтах `0xB3`/`0xBF`), інтерпретується так, ніби цей байт — це напряму код Latin-1/WinAnsi-символу з тим самим числовим значенням. Збіг з обома спостереженими символами (не одним) робить випадковість малоймовірною — це системна помилка мапінгу, не шум.

Найімовірніший механізм на рівні PDF/pdf.js: вбудований шрифт цього PDF (можливо, лише шрифт заголовків — тіло абзацу читається правильно, отже це не той самий шрифт, що й основний текст) використовує власну (`/Differences`) таблицю кодування, де гліфи `і`/`ї` мають коди символів `0xB3`/`0xBF` (типово для кириличних PDF, зроблених з розрахунком на CP1251), АЛЕ або (a) `ToUnicode` CMap цього шрифту не містить записів саме для цих двох кодів (пропуск при генерації PDF видавництвом), або (b) сам `ToUnicode` помилково відображає ці коди на Latin-1-еквіваленти замість кирилиці — і pdf.js/`unpdf` у відсутності коректного запису повертає сирий код символу як code point, що для однобайтових кодів `0xB3`/`0xBF` збігається з Latin-1.

**Це дефект самого вихідного PDF-файлу (конкретного шрифту заголовків видавництва), не нашого пайплайна.**

## Що НЕ зроблено (свідомо)

Не впроваджено «репаро-мапу» (`³→і`, `¿→ї`) у `normalizeText` чи деінде. Причина: `³` (верхній індекс 3) — легітимний символ у математичних/фізичних/хімічних підручниках (см³, м³, degrees Celsius formulas тощо) — ті самі `normalizeText`/`extract-pdf.ts` обробляють ВСІ предмети, не лише літературу. Сліпа заміна `³→і` в усьому пайплайні зламала б легітимні кубічні одиниці в математиці/фізиці — це саме той необґрунтований «guess-fix», якого варто уникати. `¿` (перевернутий знак питання) практично ніколи легітимно не з'являється в українському тексті, тому теоретично безпечніший для заміни, але сама по собі часткова заміна одного з двох симптомів того самого дефекту не вирішує кореневу причину і не покриє інші літери, які той самий шрифт може так само калічити (не перевірено — маємо докази лише для і/ї з одного скриншота).

Не вдалося отримати реальний файл `6-klas-zarlit-kovbasenko-2023.pdf` для прямого аналізу таблиці шрифтів (pdffonts-подібний огляд) — у репозиторії немає PDF-фікстур цієї книги, і немає доступу до Google Drive/сховища тата в рамках цієї сесії.

## Впевненість і рекомендація

**Впевненість: середньо-висока** в тому, що це шрифтовий/кодовий дефект конкретного PDF (не наш код) — підтверджено точним числовим збігом CP1251↔Latin-1 для ОБОХ спостережених символів. **Низька** впевненість щодо точного механізму всередині pdf.js (потрібен реальний файл для pdffonts/`getMeta`+font dump перевірки) і щодо того, чи це обмежено лише `і`/`ї`, чи ширший клас символів у цьому шрифті.

Це той самий клас проблеми, що й D-110 (якість розпізнавання друкованого PDF) — PO вже свідомо визнав це відомою, більшою за один точковий фікс прогалиною і затвердив ADR-031 (ручний DOCX-імпорт) як обхідний шлях для матеріалів, де якість критична, замість нескінченного патчення власного PDF-парсера під кожне видавництво.

**Рекомендований наступний крок (не для негайної реалізації без окремого рішення PO/architect):**
1. Якщо і коли зʼявиться реальний файл цієї книги (чи інший приклад того самого патерну) — дослідити таблицю шрифтів сторінки 4 (`pdffonts`/pdf.js font dump) для підтвердження гіпотези.
2. Якщо підтвердиться і патерн виявиться поширеним (не одна книга) — розглянути вузько-scoped пост-екстракційний ремонт, що діє **лише коли одразу за символом стоїть кирилична літера в тому самому слові** (напр. regex на кшталт «кирилична літера + `³`/`¿` + кирилична літера» — різко звужує ризик зачепити легітимні `см³`, де сусід — латиниця/цифра/пробіл), з юніт-тестами на обидва випадки (зберегти легітимний `³`, полагодити кирилично-контекстний).
3. Якщо ні — залишити як відомий D-110-scope дефект якості конкретних видавництв, з рекомендацією тату для чутливих матеріалів (як «Зарубіжна література») розглянути ручний DOCX-імпорт (US-2.10, уже затверджений).

Код-фіксу в цьому баг-репорті НЕ впроваджено — ризик занадто широкий для точкового рішення без реального файлу для перевірки.
