# BUG-019 — Правильні відповіді дитини оцінюються як «Майже»

| Поле | Значення |
|---|---|
| Статус | **Fixed** (2026-09-26) |
| Серйозність | **Critical** — блокує проходження уроку навіть при правильних відповідях |
| Зріз | S3 (педагогічний конвеєр / оцінювання відповідей) |
| Пов'язано з | `submitStepAnswer` / `evaluateAnswer` в `app/src/server/lessons/orchestrator.ts`, `LessonRunner.tsx` |

## Кроки відтворення
1. Відкрити урок (після фіксу BUG-017/018 урок тепер відкривається).
2. Дати відповідь на крок, яка об'єктивно правильна.
3. Система відповідає «Майже» (verdict `partial`/`almost`) замість «Правильно».

## Очікувано
Правильна відповідь (за змістом, з урахуванням допустимих варіацій формулювання/запису) має оцінюватись як `correct`, а не `partial`.

## Фактично
Алекс підтвердив: навіть очевидно правильні відповіді дитини система систематично не зараховує, пише «Майже» тощо.

## Гіпотези для розробника (потребують перевірки, не підтверджені)
- Регресія від BUG-013: фікс форсував `verdict = "partial"` для termінового safety-шляху — перевірити, чи це правило випадково не спрацьовує/не залишилось на звичайному (не safety) шляху оцінювання.
- Порівняння відповіді занадто строге (точний рядковий збіг замість семантичної/математичної еквівалентності): зайві пробіли, різний запис дробу («1/2» vs «0,5»), регістр, розділові знаки.
- Схема відповіді (`evaluate` в описі кроку) чи промпт для LLM-оцінювача повертає занижену впевненість/невірний поріг correct/partial.

## Завдання для developer (терміново — блокер основного функціоналу)
1. Відтворити на реальному прикладі (взяти конкретний крок і правильну відповідь, які Алекс використовував).
2. Знайти корінну причину (не просто підняти поріг) — окремо перевірити звичайний шлях оцінювання і safety-override з BUG-013, щоб не зламати той фікс.
3. Додати автотест, що фіксує регресію: конкретна правильна відповідь на реальний тип кроку (drag_sort/number_line/step_reveal/відкрита відповідь) має повертати `correct`.
4. Незалежна QA-перевірка перед мержем — це safety-суміжна логіка (оцінювання впливає на те, чи дитина рухається далі), тому не покладатись лише на звіт розробника.

## Рішення PO
Найвищий пріоритет зараз — це основний функціонал уроку, дитина не може нормально проходити урок.

## Фікс (2026-09-26)
Було **дві незалежні корінні причини**, не одна:

1. **`drag_sort` (і будь-який `interactive` крок) — регресія в клієнті, не в `evaluateAnswer`.**
   `LessonRunner.tsx`'s `onInteractiveSubmit` надсилав на сервер
   `{ component, answer, correct }`, а `evaluateAnswer` для типу `"interactive"`
   очікує саму відповідь (`def.evaluate(props, answer)`) без обгортки — тож
   сервер завжди оцінював "не той" об'єкт і повертав `incorrect` незалежно від
   того, що дитина насправді розставила. У парі з окремою вадою фронтенду
   (нижче) це виглядало як «Майже» на правильну відповідь. **Фікс:** клієнт
   тепер надсилає саму відповідь без обгортки; серверна логіка оцінювання
   `drag_sort` не змінювалась (вона й була правильною).
2. **Відкриті (текстові) відповіді — оцінювач був занадто шаблонним.**
   За реальними прикладами Алекса: відповідь "просто цифрою" ("2") чи у
   форматі переліку ("а) ... б) ... в) ...") ШІ-оцінювач не зараховував,
   бо порівнював зі "зразком" відповіді буквально, а не по суті — хоча
   реальний вчитель приймає будь-яку форму запису правильного результату.
   **Фікс:** (а) новий детермінований попередній етап у `evaluateAnswer`
   (`matchesExpectedBySubstance`) — якщо відповідь дитини (після очищення
   від пунктуації/регістру/форматування) збігається зі зразком або
   міститься в ньому як цілий фрагмент, одразу `correct`, без звернення до
   моделі; (б) значно переписаний системний промпт оцінювача
   (`OPEN_ANSWER_EVALUATION_SYSTEM_UK`), який прямо каже: «Еталон» — це
   орієнтир, не шаблон для копіювання; оцінюй суть і правильність
   результату, а не форму запису; ніколи не знижуй вердикт лише за формат.
3. **Додатково (косметично, але вводило в оману):** `LessonRunner.tsx`
   показував той самий текст «Майже! Спробуй ще раз» і для `partial`, і
   для `incorrect` — тепер вони розрізняються (`t.almost` / `t.incorrect`),
   щоб справжня помилка не виглядала як «майже вірно».

**BUG-013 (safety-override) не зачеплено:** він і раніше спрацьовував лише
на шляху `open`-відповіді, коли `moderateMessage` повертає
`severity: "urgent"` — цей код не змінювався; новий детермінований
substance-check рахується РАНІШЕ виклику LLM-оцінювача, але не раніше й не
замість перевірки модерації (та однаково виконується паралельно, як і
раніше) — тест `"an 'urgent' open answer ALWAYS gets the deterministic
go-to-dad reply"` (та сусідній тест на нормальний випадок) пройшли без змін.

**Автотести** (`app/src/server/lessons/orchestrator.test.ts`, описи
`submitStepAnswer — BUG-019 (...)`): коректні `choice`, `drag_sort`
(«сира» відповідь, без обгортки), відкрита відповідь-цифра, відкрита
відповідь-перелік а)/б)/в) — усі очікують `correct`; окремий тест, що
справді неправильна відповідь і далі йде через LLM-оцінювач без
перекручення його вердикту.

**Відомий, свідомо залишений поза обсягом gap (D-74, US-6.15, майбутній
зріз):** після дійсно неправильної відповіді система й зараз (як і до
фіксу) показує лише коротке пояснення (`explanation`, з `describe()`/
`explanationUk`/`explanationUk` LLM-оцінювача) і "Спробуй ще раз" — без
повноцінного циклу «пояснити помилку → дати ще одне закріплювальне
завдання на той самий навик → тоді рухатись далі». Це не було звужено чи
зламано цим фіксом (шлях фідбеку — `result.explanation`, тепер з окремим
заголовком для `incorrect` — лишився чи став чіткішим), лише не
реалізовувалось: це предмет окремого зрізу (US-6.15).
