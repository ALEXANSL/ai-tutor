# BUG-012 — Офлайн-черга відповіді записується ПІСЛЯ мережевого виклику (не до нього), як задокументовано

| Поле | Значення |
|---|---|
| Серйозність | **Minor** |
| Зріз | S3 (BUG-007 fix) |
| Пов'язані критерії | US-6.5 КП-2, NFR-RES-1 (те саме, що BUG-007); документація фіксу BUG-007 (`docs/bugs/BUG-007-…md`, `docs/STATUS.md`) |
| Статус | **Open** |

## Кроки відтворення (код-рев'ю)

1. `docs/bugs/BUG-007-no-offline-answer-buffering.md` (статус «Fixed») і `docs/STATUS.md`
   обидва прямо стверджують: «`LessonRunner.submit()` ставить намір відповіді в чергу з тим
   самим `idempotencyKey` **до** мережевого виклику, забирає його лише після підтвердженого
   успіху».
2. Фактичний код (`app/src/components/lesson/LessonRunner.tsx`, `submit()`):
   ```ts
   async function submit(channel, answer) {
     ...
     const idempotencyKey = crypto.randomUUID();
     try {
       const result = await submitStepAnswerAction(sessionId, step.stepId, idempotencyKey, { channel, answer, latencyMs });
       setQueuedAnswer(null);
       applyAnswerResult(result);
     } catch {
       await enqueueAnswer({ idempotencyKey, sessionId, stepId: step.stepId, channel, answer, latencyMs, queuedAt: Date.now() });
     } finally {
       setBusy(false);
     }
   }
   ```
   — `enqueueAnswer` викликається **лише в `catch`**, тобто **після** того, як мережевий
   виклик уже стартував і встиг провалитися, а не до нього.

## Очікуваний результат
Або (а) поведінка відповідає опису у `docs/bugs/BUG-007-…md`/`docs/STATUS.md` (запис у чергу
до мережевого виклику), або (б) документи виправлені так, щоб точно описувати код.

## Фактичний результат і чому це має значення (не лише розбіжність документації)
Поточний порядок («мережа → catch → чергa») працює для типового сценарію (мережа зникає, і
`fetch`/Server Action одразу відхиляється помилкою) — саме це й перевіряє
`offlineQueue.test.ts`. Але є вузьке вікно, яке архітектура «чергa спершу» з документів якраз
і закривала б, а поточний код — ні: якщо дитина натискає «Перевірити» саме в момент обриву
мережі, а `await submitStepAnswerAction(...)` **зависає** (мережевий запит ще не встиг
відхилитися — типово для мобільного з'єднання, що деградує, а не миттєво зникає) і дитина/
планшет у цей момент закриває вкладку, переходить на іншу сторінку чи вимикається (посадка на
таксі й закритий екран, наприклад) — `catch` ніколи не виконається, `enqueueAnswer` не
викликається, і відповідь губиться так само, як до фіксу BUG-007, лише для вужчого підмножини
випадків.

## Чому Minor, не Major
- Вимагає збігу двох умов одночасно (мережа деградує повільно, а не миттєво відхиляє запит,
  **і** сторінка закривається/вивантажується саме в цьому вікні) — рідше за основний сценарій
  BUG-007, який уже виправлено для найпоширенішого випадку.
- Не стосується безпеки дитини чи приватності.
- Легко виправляється в межах наявної інфраструктури (черга вже існує) без нової архітектури.

## Завдання для `developer`
1. У `submit()` викликати `enqueueAnswer(...)` **до** `await submitStepAnswerAction(...)`
   (як і задокументовано), і лише `dequeueAnswer(idempotencyKey)` — після підтвердженого
   успіху (аналогічно тому, як уже влаштований `flushQueue`). Це закриває вікно «сторінка
   закрита під час зависання запиту» так само, як `visibilitychange`/`beforeunload` не
   встигне спрацювати, а дані вже будуть у IndexedDB.
2. Оновити `pipeline`/коментарі й переконатися, що `offlineQueue.test.ts`/новий тест
   компонента покриває саме порядок «enqueue перед мережею, dequeue після успіху» (наразі
   тести перевіряють лише саму чергу, не інтеграцію з `LessonRunner.submit()`).

## Тести
Не автоматизовано на рівні компонента (вимагає симуляції зависання мережевого запиту та
вивантаження сторінки під час нього — складно детерміновано відтворити без реального
браузера); задокументовано код-рев'ю вище. `offlineQueue.test.ts` продовжує коректно
покривати саму логіку черги (порядок, ідемпотентність, зупинка на першій невдачі) — це не
під сумнівом, під сумнівом лише момент виклику `enqueueAnswer` у `LessonRunner`.
