# Аудит D-112: чи справді система зайве повторно індексує/розпізнає — і чому вчорашній урок «завис»

**Дата:** 2026-09-28. **Автор:** `architect` (за прямим дорученням PO, `docs/01-requirements.md` 12.31).
**Метод:** повне читання коду реального ланцюжка викликів ШІ-провайдера (не архітектурних документів) — `app/src/server/ingest/pipeline.ts`, `app/src/server/lessons/pipeline.ts`, `app/src/server/lessons/warmup.ts`, `app/src/server/lessons/generate.ts`, `app/src/server/lessons/orchestrator.ts`, `app/src/app/actions/{subjects,books,lesson}.ts`, `app/src/server/jobs/{runner,kick}.ts`, `app/src/app/api/jobs/tick/route.ts`, `app/vercel.json`, міграції `supabase/migrations/20260926100000_s1_ai_router_costs_jobs.sql` (партиційний унікальний індекс) і `docs/adr/015-background-jobs-pg-cron.md`.

## Висновок одним реченням

**Підозра PO на «зайву повторну індексацію/розпізнавання» — НЕ підтверджена: дублікатів платних викликів немає ніде в коді.** Реальна причина вчорашнього «зависання» — інша, справжня і конкретна вада: **дві з трьох точок опитування прогресу прогріву («LibraryWarmProgress» на дитячому боці і бейджі статусу на панелі масової підготовки тата) ніколи не «підштовхують» чергу задач (`kickJobs()`), хоча сама архітектура (ADR-015) прямо документує це як обов'язковий запасний механізм замість `pg_cron`, якого в проді насправді НЕМАЄ** (не знайдено жодного `cron.schedule`/`pg_net`-виклику в жодній міграції — лише коментар-намір у коді). Це знайдена, конкретна, малою правкою виправна вада — не редизайн.

## 1. `runStructure` (індексація книги) — один раз, підтверджено

`app/src/server/ingest/pipeline.ts`:
- `runExtract` (рядки 364–438) явно перевіряє `skipReextraction(hash, m.content_hash, chunkCount)` (рядки 360–362, з регресійним коментарем «QA regression») — той самий незмінний файл повторно НЕ проходить `sourceExtractors`/`callVisionStructured` (OCR), одразу передається в `ingest.embed`.
- `runStructure` (рядки 605–802) — єдиний виклик `callStructured("indexing_structure", …)` (рядок 656) за весь конвеєр одного матеріалу; викликається лише job'ом `ingest.structure`, який `ingest.embed` ставить у чергу рівно один раз після завершення ембедингів (рядок 567) або `requestReindex`/«Переіндексувати» (рядок 206–217, ручна дія тата) чи зміна `content_hash` (новий файл на тому самому Drive ID — `runExtract` тоді просто не збігається з `skipReextraction` і йде по звичайному шляху, теж один раз).
- **Немає жодного авто-ретригера**: ні ретрай джоба (`runner.ts` ретраїть лише сам job type, що впав, не ставить новий `ingest.structure`), ні промах кешу, ні пере-виведений список тем ніде не викликає `runStructure` вдруге для того самого `content_hash`.

**Висновок п.1: підтверджено — книга індексується (структура) рівно один раз, як і задокументовано в ADR-008/022/023.**

## 2. `runPedagogicalPipeline` — обмежений цикл підтверджено без регресії, і він одноразовий на блок

`app/src/server/lessons/pipeline.ts`, рядки 305–367:
- Цикл `for (let iteration = 1; iteration <= MAX_REVISIONS + 1; iteration++)` з `MAX_REVISIONS = 2` — **максимум 3 проходи generate+review**, `break` одразу на `verdict === "approved"`, інакше `break` після `iteration > MAX_REVISIONS` зі статусом `needs_review`. Точна відповідність `MAX_REVIEW_PASSES = MAX_REVISIONS + 1 = 3`, яку дитячий екран показує як «Перевірка X з 3» (BUG-035) — **без регресії, межа коректно застосована**.
- Це відбувається РІВНО ОДИН РАЗ на один блок бібліотеки (`generateOneBlock`, `generate.ts` рядки 222–324) — результат одразу зберігається в `library_items`/`library_steps` (рядки 274–297). Кожен наступний запит на цю тему читає збережений блок через `loadCandidates`/`loadLibraryItem`, **жодна дія (відкриття уроку дитиною, повторний job, `nextSessionBlock`) не перезапускає pipeline для вже активного блоку** — `getOrGenerateLessonBlocks` (generate.ts рядки 372–415) повертає наявні `candidates` без виклику ШІ, якщо `loadCandidates` не порожній (рядок 382–384).

**Висновок п.2: підтверджено — обмежений цикл ревізій працює правильно (без регресії BUG-035), і результат генерується та кешується рівно один раз на блок.**

## 3. Три тригери D-103 + новий D-108 bulk-тригер — дедуплікація підтверджена коректною для точного інтерлівінгу з учора

Усі чотири шляхи (`warmAheadForSubject` з `runStructure`, `warmAheadForSubject` з `setCurrentTopicAction`, `warmAheadForSubject`/пряма warm-ahead з `startLessonSession`, і `confirmBulkWarmupAction`) **проходять через ЄДИНУ функцію** `ensureActiveLibraryBlock` (`warmup.ts` рядки 101–209), і — критично — **використовують той самий ключ дедуплікації** `warmDedupeKey(topicId) = "library.warm:" + topicId` (рядок 29–31), незалежно від `source: "auto" | "manual_bulk"`. Це перевірено прямим пошуком у коді: `LIBRARY_WARM_JOB_TYPE`-задача вставляється **рівно в одному місці** в усьому коді (`warmup.ts` рядки 173–189) — жодного альтернативного шляху вставки з іншим ключем немає.

Дедуплікація на трьох рівнях, кожен незалежно перевірений:
1. **Логічна перевірка перед вставкою** (рядки 135–148): якщо задача з тим самим `dedupe_key` вже `queued`/`running` — повертає її `id`, нічого не вставляє.
2. **Партиційний унікальний індекс у БД** (`20260926100000_s1_ai_router_costs_jobs.sql`, рядки 297–298: `unique index … on jobs (family_id, dedupe_key) where dedupe_key is not null and status in ('queued','running')`) — гарантія на рівні схеми навіть при гонці двох одночасних запитів; код ловить `23505` і перечитує вже існуючу задачу (рядки 191–203) замість падіння чи дубля.
3. **Друга перевірка всередині самого job-хендлера, прямо перед витратою грошей** (рядки 462–464): `const already = await loadCandidates(...); if (already.length > 0) return;` — навіть якби дві задачі якимось чином обидві дійшли до виконання, друга не викликає pipeline вдруге.

**Сценарій учора (дитина відкрила тему → `startLessonSession` warm-ahead; тато паралельно запустив bulk-warmup, можливо на ту саму тему) відтворено крок за кроком:** обидва шляхи звертаються до `ensureActiveLibraryBlock` з ОДНАКОВИМ `dedupeKey`. Хто б не прийшов першим — вставляє задачу; другий (навіть у справжній одночасній гонці, яку ловить унікальний індекс) приєднується до тієї самої задачі й повертає той самий `jobId`. `session.warm_job_id` (яким дитячий екран прогресу опитує статус, `orchestrator.ts` рядок 244–250) і `getTopicWarmupStatuses` (яким панель тата читає бейджі, `warmup.ts` рядки 326–369) **обидва читають з того самого рядка `jobs` за тим самим `dedupe_key`** — розбіжності «дитина чекає джоб A, а бейдж тата показує джоб B» для тієї самої теми **структурно неможливо**, доки жодне нове місце вставки не з'явиться з іншим ключем.

**Висновок п.3: дедуплікація підтверджена коректною саме для цього інтерлівінгу — нуль дублікатів витрат, і job-mismatch неможливий за конструкцією.**

## 4. Справжня причина «зависання» — знайдено, конкретно, з високою впевненістю

Це не гонка чи дублікат — це **відсутність «підштовхування» черги задач там, де воно документовано як обов'язкове**.

### Факт 1: `pg_cron` щохвилини НЕ налаштований у проді
`docs/adr/015-background-jobs-pg-cron.md` (§Примітка, рядки 27–34) прямо визнає: `pg_cron`/`pg_net` необов'язкові, бо задачі рухаються трьома способами — (1) `after()` одразу в тому самому запиті, (2) **«поки відкрито сторінку з активною задачею… клієнт опитує сервер і кожен виклик підштовхує чергу (`kickJobs()`)»**, (3) щоденний Vercel Cron (Hobby) як підстраховка. Пошук по всьому репозиторію (`grep -r "cron.schedule\|pg_net\|jobs/tick" supabase/`) **не знайшов жодної міграції, що реально створює `pg_cron`-розклад** — це лишається коментарем-наміром, не реалізованим кроком. `vercel.json` (рядки 7–12) містить лише ОДИН запис: `"/api/jobs/tick?sync=1"` раз на добу о 3:47 (UTC).

**Отже, спосіб (2) — клієнтське опитування, що підштовхує чергу — це, по факту, ЄДИНИЙ спосіб, який реально рухає фонові задачі протягом дня**, крім одноразового `kickJobs()` у момент, коли дію ініціює сам тато/дитина.

### Факт 2: спосіб (2) реалізовано правильно в одному місці й **пропущено в двох нових**

`app/src/app/actions/books.ts`, рядок 75 — `pollIndexingAction` (опитується екраном «Мої книги» під час індексації):
```
if (books.some((b) => b.status === "queued" || b.status === "indexing")) kickJobs();
```
Це саме той патерн, що ADR-015 документує як «безпечний запасний механізм».

Але:
- `app/src/app/actions/lesson.ts`, `checkWarmupProgressAction` (рядки 343–356) — опитується компонентом `LibraryWarmProgress.tsx` кожні 3–8 секунд, поки дитина чекає на прогрів теми (саме та «зависла тема» з учора) — **не імпортує й не викликає `kickJobs()` жодного разу**.
- `app/src/app/actions/subjects.ts`, `getBulkWarmupStatusAction` (рядки 330–335) — опитується `BulkWarmupPanel.tsx` для оновлення бейджів статусу масової підготовки — **теж не викликає `kickJobs()`**, і файл узагалі не імпортує `kickJobs` (перевірено — `import { ensureActiveLibraryBlock, estimateBulkWarmup, getTopicWarmupStatuses, … } from "@/server/lessons/warmup"`, без `kickJobs`).

Додатково: обидва тригери D-103 (`warmAheadForSubject` з індексації й з `setCurrentTopicAction`) і новий тригер D-108 (`confirmBulkWarmupAction`) **навмисно** викликають `ensureActiveLibraryBlock` з `{ immediate: false }` (обґрунтування в коментарях: «може почекати кілька секунд, не блокуюче») — тобто вставляють задачу(і) в чергу, **не підштовхуючи чергу одразу**. Це свідоме рішення само по собі не є вадою — воно **покладається саме на спосіб (2)** як на підстраховку. Але спосіб (2) не працює для двох саме тих екранів, де дитина/тато фактично чекають і дивляться на прогрес.

### Як це склалося у вчорашній вечір (найімовірніша реконструкція, за фактами коду)

1. Тато вже кілька днів індексує підручники й активує предмети/теми (сам каже: «для десятка предметів»). Кожна така дія (`runStructure` після індексації, `setCurrentTopicAction`) ставить у чергу `library.warm_topic`-задачі для кількох тем наперед (`LIBRARY_WARM_LOOKAHEAD_TOPICS`, за замовчуванням 3) — **з `immediate: false`, тобто без підштовхування черги**.
2. Без реального `pg_cron` ці задачі рухаються лише тоді, коли щось ІНШЕ (завантаження книги, «Перевірити папку», чи «холодний старт» дитини десь-інде) випадково викликає `kickJobs()` і чергу глобально обробляє `claim_jobs()`.
3. `claim_jobs()` (міграція `20260926100000…`, рядки 304–322) — це **чиста FIFO-черга за `run_after`, без урахування типу задачі, сім'ї чи пріоритету** («дитина зараз дивиться на екран» проти «фонова підготовка на ніч» не розрізняються нічим). Якщо за день накопичився «хвіст» неопрацьованих `library.warm_topic`-задач з давнішим `run_after` — будь-який наступний `kickJobs()` спершу обробляє їх по черзі, перш ніж дійде до щойно підштовхнутої задачі дитини.
4. Дитина відкриває «завислу» тему → `startLessonSession` → тема «холодна» → `ensureActiveLibraryBlock({ immediate: true })` або оновлює `run_after` наявної задачі на «зараз», або вставляє нову, і викликає `kickJobs()` **рівно один раз**, у тому самому запиті (обмежений `budgetMs: 240_000`, сторінка має `maxDuration = 300` — цього достатньо на папері). Але якщо на цей момент у черзі вже є «хвіст» старіших задач (п.3) або сам конвеєр цього блоку не вкладається в один прохід `runJobs()` (наприклад, збігається з іншою одночасною фоновою роботою), задача дитини може НЕ встигнути завершитись за цей один `kickJobs()`.
5. Дитина лишається на екрані `LibraryWarmProgress`, який опитує `checkWarmupProgressAction` кожні 3–8 с — **і жоден з цих опитів більше НІКОЛИ не підштовхує чергу** (Факт 2). Якщо той єдиний перший `kickJobs()` не довів задачу до кінця — вона просто лежить `queued`/`running`, а `resolveWarmupProgress` (orchestrator.ts, рядки 229–279) чесно показує `ready: false` знову і знову, бо задача **не «зависла» технічно** (не `failed`, не `done`) — вона просто ніким не оброблюється далі.
6. Тато, бачачи, що дитячий урок не формується, відкриває панель масової підготовки й запускає `confirmBulkWarmupAction` — **яка теж вставляє задачі з `immediate: false`**, і статус-бейджі, які він дивиться (`getBulkWarmupStatusAction`), **теж ніколи не підштовхують чергу**. Тому й з боку тата видимого прогресу могло не бути — не тому, що щось «перепитує повторно», а тому, що **черга просто стоїть**, поки якась третя, непов'язана дія (наприклад, наступний день о 3:47 ранку) її не розблокує.

### Ранжування гіпотез за впевненістю

1. **(Найвища впевненість, підтверджено читанням коду напряму)** Відсутність `kickJobs()` у `checkWarmupProgressAction` і `getBulkWarmupStatusAction` — при реально відсутньому `pg_cron` — це і є причина, чому обидва екрани («зависла» дитяча тема і статус bulk-панелі тата) могли не показувати прогресу, попри те що задачі коректно стоять у черзі (не втрачені, не задубльовані).
2. **(Середня впевненість, правдоподібний підсилювальний фактор)** Накопичений «хвіст» неопрацьованих `immediate:false`-задач від попередніх днів індексації/активації предметів («для десятка предметів») у чистій FIFO-черзі без пріоритету міг забрати весь бюджет того єдиного `kickJobs()`, який дитячий холодний старт таки викликав, не давши йому дійти до задачі саме цієї теми за один прохід.
3. **(Нижча впевненість, не виключено, але не знайдено прямого підтвердження в коді)** Платформний тайм-аут середини виконання (Vercel) якщо job впав по `locked_until` до завершення — сам механізм ретраю (`runner.ts`) це коректно підхоплює при НАСТУПНОМУ виклику `runJobs()`, тож це підсилює (1)/(2), а не є окремою причиною.

## 5. Кошторис для реалістичного сценарію: 20 тем, масова підготовка на ніч

- Кожна тема, що справді потребує підготовки (`needsPrep: true` в `estimateBulkWarmup`), запускає **рівно один** `library.warm_topic`-job → **рівно один** прохід `runPedagogicalPipeline`: 1 виклик `lesson_planning` + від 1 до 3 пар `lesson_generation`+`lesson_review` (залежно від вердикту рецензента) = **від 3 до 7 реальних платних викликів ШІ-провайдера на тему**.
- Для 20 тем: **від 60 до 140 викликів провайдера сумарно**, орієнтовний кошторис — рівно той, що бачить тато на екрані підтвердження: `20 × $0.33 ≈ $6.60` (`WARM_TOPIC_COST_USD`, фіксована оцінка на тему, а не за фактичну кількість проходів).
- **Немає жодного шляху, яким та сама тема була б оброблена двічі**: дедуплікація підтверджена на трьох незалежних рівнях (розділ 3 вище) — логічна перевірка, унікальний індекс БД, і повторна перевірка «вже активно?» прямо перед витратою грошей усередині самого job-хендлера. Навіть якщо тато випадково вибере в bulk-панелі тему, яку дитина вже «розігріла» хвилину тому, `estimateBulkWarmup`/`getTopicWarmupStatuses` покажуть її як `needsPrep: false` (уже `ready`/`queued`/`generating`) і **не порахують і не поставлять їй ще одну задачу**.

## Що виправити (для `developer`, точний опис — без редизайну)

**Дефект:** два опитувальні server actions не підштовхують чергу фонових задач, порушуючи задокументований в ADR-015 запасний механізм (спосіб 2) — критично важливо саме тому, що `pg_cron` у проді фактично не налаштований.

1. `app/src/app/actions/lesson.ts`, `checkWarmupProgressAction` — додати `kickJobs()` (той самий імпорт, що вже є в `books.ts`: `import { kickJobs } from "@/server/jobs/kick"`) щоразу, коли `progress.ready === false` — так само, як `pollIndexingAction` робить це для `status === "queued" || status === "indexing"`.
2. `app/src/app/actions/subjects.ts`, `getBulkWarmupStatusAction` — додати той самий імпорт і викликати `kickJobs()`, якщо серед `statuses` є хоч один `"queued"` чи `"generating"`.
3. **Окреме питання для PO, не для цього фіксу:** чи варто нарешті увімкнути `pg_cron` щохвилини в Supabase (сам ADR-015 називає це «бажаним покращенням», не критичним) — це прибрало б залежність від того, чи хтось тримає відповідну сторінку відкритою, і дало б чергі рухатись навіть тоді, коли ні дитина, ні тато нічого не дивляться. Це вимагає доступу Алекса до Supabase SQL editor (окремий крок, не код) — залишаю на його рішення, не роблю сам.
