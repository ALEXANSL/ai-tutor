# ADR-028. Ремедіаційний діалог у кроці уроку та в розборі домашніх завдань: зупинити крок → пояснити конкретну помилку → закріпити → повернутись на точку зупинки

- **Статус:** прийнято (рішення PO D-104, 2026-09-27; закриває ВП-35…ВП-38, самі відповіді на ці питання зафіксовані `product-manager`, `docs/01-requirements.md` §12.23 — тут лише технічна реалізація закритих рішень, ВП-35…ВП-38 повторно не переглядаються)
- **Вимоги:** D-74, D-77, D-104, US-6.15 (E-6), US-8.7 (E-8), NFR-SAFE-4 (BUG-013), NFR-COST-4; пов'язані ADR-007 (оркестратор/стейт-машина), ADR-009 (модерація), ADR-014 (бібліотека уроків), ADR-020 (інтерактивні компоненти, доповнено — див. той файл), ADR-022 (педагогічний конвеєр), ADR-023 (фонове прогрівання і два бюджети швидкості — цей ADR реалізує вже заскафолджену там роль `step_reinforcement`)

## Контекст

PO повторно й з наголосом (D-104, 12.23) зафіксував, що сьогодні в застосунку є лише одноразова кнопка «Пояснити» (US-6.9 КП-1 — альтернативне пояснення поточного кроку, без діалогу) і окремий предметно-темовий чат (`server/lessons/chat.ts`, US-8.1/8.2) — жодного зв'язаного циклу «дитина помилилась → ШІ зупиняє крок, пояснює конкретно ЦЮ помилку, дає завдання на закріплення → дитина повертається саме на той крок, де зупинилась» ще не реалізовано, хоча модель поведінки вже детально описана в US-6.15 (D-74) і US-8.7 (D-73) і чотири відкриті питання, що блокували точну реалізацію (ВП-35…ВП-38), тепер закриті:

- **ВП-35 → 1 цикл** «поясни → закріпи» перед м'яким fallback (узгоджено з D-96: 2 невдалі спроби поспіль на кроці — перша веде в цикл, друга — fallback).
- **ВП-36 → комбінація:** для `choice`/`open` — невеликий кешований пул (2–3 варіанти) на навик, збережений у самому кроці бібліотеки, без нового виклику ШІ під час уроку; для інтерактивних компонентів (ADR-020) — детермінована зміна `props`, теж без ШІ.
- **ВП-37 → розширення наявного формату кроку** новими необов'язковими полями (`remediation.explanation`, `remediation.retry_step`), а не новий тип кроку — точну схему фіксує цей ADR.
- **ВП-38 → окреме число спроб для US-8.7**, +1 проти US-6.15 (2 спроби після пояснення методу в розборі ДЗ проти 1 циклу+fallback у кроці уроку) — та сама модель, ті самі параметри виклику, лише інший лічильник.

Дві принципово різні точки застосування однієї педагогічної моделі («пояснити → дати спробувати → перевірити → скоригувати → лише потім розв'язок», P-H) вимагають РІЗНОЇ технічної реалізації, бо в них різний носій стану:

- **US-6.15** живе всередині вже наявної стейт-машини уроку (`lesson_sessions`/`step_attempts`, ADR-007) — має «зупинити крок», не ламаючи `current_step_id`/`step_attempts`/паузу/відновлення/safety-override, які вже там є.
- **US-8.7** живе в per-темовому чаті (`chats`/`messages`, поза `lesson_sessions` взагалі) — там немає «кроку» й «спроби» як окремих рядків БД, лише послідовність повідомлень.

Обидві мають бути **швидким, живим шаром** (D-77/D-78, ADR-023 Частина 2) — жодного синхронного `lesson_planning→lesson_generation→lesson_review`; ADR-023 вже заздалегідь створив (S27, `20261002110000_s27_library_warmup.sql`) роль `model_routes.step_reinforcement` (Claude Sonnet 5, ескалація на Opus 5.5) саме як «скафолдинг» для цього моменту — цей ADR її нарешті підключає, і **тим самим маршрутом** для обох US (спільна модель — ВП-38 (б) явно вимагає «той самий базовий параметр моделі»).

## Рішення

### 1. Дані: розширення `library_steps` (не нова таблиця, не новий тип кроку — ВП-37)

`library_steps.content`/`library_steps.visual` — уже `jsonb`, міграція схеми не потрібна, лише нові узгоджені необов'язкові ключі, що генеруються й рецензуються **разом із рештою кроку** в наявному конвеєрі (ADR-022, розд. 3.2а/3.2а тут не подорожчує окремо — маргінальний приріст токенів на блок, розд. «Вплив на вартість» нижче):

**`choice`-крок** (`content`):
```jsonc
{
  "questionUk": "...", "options": [
    { "id": "a", "textUk": "...", "misconceptionUk": "чому САМЕ цей неправильний варіант хибний — конкретна причина (US-6.15 КП-1), не загальна фраза" },
    { "id": "b", "textUk": "...", "correctOptionId": true }
  ],
  "remediation": {
    "retryVariants": [
      { "questionUk": "...", "options": [ /* той самий навик, інші числа/приклад — 2–3 варіанти в пулі */ ] }
    ]
  }
}
```
`misconceptionUk` — **сиблінг усередині кожного `option`**, не всередині `remediation`: причина хибності неправильного варіанту відома наперед (варіантів скінченна кількість, відомі при генерації), тому кешується разом з опцією — жодного живого виклику на пояснення для `choice`-кроків не потрібно взагалі.

**`open`-крок** (`content`):
```jsonc
{
  "questionUk": "...", "expectedAnswerUk": "...", "rubricUk": "...",
  "remediation": {
    "retryVariants": [ { "questionUk": "...", "expectedAnswerUk": "...", "rubricUk": "..." } ]
  }
}
```
Пояснення конкретної помилки для `open` **не кешується** — вільна відповідь дитини наперед невідома (КП-1 явно вимагає «конкретну причину», а не шаблон), тому це єдиний випадок, що потребує живого виклику `step_reinforcement` під час уроку (розд. 3 нижче).

**`interactive`-крок** (`visual`, доповнює ADR-020):
```jsonc
{
  "component": "number_line", "v": 1, "props": { ... }, "evaluate": { ... }, "fallback_text": "...",
  "remediation": { "hasRetry": true }
}
```
Для інтерактивних кроків пул варіантів **не потрібен** — нові `props` для повторної спроби породжує новий `regenerate(props, seed)` компонента (доповнення ADR-020, той самий документ); пояснення помилки — з наявної `describe(props, result)` (уже є, ADR-020 п. 1), теж без ШІ. `remediation.hasRetry` — лише прапорець «цей крок підтримує ремедіацію» (є сенс лише якщо компонент реалізує `regenerate()`); відсутність поля або `hasRetry: false` — крок без ремедіації, поводиться як сьогодні (`alt_explanation` → fallback без інтерактивного закріплення), ніколи не блокує урок.

**Немає жодного нового типу кроку** (ВП-37 (а)): `remediation`/`misconceptionUk` — необов'язкові поля існуючих `choice`/`open`/`interactive`; крок без цих полів (старий, згенерований до цього ADR, або компонент без `regenerate()`) деградує до сьогоднішньої поведінки (`alt_explanation` показує генеричний `explanation` з `evaluateAnswer`, потім fallback) — сумісність зі всією вже згенерованою бібліотекою збережена без міграції даних.

### 2. Стейт-машина US-6.15: жодних нових колонок сесії — стан виводиться з наявних `step_attempts`

Ключове архітектурне рішення: **`lesson_sessions.current_step_id` НІКОЛИ не змінюється під час ремедіації** — ремедіація не є новим кроком чи новою сесією стану, це лише інший ВМІСТ, що показується на тому самому кроці для другої спроби. Це означає, що вся вже наявна інфраструктура (пауза/відновлення, safety-override BUG-013, offline-черга, «Пояснити»/навігація US-6.16) працює без жодної спеціальної обробки — вона вже прив'язана до `session_id`+`current_step_id`, а не до того, ЩО саме показано.

**Хто в ремедіації визначається читанням `step_attempts`, не новим полем:**
```
remediationActive(session, step) :=
  step has remediation content (choice: any option.misconceptionUk, open/interactive: remediation present)
  AND count(step_attempts WHERE session_id, step_id) == 1
  AND that one attempt's verdict != 'correct'
```
Це буквально той самий предикат, що вже обчислює `decideBranch`'s "consecutiveFailures" (`state-machine.ts`) — жодної нової логіки підрахунку, лише додаткова гілка на тому самому вже наявному розгалуженні `alt_explanation` vs `mark_for_review_and_advance`.

**Потік (розширює `submitStepAnswer`, `app/src/server/lessons/orchestrator.ts`):**

1. **Спроба 1** (як і сьогодні): `evaluateAnswer` оцінює відповідь проти оригінального вмісту кроку. `verdict != 'correct'` → `decideBranch` повертає `alt_explanation` (без змін, той самий чинний код `state-machine.ts`).
2. Якщо крок МАЄ ремедіаційний вміст:
   - **`choice`:** пояснення = `options.find(o => o.id === chosenOptionId).misconceptionUk` (готове, без виклику ШІ). Варіант закріплення = `remediation.retryVariants[0]` (детермінований вибір — індекс `0`, бо на спробу 2 в циклі завжди рівно один прохід пулу; ротація за декількома проходженнями бібліотеки — відповідальність повторного проходження, поза цим ADR).
   - **`open`:** **один** живий виклик `step_reinforcement` (Sonnet 5) з контекстом: питання, еталон, рубрика, **дослівна відповідь дитини з цієї спроби** → повертає `explanationUk` (конкретна причина). Варіант закріплення = `remediation.retryVariants[0]` (кешований, без ШІ).
   - **`interactive`:** пояснення = `describe(props, evaluateResult)` (наявна функція ADR-020, без ШІ). Нові `props` = `component.regenerate(props, seed)` де `seed = hash(sessionId, stepId, attemptNo=2)` (доповнення ADR-020).
   - Крок БЕЗ ремедіаційного вмісту (старий крок / компонент без `regenerate()`) — поведінка як сьогодні: генеричний `explanation` з `evaluateAnswer`, та сама точна питання/варіанти на повторний показ (без зміни).
3. Відповідь `submitStepAnswer` (`AnswerResult`, розширено новим необов'язковим полем `remediation: { explanationUk, retryStep: LessonStepView } | null`) — коли `remediation != null`, клієнт (`LessonRunner.tsx`) показує `retryStep` **на місці поточного кроку** (той самий `stepId`, `stepNumber`/`totalSteps` не змінюються — лише `content`/`visual` замінені варіантом), з банером пояснення над ним (той самий UI-патерн, що вже є для `feedback` — просто тепер сам вміст кроку теж змінюється, не лише банер над ним).
4. **Спроба 2** (дитина відповідає на варіант закріплення): `submitStepAnswer` викликається знову з тим самим `stepId` (клієнт не знає і не повинен знати про існування «варіанту» — з його погляду це просто наступна спроба на той самий крок). Сервер повторно обчислює `remediationActive` (тепер `count == 1`, тобто активний) → **оцінює відповідь ПРОТИ ВАРІАНТА**, не проти оригінального вмісту кроку (`evaluateAnswer` отримує ефективний `content`/`visual`, підставлений з `remediation.retryVariants[0]`/regenerated `props`, а не зі `stepRow` напряму).
   - `correct` → `decideBranch` (attemptNo=2, verdict=correct) → `{ kind: "advance", skipHelpers: false }` — рух далі по уроку, цикл завершено успішно (ВП-35: 1 цикл вистачило).
   - знову не `correct` → `decideBranch` (2 невдачі поспіль) → `mark_for_review_and_advance` — **м'який fallback (КП-3):** відповідь несе `fallback: { textUk }`, зібраний **без нового виклику ШІ** з уже наявних полів оригінального кроку (`options.find(correct).textUk`/`content.explanationUk` для `choice`, `content.expectedAnswerUk` для `open`, `visual.fallback_text` для `interactive`) — «Ось як це вирішується» одним-двома реченнями, і урок рухається далі (тема так само позначається для повторення, US-6.3 КП-2, без змін).

**Відновлення після перезавантаження/паузи (`getLessonView`/`resumeLessonSession`):** реконструюється ТОЧНО той самий предикат `remediationActive` із наявних `step_attempts` для `current_step_id` — якщо активний, показується та сама ремедіаційна варіація, а не оригінальне питання. Єдина причина не перераховувати пояснення `open`-кроку живим викликом заново при кожному відновленні (що коштувало б повторний виклик ШІ й теоретично могло дати НЕ дослівно той самий текст при повторному виклику, що виглядало б як «зникло й з'явилось інше пояснення») — **єдина нова колонка цього ADR:**

```sql
alter table public.step_attempts
  add column if not exists remediation jsonb null;
comment on column public.step_attempts.remediation is
  'ADR-028: заповнюється лише на спробі, що ЗАПУСТИЛА цикл «поясни → закріпи» (attempt_no=1, verdict != correct, крок має remediation-вміст): { explanationUk, retryVariantIndex, source: "cached"|"live" } — кешує результат живого виклику (open-кроки) для ідемпотентного показу при перезавантаженні/відновленні й для журналу (US-6.15 КП-7), без повторного виклику ШІ.';
```
Для `choice`/`interactive` (де пояснення й так детерміноване/кешоване) це поле — лише журнал/аудит (КП-7), не критичне; для `open` — це те, що робить показ ідемпотентним. **Це єдина зміна схеми БД в усьому цьому ADR для US-6.15.**

### 3. Стейт-машина US-8.7 («поясни задачу №N»): стан виводиться з історії повідомлень чату, одна нова колонка `messages.meta`

US-8.7 не має «кроку уроку» — це послідовність повідомлень у per-темовому чаті (`chats`/`messages`, `server/lessons/chat.ts`). Той самий принцип «стан виводиться з наявної історії, а не зберігається окремо» застосовується тут через нову узагальнену колонку:

```sql
alter table public.messages
  add column if not exists meta jsonb not null default '{}'::jsonb;
comment on column public.messages.meta is
  'ADR-028: узагальнене тегування AI-повідомлень для секвенційних під-потоків усередині одного чату (сьогодні — лише US-8.7 "розбір задачі за номером": { kind: "homework_problem", problemNumber, stage: "method"|"attempt_feedback"|"fallback"|"solved", attemptNo }). Порожній об'єкт для решти повідомлень (звичайні питання-відповіді US-8.1/8.2) — не потребує міграції даних.';
```

**Потік (нова функція, напр. `explainProblemByNumber`/`submitProblemAttempt`, `server/lessons/chat.ts`, поруч із наявними `askTopicChat`/`explainStepAgain`):**

1. Дитина пише «поясни задачу №117» → номер уже однозначно визначено (US-2.8, поза цим ADR) → сервер шукає останнє AI-повідомлення в цьому чаті з `meta.kind='homework_problem' AND meta.problemNumber=117`, щоб визначити стадію.
2. **Немає попереднього повідомлення для цієї задачі** → **пояснення методу** (КП-1): retrieval тексту задачі за номером (уже проіндексовано, S1/S1b — без ШІ) + **один** легкий виклик (`tutor_chat`-рівень, той самий, що `askTopicChat` уже використовує) — метод/правило, БЕЗ розв'язку. Зберігається як AI-повідомлення з `meta = { kind: 'homework_problem', problemNumber: 117, stage: 'method', attemptNo: 0 }`.
3. Наступне повідомлення дитини (її спроба розв'язати) → стадія `'method'`/`'attempt_feedback'` з `attemptNo < 2` (ВП-38: 2 спроби після пояснення методу) → **модерація насамперед** (`moderateMessage`, той самий виклик, що вже є в `askTopicChat`) — `severity: 'urgent'` перериває ВСЮ послідовність і повертає `URGENT_REPLY_UK` (BUG-013, КП-6), незалежно від стадії/лічильника спроб, лічильник НЕ інкрементується. Інакше — **один** виклик `step_reinforcement` (той самий маршрут/модель, що й US-6.15, ВП-38 «той самий базовий параметр») з контекстом (текст задачі, метод із кроку 2, спроба дитини) → вердикт + конкретне пояснення помилки:
   - `correct` → підтверджуюча відповідь, `meta.stage = 'solved'` (цикл завершено, ВП-38 задоволено швидше за ліміт спроб).
   - не `correct`, `attemptNo + 1 < 2` → `meta = { ..., stage: 'attempt_feedback', attemptNo: attemptNo + 1 }`, дитині пропонується спробувати ще раз (КП-3).
   - не `correct`, вичерпано (`attemptNo + 1 >= 2`) → **fallback** (КП-4): **один** виклик, повний розв'язок із поясненням кожного кроку, `meta.stage = 'fallback'` — як останній, а не перший крок взаємодії.
4. **«Просто дай відповідь» / «розв'яжи за мене» до вичерпання спроб (КП-5):** розпізнається як частина того самого виклику `step_reinforcement`/method-пояснення (промпт явно інструктує не видавати розв'язок на стадіях `method`/`attempt_feedback` і доброзичливо пояснити чому) — не окрема гілка коду, а вимога до промпту; `developer` додає явний приклад у `prompts/`.

**Чому не той самий механізм, що й `askTopicChat` (пряме питання архітектору в постановці задачі):** примітиви (`moderateMessage`/`URGENT_REPLY_UK`, `getOrCreateChat`, збереження повідомлень, retrieval фрагментів за темою) **повністю перевикористовуються** — нових інфраструктурних шматків тут немає. Але сама СЕКВЕНЦІЯ (метод → спроба → перевірка → спроба → fallback, з лічильником і протидією «дай готову відповідь») — це НЕ той самий код-шлях, що вільне питання-відповідь `askTopicChat`: `askTopicChat` не має поняття «стадії» чи «спроби» і ніколи не повинен відмовляти видати пряму відповідь (це нормально для звичайного питання на кшталт «що таке дріб»). Тому це — нова, вузько сфокусована функція поверх спільних примітивів, а не розширення `askTopicChat` прапорцем.

### 4. UI (`LessonRunner.tsx`): вбудована заміна вмісту кроку, не модальне вікно/окремий екран

Ремедіація показується **на місці кроку**, не як модальне вікно чи окремий екран: `AnswerResult`'s `remediation.retryStep` рендериться через той самий `StepBody`-перемикач за `type`, що й звичайний крок (той самий React-компонент `DragSortStep`/вибір/відкрите поле) — лише з іншим `content`/`visual`, `stepId` не змінюється. Банер пояснення (`remediation.explanationUk`) з'являється НАД цим вмістом, тим самим стилем, що вже є для `feedback`. Це свідомий вибір, не модальне вікно поверх кроку: (а) уся навігаційна панель (US-6.16: «Пояснити», «На головну», «До списку уроків», тривога) лишається доступною й функціональною без жодних змін, оскільки технічно нічого не «зупинилось» на рівні сесії — це та сама сесія, той самий крок, лише інший показаний вміст; (б) дитина сприймає це як природне продовження діалогу «репетитор розбирається з тобою тут же», а не як перехід на інший екран.

### 5. Взаємодія з BUG-013 (safety-override) і D-77/D-78 (два бюджети швидкості)

- **BUG-013 — беззаперечний пріоритет, без винятків (як і в чинному коді сьогодні):** для US-6.15 модерація `open`-відповіді дитини вже відбувається в `submitStepAnswer` БЕЗУМОВНО для кожної реальної (не ідемпотентної) відправки типу `open` (наявний код, не змінюється) — оскільки ремедіація повторно використовує ТОЙ САМИЙ код-шлях `submitStepAnswer` для спроби 2 (просто з іншим ефективним вмістом для оцінки), захист спрацьовує автоматично без жодної спеціальної обробки; `verdict` так само примусово `partial` з `URGENT_REPLY_UK` замість пояснення помилки, і ремедіаційний цикл у цьому випадку взагалі не запускається (той самий чинний код, коментар у `submitStepAnswer` уже це описує). Для US-8.7 — модерація явно й першою в новій функції (розд. 3, крок 3) — теж без винятків.
- **Два бюджети швидкості:** кожен цикл ремедіації — **щонайбільше один** живий виклик ШІ (`step_reinforcement`, лише для `open`-кроків US-6.15 і для кожної спроби/fallback US-8.7); жодного синхронного `lesson_review` чи іншого провайдера в цьому шляху. `choice`/`interactive` — **нуль** живих викликів на цикл узагалі (повністю кеш/детермінізм). Це прямо задовольняє «має бути швидко, майже миттєво, одна репліка» (D-77) сильніше, ніж первісно закладено в ADR-023 (де малось на увазі «один виклик» для всіх типів кроку) — закриті ВП-36/37/38 фактично ще й здешевили та прискорили цей шлях проти первісного плану.

## Вплив на вартість

Див. `docs/03-resources-and-costs.md` розд. 3.2в (оновлено) — коротко: додатковий приріст ≈ **$0,5–2/міс** у «Економі» (нижче за первісну оцінку ADR-023 $1–3/міс, завдяки кешуванню/детермінізму для `choice`/`interactive`); маргінальний приріст токенів `lesson_generation`/`lesson_review` на блок (нові поля `misconceptionUk`/`retryVariants` у промпті й виводі) — не оцінюється окремою рядком, у межах вже закладеного запасу конвеєра (розд. 3.2а).

## Альтернативи

| Варіант | Чому ні |
|---|---|
| Новий тип кроку `remediation` у реєстрі (ВП-37 (б)) | ВП-37 явно закрито на користь (а) — розширення полів; більше змін в оркестраторі/бібліотеці/UI без переваги, якої немає в закритому варіанті |
| Нова колонка сесії (`lesson_sessions.remediation_stage`) для явного трекінгу «ми зараз у ремедіації» | Стан повністю виводиться з наявних `step_attempts` (той самий предикат, що вже рахує `decideBranch`) — нова колонка дублювала б інформацію й додала б ще один шлях розсинхронізації (як BUG-016 вже показав для схожого дублювання) |
| Live-виклик пояснення для КОЖНОГО типу кроку (`choice`/`open`/`interactive` однаково), як первісно окреслено в ADR-023 | ВП-36 (в) закриває це на користь кешу/детермінізму для `choice`/`interactive` — дешевше й швидше без втрати конкретності пояснення (обидва типи мають наперед відомий, скінченний набір можливих помилок) |
| Окрема нова таблиця для стану US-8.7 (`homework_problem_sessions`) замість `messages.meta` | Чат уже є журналом станів по конструкції (кожне повідомлення — подія); нова таблиця дублювала б це й ускладнила синхронізацію з `chats`/`messages`, не даючи нової можливості |
| Модальне вікно/окремий екран для ремедіації в уроці | Технічно нічого не «призупиняється» на рівні сесії — модальне вікно створило б враження зупинки там, де її немає, і додало б код для входу/виходу з нього замість перевикористання наявного рендеру кроку |

## Наслідки

- **Нові колонки БД (2, обидві nullable/default, без нової таблиці):** `step_attempts.remediation jsonb null` (US-6.15), `messages.meta jsonb not null default '{}'` (US-8.7).
- **Нові необов'язкові JSON-поля** в уже наявних `jsonb`-колонках `library_steps.content`/`library_steps.visual` (без міграції) — `options[].misconceptionUk`, `content.remediation.retryVariants[]`, `visual.remediation.hasRetry`.
- **Новий пункт реєстру компонентів** ADR-020 — `regenerate(props, seed)` (доповнення того ADR).
- **Немає нової моделі/маршруту** в `model_routes` — перевикористовує вже заскафолджений `step_reinforcement` (ADR-023, S27).
- Стара, ще не доповнена цим форматом бібліотека (кроки без `remediation`) продовжує працювати без змін (деградує до сьогоднішньої поведінки `alt_explanation`) — жодної обов'язкової міграції даних чи перегенерації існуючих `library_items`.
- Вартість — `docs/03-resources-and-costs.md` розд. 3.2в (оновлено).
- **Питання для Алекса (не з ВП-35…38 — ці лишаються закритими, це нове, не блокує реалізацію):** чи варто з часом (після кількох тижнів реального використання) розширити пул `retryVariants` понад 2–3 (наприклад, якщо та сама тема проходиться повторно кілька разів і діти бачать однакові варіанти закріплення) — рекомендація архітектора: почати з 2–3 (ВП-36 default), переглянути за даними частоти повторних проходжень тієї самої теми (`docs/STATUS.md`).
