# ADR-038. Візуальний контент уроків — чотири окремі питання: бюджет Pictory+ElevenLabs, адаптивні вставки на льоту, програмні діаграми для математики/геометрії, і ризик авторських прав веб-зображень

- **Статус:** дослідження (architect, 2026-09-29), за прямим дорученням оркестратора на основі побажань PO цієї сесії. Рішення й пріоритезація — за PO; цей ADR не запускає розробку сам по собі.
- **Вимоги:** розширює US-6.1 КП-3/КП-4, US-6.17 (D-113, ADR-020 §1 «каталог ресурсів»); US-6.15 (адаптивна корекція помилки), US-6.16 (кнопка «Пояснити»), US-6.19/US-6.20 (кандидати, не пріоритезовані), E-21 (US-21.2/21.3 — «проблемна тема», черга додаткових уроків), E-24/US-24.6 (карта знань, джерело сигналу); NFR-SAFE-15 (ADR-020 — модель ніколи не генерує довільний код/HTML/SVG, лише дані для реєстру компонентів)
- **Пов'язані:** ADR-006 (жива розмова, ElevenLabs — заплановано, S12, ще не реалізовано), ADR-025 (пасивна начитка — OpenAI `gpt-4o-mini-tts`, уже в коді), ADR-020 (каталог ресурсів і реєстр інтерактивних компонентів), ADR-022/033 (педагогічний конвеєр, кешування «згенеровано раз — показано багато разів»), ADR-031 §2 (зображення з підручника vs ШІ-генерація — уже підняте, частково відкрите питання), ADR-019 (модерація зображень — прецедент для §3.3 нижче)
- **Не дублює й не перевирішує:** ВП-60/ВП-61/ВП-62 (11.3, `docs/01-requirements.md` — D-113, тарифи слайд-шоу/відео) лишаються чинними відкритими питаннями, цей ADR **додає до них конкретні цифри вартості для одного вузького сценарію** (Pictory+ElevenLabs для скриптованого відео-фрагмента), не переглядає сам продуктовий вибір; ВП-57/58/59 (AI-згенеровані тематичні зображення для уроку — **вже схвалено в принципі**, статичний показ, без модерації, час-обмежено особистим тестуванням PO з донькою) приймається тут як **уже прийняте рішення**, на якому §3 і §4 нижче будуються, а не яке переглядається.

## Контекст

PO цієї сесії окремо підняв чотири пов'язані, але різні за природою питання про візуальний контент уроків: (1) чи має сенс купувати Pictory+ElevenLabs для генерації відео з книг, (2) чи можна на льоту під час уроку вставляти нові пояснювальні блоки з інших уроків чи згенеровані заново, коли дитина помиляється, (3) чи можна на льоту малювати діаграми для математики/геометрії, (4) чи можна шукати «безкоштовні» картинки в інтернеті для ілюстрації тем (наприклад, історія X століття). Нижче — дослідження й рекомендація по кожному, окремо, з бюджетом де можливо.

## Частина 1. Pictory + ElevenLabs для відео-контенту уроку

### Реконсиляція: що з цього вже є в коді сьогодні

Перевірено (`app/src/server/ai/providers/`): **ElevenLabs у коді відсутній.** Живий голос репетитора (роль `tts`, ADR-006) — **заплановано**, S12, ще не реалізовано. Пасивна начитка вже готового тексту (роль `passive_narration`, ADR-025) — **реалізована сьогодні через OpenAI `gpt-4o-mini-tts`** (`openai.ts`, функція `openaiTts`), не ElevenLabs — свідомий вибір ADR-025 (у 3–7 разів дешевше за ElevenLabs для цього застосування, українська підтверджена). Отже сама постановка питання «Pictory + ElevenLabs» сьогодні означала б **два нові платні провайдери одразу**, жоден з яких ще не інтегрований, для функції (озвучений відео-ролик), якої немає в жодному MVP-US.

### Пряме протиріччя з уже сформульованою позицією PO цієї сесії

PO дослівно (перефразовано з цієї сесії): продукт має бути **рецензентом-репетитором, а не курсом із наперед змонтованих відео на кшталт ChatGPT/Pictory**; PO був явно скептичний щодо підходу «купити дорогий ElevenLabs+Pictory, заскриптувати відео з книг» саме як **неправильної архітектури** для того, чого він хоче — адаптивного ШІ-репетитора, а не статичного відеокурсу. Це узгоджується з уже задокументованим висновком PM за D-113 (12.32, `docs/01-requirements.md`): анімовані/відео-фрагменти (Gemini чи будь-який інший провайдер) — це «якісно новий, значно дорожчий і ризикованіший режим подачі», свідомо не рекомендований до старту зараз (ВП-61 лишається відкритим, не для реалізації).

### Бюджет для вузько-обмеженого сценарію (не повна заміна уроку, а короткий скриптований вступ/пояснювач на тему, згенерований один раз і закешований — за аналогією з принципом «згенеровано раз, показано багато разів», ADR-022/033)

**Довірчий рівень цих цифр — середній**: перевірено пошуком офіційних/агрегованих джерел 2026-09-29, ціни на планові підписки (не pay-per-video API), точна вартість одного конкретного короткого ролика через API Pictory не публікується прозоро (кредитна модель) — цифри нижче орієнтовні, не контрактні.

| | Pictory (відео) | ElevenLabs (голос до відео) |
|---|---|---|
| Модель ціни | Підписка, $29–199/міс (річна: $25–119/міс), ліміт 200–1800 хв відео-експорту/міс + окремі «AI-кредити» на функції | Підписка чи pay-as-you-go, ≈ $0,05–0,10/1000 символів (Flash/Multilingual v2, за прайсом уже зафіксованим у ADR-025 §Дослідження) |
| Вартість «один короткий вступ/тема» (≈ 60–90 сек, ≈ 700–1000 симв. скрипту) | Не окремо тарифікується — «з'їдає» частину місячного ліміту хвилин підписки, яку так само треба платити навіть за 1 відео/місяць (мінімум $25–29/міс) | ≈ $0,05–0,10 за озвучку самого скрипту (дешева частина) |
| Разом, «1 тема/тиждень» (≈ 4 теми/міс) | **Мінімум $25–29/міс** (найдешевший тариф Pictory) незалежно від фактичного обсягу, бо це вхідний квиток підписки, не оплата за штуку | + ≈ $0,20–0,40/міс за озвучку |
| Порівняно з наявним підходом | Кожен блок уроку сьогодні коштує ≈ **$0,27–0,33 за генерацію** (весь текст+вправи+рецензія, ADR-022/033 `docs/03` розд. 3.2а), а показується **необмежену кількість разів безкоштовно** (кешовано в бібліотеці) | — |

### Рекомендація

**Не інтегрувати Pictory чи ElevenLabs-для-відео зараз, ні у вузькому, ні в повному сценарії.** Причини:
1. Мінімум $25–29/міс **фіксованої** підписки Pictory за функцію, якої немає в жодній US, і яка прямо суперечить сформульованій PO архітектурній перевазі («адаптивний репетитор, не готове відео»).
2. Уже узгоджений з PO шлях посилення «текст демотивує» — **US-6.17 («ілюстрована послідовність слайдів», Should/R2-кандидат, ВП-60)** — дає близький ефект (яскравіша, менш суцільно-текстова подача) істотно дешевше: це розширення вже наявного кроку `slide` (текст + зображення з каталогу, генерується й кешується разом з рештою блоку тим самим конвеєром — не нова інфраструктура, не нова підписка) — саме той компроміс «база кешується один раз + інтерактивний шар зверху», який PO вже обговорював цієї сесії.
3. Якщо PO все ж хоче озвучений короткий вступ/пояснювач до теми (не заміну уроку) — дешевший і вже узгоджений шлях **існує сьогодні**: текст пояснення (уже генерується) + **пасивна начитка через `gpt-4o-mini-tts`** (ADR-025, вже в коді, ≈ $0,02–0,04/1000 симв., без нової підписки) — без відео-шару Pictory взагалі. Це не нова робота, а можливе розширення застосування вже наявного `passive_narration`.
4. Це узгоджується з ВП-61 (11.3) — не переглядає його, а дає конкретну причину не відкривати Фазу 0 для відео зараз: реальна цифра ($25–29/міс мінімум, для функції поза MVP) підтверджує обережність PM.

## Частина 2. Адаптивна вставка нового пояснювального блоку на льоту під час уроку

### Що вже покрито — не нова робота

| Сценарій PO | Наявний механізм | Новий? |
|---|---|---|
| Дитина помилилась — репетитор одразу пояснює й дає схоже завдання | **US-6.15** (цикл «поясни → закріпи», Must, у коді) | Ні |
| Дитина хоче інше пояснення того самого кроку в будь-який момент | **US-6.16 КП-1**, кнопка «Пояснити» (Must) | Ні |
| Дитина хоче побачити готову відповідь, не намагаючись далі | **US-6.19** (кандидат, не пріоритезовано, ВП-70) | Частково — чекає рішення PO |
| Дитина хоче вийти з кроку без відповіді після N спроб | **US-6.20** (кандидат, педагогічний принцип уже закрито PO — D-119, поріг N — ВП-71) | Частково — чекає деталі |

Усі чотири — реакція **в межах одного кроку/питання**, миттєва, без пошуку зовнішнього контенту. Це вже описано.

### Що дійсно нове — проактивне підтягування контенту з **іншої** теми/уроку як сигнал прогалини в передумові

PO хоче більше: коли повторні помилки на поточній темі виглядають як ознака **прогалини в темі-передумові** (не «дитина не зрозуміла це речення», а «дитина не засвоїла попередню тему, від якої залежить ця»), репетитор має сам підтягнути короткий пригадувальний блок — або з реального минулого уроку (перевикористання), або згенерований на місці. Це **не** покрито жодною наявною US — це новий, складніший рівень адаптивності, ближчий за природою до E-21 (US-21.2 «проблемна тема», US-21.3 «черга додаткових уроків»), але на іншому часовому масштабі: **E-21 працює по завершенню(-ях) уроку/періоду** (дні-тижні, чергою, окремим наступним уроком), а тут ідеться про **втручання просто зараз, посеред поточного уроку**, без черги й без очікування.

### З чого складалась би реалізація (оцінка обсягу, не готове рішення)

1. **Сигнал** — уже частково є дані: карта знань (E-5) і `topics.dependencies` (ADR-004/022 — теми вже мають зв'язки передумов, ADR структурування книги індексує їх) дають технічну можливість запитати «чи є в темах-передумовах поточної теми незасвоєний рівень». Бракує: явного **порогу спрацювання** (скільки повторних помилок на поточному кроці/темі за яке вікно вважати сигналом «ймовірно, проблема в передумові, не в цьому кроці» — окреме педагогічне рішення PM/PO, не технічна деталь) і **логіки, що саме з кількох можливих тем-передумов вибрати** (найближча за графом залежностей? найгірша за картою знань?) — обидва потребують окремого продуктового рішення перед оцінкою обсягу коду.
2. **Пошук релевантного минулого уроку** — технічно дешевий крок: `library_items`/`library_steps` уже проіндексовані за темою (та сама бібліотека, що ADR-014); вибір «показати вже готовий, закешований блок теми-передумови» — **$0 AI-виклику**, лише запит у БД + показ наявного кроку.
3. **Генерація нового, вужче сфокусованого міні-пояснення на льоту (коли готового блоку немає чи він завеликий для вставки посеред іншого уроку)** — це **справді новий платний AI-виклик**, не безкоштовний варіант. За аналогією з вартістю вже наявного одиничного виклику пояснення в циклі US-6.15 (те саме сімейство моделі/провайдера `[$L]`, короткий, сфокусований текст, не повний блок з рецензією) — orientировочно **$0,01–0,03 за виклик** (не проходить повний конвеєр `lesson_generation`+`lesson_review`, ADR-022 — це живий, «легкий» виклик під час діалогу, аналог одиничних реплік US-6.15/US-6.16, не кешований генератор блоку). Точна цифра — оцінка після вибору моделі й формату промпту, не контрактна.
4. **Безпека/якість** — той самий принцип NFR-LANG-3 (не суперечити підручнику) застосовний і тут: міні-пояснення на льоту повинно спиратися на вже проіндексований `chunks`-текст теми-передумови (RAG-контекст), а не вигадувати з нуля — тобто це **розширення наявного генератора пояснень**, не нова архітектура генерації.

### Рекомендація

Це — **реальна, окрема, педагогічно виправдана можливість**, не дублювання наявних механізмів, але вона потребує **окремої Фази 0** (нова US, нове ВП про поріг спрацювання й вибір теми-передумови) перш ніж оцінювати обсяг коду й остаточну вартість — той самий процес, що вже застосований до E-21. Пропоную `product-manager` сформулювати це як нову історію під E-21 чи новий епік (за аналогією з уже прийнятим рішенням об'єднати D-90/D-91 в один механізм, 12.20) — **не оцінка цього ADR**, лише фіксація обсягу дослідження й орієнтовної вартості одиничного виклику вище.

## Частина 3. Діаграми на льоту для математики/геометрії

### Рекомендація — однозначно (б): програмний рендеринг структурованих даних, не ШІ-генерація зображення

Геометричний малюнок (трикутник із заданими кутами, числова пряма, точка на координатній площині) — це задача **рендерингу відомих чисел**, не задача «намалювати картинку» у творчому сенсі. Це прямо узгоджується з уже прийнятим принципом **NFR-SAFE-15/ADR-020**: «модель ніколи не генерує довільний код/HTML/JS/SVG — лише дані (`props`) для заздалегідь написаного, перевіреного компонента реєстру». Практично: генератор уроку (той самий `[$L]`-виклик, що вже формує задачу) повертає структуровані дані («трикутник, кути 40°/60°/80°, підписати вершини A/B/C») як `props` нового чи наявного компонента реєстру (за аналогією з `diagram_hotspots`, R2-план ADR-020), а **клієнтський код** (бібліотека на кшталт `react-konva`/чистий SVG, написана й перевірена розробником один раз) малює точну, детерміновану картинку з цих чисел — той самий патерн, що графік малює бібліотека діаграм із чисел, а не «ШІ малює графік».

### Порівняння вартості

| | (б) Програмний рендер (рекомендовано) | (a) ШІ-генерація зображення (DALL-E/`gpt-image-*`) |
|---|---|---|
| Вартість за діаграму | **$0** (детерміноване виконання коду клієнта/сервера, як і будь-який інший інтерактивний компонент ADR-020) | ≈ $0,01–0,25/зображення залежно від якості/роздільності (перевірено пошуком 2026-09-29 для `gpt-image-1`: $0,011–0,016 (low), $0,042–0,063 (medium), $0,167–0,25 (high); **`gpt-image-1` знімається з підтримки 23.10.2026** — на момент реалізації перевірити актуальну модель-наступника) |
| Точність | **100% точна** — кути/координати саме ті, що задані даними, завжди коректні | Ненадійна — відомий клас проблем image-моделей із точним відтворенням геометрії/тексту на зображенні (підписи кутів, точні пропорції) — реальний ризик показати дитині з математики **неправильну** діаграму |
| Кешованість | Кожна унікальна комбінація значень рендериться на льоту з тих самих даних — фактично безкоштовна «регенерація» за потреби (інша дитина, інше число — та сама формула рендера) | Кожна унікальна комбінація значень — нове зображення, новий платний виклик, і без гарантії коректності навіть тоді |
| Обсяг розробки | Одноразовий (на клас діаграм — трикутник, числова пряма, координатна площина) компонент реєстру ADR-020, оцінює `developer`; далі — $0 за використання | $0 розробки, але постійна вартість за виклик + ризик якості вище |

**Коли (a) все ж доречна:** лише коли зміст справді не зводиться до структурованих даних (наприклад, «намалюй, як виглядає сузір'я Оріон» для природознавства — це не про числа) — тоді це вже питання §4 нижче (ілюстрація, не діаграма), не цього розділу.

## Частина 4. Пошук зображень з інтернету для ілюстрації уроків (напр. історія X століття)

> **Це питання несе реальний, серйозний юридичний ризик — авторське право/ліцензування — який потрібно позначити прямо, а не побіжно.** «Безкоштовно знайти в інтернеті» **не означає** «законно використовувати/показувати в застосунку», навіть для особистого використання, і тим паче якщо продукт коли-небудь вийде за межі однієї родини (комерційна готовність — вже піднята тема, ADR-018). Зображення з випадкового пошуку (Google Images і подібне) майже завжди має власника авторських прав, і показ дитині в застосунку без ліцензії — це **реальна юридична відповідальність**, не гіпотетичний ризик.

### Рекомендація — однозначна: **не будувати** функцію «пошук по інтернету → вставити перше знайдене зображення»

Це пряма юридична вразливість, порівнянна за принципом із уже відкинутим варіантом «модель генерує довільний код» (NFR-SAFE-15) — і тут, і там причина одна: **непідконтрольний, непередбачуваний зовнішній вхід, який показується дитині без перевірки**.

### Безпечні альтернативи

1. **Wikimedia Commons** — реальне, добре придатне для історії джерело: мільйони зображень із чіткою, перевіреною по кожному файлу ліцензією (суспільне надбання/CC), включно з історичними артефактами, картинами, картами саме тих епох, які цікавлять PO (X століття, Київська Русь тощо). API безкоштовний. **Довірчий рівень: високий** — це загальновідомий, документований статус проєкту; конкретний ліцензійний статус кожного окремого файлу все одно потрібно перевіряти програмно (поле `license`/`permission` у метаданих Commons API), не вважати «весь сайт» автоматично безпечним без цієї перевірки.
2. **Інші публічні архіви суспільного надбання** (напр. національні музейні цифрові колекції, Europeana) — існують, але architect **не перевіряв** конкретні умови кожного окремого архіву цим дослідженням — прапорець низької впевненості, вимагає окремої перевірки перед використанням, якщо PO захоче розширити за межі Wikimedia Commons.
3. **Платні stock-фото API з чіткими комерційними умовами** (напр. Unsplash API/Adobe Stock API) — можливі, але architect **не перевіряв** актуальні умови для «показ дітям у навчальному застосунку» конкретно — прапорець низької впевненості, окрема перевірка ліцензійних умов перед вибором, якщо Wikimedia Commons не покриває потрібний випадок (сучасні фото, не історичні артефакти).
4. **ШІ-генерація ілюстрації замість реального фото** («згенеруй ілюстрацію вбрання Київської Русі X століття») — обходить питання авторських прав **повністю** (нове, згенероване зображення, не чиясь чужа робота), коштом іншого, керованішого ризику: **історична неточність** — згенероване зображення може бути не зовсім достовірним відтворенням реалій епохи. Цей ризик **приймається й контролюється** явним підписом-застереженням («художня реконструкція», не «фотографія артефакту») — той самий принцип чесності з дитиною, що вже застосований у застосунку (NFR-SAFE-1 — репетитор завжди чесний, що він ШІ). Вартість — та сама, що вже схвалена ВП-57/58/59 для тематичних зображень уроку (≈ $0,01–0,25/зображення залежно від моделі/якості, кешується один раз на тему за тим самим принципом, що решта контенту, ADR-022/033).

### Підсумкова рекомендація по §4

**Не** будувати відкритий пошук/скрейпінг веб-зображень. Для історії конкретно — **Wikimedia Commons як основне, перевірене джерело** (реальні артефакти/мистецтво, з явною атрибуцією джерела дитині — узгоджується з наявним принципом US-6.1 КП-2 «кожне пояснення містить посилання на джерело»); для випадків, коли Commons не має відповідного зображення чи PO хоче стилістично єдину, «намальовану» ілюстрацію — **ШІ-генерація з явним підписом «художня реконструкція»**, той самий механізм і бюджет, що вже схвалено ВП-57/58/59, лише з доданою вимогою підпису-застереження для історично-чутливого контенту конкретно (нова, вузька умова, не перегляд самого схвалення).

## Наслідки

- **§1:** жодної нової інтеграції/підписки зараз; підтверджує вже прийняту обережність ВП-61 конкретною цифрою ($25–29/міс мінімум Pictory, поза MVP); якщо PO захоче озвучений вступ до теми — дешевший шлях уже існує (текст + `gpt-4o-mini-tts`, ADR-025), без нового ADR.
- **§2:** реальна, окрема нова можливість (проактивне підтягування контенту теми-передумови) — потребує нової Фази 0 в `product-manager` (нова US/ВП про поріг сигналу й вибір теми) перш ніж `architect` дає остаточну оцінку обсягу коду; вартість одиничного нового AI-виклику на льоту — орієнтовно $0,01–0,03, не $0.
- **§3:** рекомендація зафіксована — новий компонент реєстру ADR-020 для геометричних діаграм (трикутник, числова пряма, координатна площина), $0 маржинальної вартості за використання; обсяг розробки компонента — оцінка `developer`, окрема задача, не в цьому документі.
- **§4:** нова функція «пошук картинок в інтернеті» **не рекомендується до розробки** в жодній формі без окремого явного рішення PO, що прямо приймає юридичний ризик; безпечна альтернатива для історії — Wikimedia Commons (нова, легка інтеграція API, окрема оцінка обсягу, якщо PO підтвердить напрям) + вже схвалена ШІ-генерація з підписом «художня реконструкція» для решти випадків.
- Без впливу на `docs/03-resources-and-costs.md` цим документом — жодна з рекомендованих дій (§2 генерація на льоту, §3 рендер, §4 Wikimedia+генерація з підписом) не запускається цим ADR; оновлення кошторису — коли/якщо PO підтвердить конкретний напрям і `product-manager` сформулює US.

## Відкриті питання до PO

1. **§2:** чи вважати проактивне підтягування контенту теми-передумови пріоритетом для `product-manager` (нова Фаза 0), чи це кандидат дорожньої карти без активної роботи зараз (за аналогією зі статусом E-21/ВП-47)?
2. **§4:** чи підтверджуєте напрям «Wikimedia Commons + ШІ-генерація з підписом "художня реконструкція"» як єдину дозволену пару джерел зображень для тем без підручника-джерела (напр. історія), чи потрібне ширше дослідження інших ліцензійних архівів/stock-API перед рішенням?
3. **§1:** чи достатньо цього дослідження, щоб вважати ВП-61 (D-113, тариф 3 — відео) закритим у бік «не зараз», чи PO хоче окрему, повнішу Фазу 0 саме для вузького сценарію «короткий озвучений вступ до теми» (без Pictory, лише текст + наявний `gpt-4o-mini-tts`) як самостійну ідею?
