# ADR-043. Спільний інтерфейс «чи є активний імпортований урок для теми» — хелпер зараз, схемна уніфікація відкладена (AR-29 п.2)

- **Статус:** прийнято
- **Вимоги:** AR-29 (`docs/01-requirements.md` §11.2), E-31/S45 (`docs/05-backlog.md`)
- **Пов'язані:** ADR-044 (модель даних `literature_v3_*`, та сама задача AR-29); `app/src/server/subjects/queries.ts` (`getSubjectDetail`, `SubjectTopicOption`); `app/src/app/(child)/lesson/[sessionId]/page.tsx` (safety-net redirect)

## Контекст

Чотири паралельні, незалежні системи «імпортований урок для теми» вже існують:

| Зріз | Таблиця | Контракт вмісту |
|---|---|---|
| S33 | `literature_lessons` | Екстракційний конвеєр, параграфно-структурований предмет |
| S34 | `course_lessons` | Image-anchored (фото сторінки — джерело істини, OCR — допоміжний) |
| S35 | `course_v2_lessons` + `course_v2_questions`/`course_v2_question_keys` | Повний текст, `single_choice` з `correct_option_id` |
| S36 | `literature_v2_lessons` + `literature_v2_tasks`/`literature_v2_task_keys` | Повний текст, відкриті завдання (без єдиної правильної відповіді) |

Кожна з них додає одну й ту саму перевірку «чи є активний рядок для цього `topic_id`» у рівно ДВА місця коду: `getSubjectDetail`/`SubjectTopicOption` (екран предмета — яку кнопку показати) і `/lesson/[sessionId]/page.tsx` (safety-net redirect зі старого/класичного оркестратора уроку, якщо хтось потрапив на цю сторінку для теми, що насправді вже обслуговується одним із імпортованих форматів). Коментарі в коді (`queries.ts`: «S33/S34/S35/S36: same lookup, Nth parallel table») прямо documentують, що це свідомо повторюваний патерн — і саме тому це реальний, уже кілька разів спрацьований клас багів: PO кілька разів ловив на реальному тестуванні випадок «додали новий зв'язок (новий `*LessonId`) в одне місце й забули про друге».

E-31/S45 додає **п'яту** таку систему (`literature_v3_*`, ADR-044). AR-29 прямо запитує: чи варто перед цим спроєктувати спільний інтерфейс замість п'ятого окремого набору перевірок.

## Варіанти

**а) Схемна уніфікація зараз.** Одна таблиця `imported_lesson_links` (`topic_id`, `kind` enum, `target_table`, `target_id`, `status`), яку заповнює кожен імпортер замість (чи на додачу до) власної. Обидва місця коду читають ОДНУ таблицю одним запитом.
- Плюс: справді один спільний контракт, легко додати 6-й/7-й формат.
- Мінус: потребує міграції й зміни ВСІХ п'яти наявних імпортерів (написати в нову таблицю при кожному імпорті/зміні статусу), ризик розсинхронізації самої нової таблиці з таблицями-джерелами (ще один клас багів замість вирішеного), і не усуває потреби в окремому рендерері для кожного формату — відповідає лише на питання «чи є урок і куди вести», не на «як його показати».

**б) Спільний серверний хелпер, схема — без змін (обрано).** Один новий експорт, напр. `getActiveImportedLessonForTopic(familyId, topicId): { kind; lessonId } | null`, що інкапсулює всі (тепер п'ять) `select`-и, які сьогодні розкидані по двох місцях коду. Обидва місця — `getSubjectDetail`/`SubjectTopicOption` і `/lesson/[sessionId]/page.tsx` — викликають **лише цю функцію**.
- Плюс: закриває РІВНО той механізм бага, що й задокументований («забули додати в друге місце») — друге місце більше не знає взагалі ні про які конкретні таблиці, лише про результат хелпера. Нуль нових таблиць, нуль міграцій. Додавання 6-го формату — одна зміна (в хелпері), не дві (в хелпері й у споживачах).
- Мінус: усередині хелпера все одно п'ять окремих `select`-ів (не одна уніфікована схема) — якщо колись формат стане залежати від спільних метаданих понад «чи існує і куди вести» (напр. єдиний список «усі активні уроки сім'ї» для якогось майбутнього звіту), доведеться або зробити (а) тоді, або агрегувати в хелпері.

**в) Нічого не робити, п'ята система так само, як перші чотири.** Найшвидше зараз, але гарантовано повторює вже двічі спійманий PO баг ще раз.

## Рішення

**Варіант б).** Один спільний хелпер замість схемної уніфікації. Обґрунтування:

1. **Сам баг — у МІСЦІ виклику, не в кількості таблиць.** Схемна уніфікація (а) — це рефакторинг заради іншої властивості (єдиний контракт для БУДЬ-ЯКОГО майбутнього споживача), яка сьогодні не потрібна жодному реальному споживачу, окрім двох, що вже закриває (б) за частку вартості.
2. **П'ять форматів — це п'ять ГЕНУЇННО різних моделей вмісту** (параграфний текст, image-anchored, full-text quiz, full-text open-response, тепер flow-based з текстами творів) — кожен і так вимагає власного компонента перегляду (ADR-044 §3: новий `LiteratureV3LessonView.tsx`, не розширення наявних). Спільна таблиця-реєстр не зменшує цю різноманітність, лише додає ще один шар, синхронізація якого з п'ятьма джерелами — новий ризик.
3. **Відповідає A-P3** («найпростіше, що задовольняє вимоги», `docs/02-architecture.md` розд. 1): хелпер — це рядків 20-30 коду й нуль нових таблиць; схемна уніфікація — нова міграція, зміна п'яти імпортерів, нові RLS-політики.

**Відкладений технічний борг (не зараз, не блокує S45):** якщо з'явиться 6-й/7-й формат АБО сам хелпер (п'ять `select`-ів поспіль) стане відчутно важким для підтримки/повільним — повернутись до варіанта (а). Орієнтовна оцінка цього майбутнього рефакторингу — **≈1–1,5 дня**. Тригер для перегляду — не календарна дата, а конкретна подія (новий формат, скарга на швидкість/складність).

## Наслідки

- `app/src/server/subjects/queries.ts`: новий експортований хелпер, що замінює п'ять окремих inline-лукапів у `getSubjectDetail` на виклики спільної функції (сама функція всередині лишається п'ятьма `select`-ами — рефакторинг мінімізує дублювання коду виклику, не змінює кількість запитів до БД).
- `app/src/app/(child)/lesson/[sessionId]/page.tsx`: safety-net redirect переписується на виклик того самого хелпера замість власного ланцюжка `if/else if`.
- Жодної нової міграції, жодної зміни RLS для цього рішення самого по собі (ADR-044 додає RLS-зміни з ІНШОЇ причини — розширення `course_v2_questions`/`course_v2_quizzes`).
- Для `literature_v3` (ADR-044) хелпер із самого початку пише саме так, щоб додавання шостого формату колись у майбутньому означало одну нову гілку в хелпері, не дві розкидані зміни.
