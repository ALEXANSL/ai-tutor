# ADR-035. Дашборд бюджету: власний облік витрат замість «балансу провайдера»

- **Статус:** дослідження архітектора — рішення про обсяг v1 за Алексом (2026-09-29)
- **Вимоги:** NFR-COST-4, NFR-COST-8, US-11.5 КП-1…КП-10, ADR-012 (примітка 2026-09-27 про деталізацію по уроку)

## Контекст
Алекс хоче бачити в застосунку «повну фінансову картину»: поточний баланс у кожного провайдера ШІ, скільки вже витрачено, платежі, що йдуть. Треба з'ясувати, що з цього технічно можливо через API провайдерів, а що доведеться будувати з власних даних, і що показати в першій версії дашборда.

Провайдери, які реально використовує застосунок (`app/src/server/ai/`):
- **Anthropic** — `structured`/`vision` виклики (`providers/anthropic.ts`).
- **OpenAI** — `structured`, `embed`, `audio`/TTS (`providers/openai.ts`).
- **ElevenLabs** — живий голос уроку, окремо від маршрутизатора моделей (ADR-006); ще не має адаптера в `router.ts`, облік вартості — за оцінкою хвилин + post-call webhook (ADR-012).
- **Google Drive** — лише зберігання/читання файлів, без тарифікації за використання в нашому обсязі → не бере участі в бюджеті, не розглядається далі.

## Дослідження: що дають API провайдерів (перевірено пошуком 2026-09-29)

| Провайдер | Є API для витрат/використання? | Що саме повертає | Баланс/кредит, що лишився? |
|---|---|---|---|
| **Anthropic** | Так — `GET /v1/organizations/usage_report/messages` (токени по часу, моделі, ключах) і `GET /v1/organizations/cost_report` (витрати в USD по днях) | Історичні агреговані дані, **потребують Admin API key** (`sk-ant-admin...`, видає адміністратор організації в консолі) | **Ні.** Немає ендпоінту балансу; `GET /v1/organizations/balance` не існує (404) — підтверджено відкритими фіче-реквестами в репозиторіях Anthropic |
| **OpenAI** | Так — `GET /v1/organization/costs` (щоденні витрати, групування по проєкту/ключу/користувачу), `GET /v1/organization/usage/*` | Історичні агреговані дані, потребує **admin/organization API key** | **Ні** офіційно. Є недокументований внутрішній `/v1/dashboard/billing/credit_grants` (той, що використовує сама консоль) — не публічний контракт, може зникнути без попередження; офіційного способу прочитати залишок передоплаченого балансу немає |
| **ElevenLabs** | Так — `GET /v1/user/subscription` | `character_count`, `character_limit` (квота символів TTS/Agents у межах тарифу), дата скидання | Це **квота символів**, не грошовий баланс. Для our use case (Creator $22/міс, 275 хв) це найближче до «скільки лишилось у пакеті» — придатне для показу «використано X із 275 хв цього місяця», але це не рахунок у доларах і не «баланс рахунку» |
| **Google Drive API** | Не стосується витрат ШІ — використання Drive у нашому обсязі безкоштовне | — | — (не релевантно) |

**Висновок дослідження:** жоден з провайдерів не дає через API «поточний грошовий баланс рахунку» — це категорія білінгу/способу оплати, яку провайдери показують лише у своїй веб-консолі. Те, що API дають (Anthropic, OpenAI) — це **історичні звіти про вже витрачене** за минулі періоди, причому вимагають окремого адмін-ключа з вищими правами, ніж робочий API-ключ застосунку (ще один секрет, ще один вектор ризику — суперечить принципу мінімізації ключів на сервері, CLAUDE.md). Крім того, ці звіти оновлюються з затримкою (не миттєво) і не замінюють роль «≤ 1 хв після виклику», яку вже виконує наш власний облік (ADR-012 явно відкидав «опитування API витрат провайдерів» із тієї ж причини — див. таблицю альтернатив ADR-012).

Тобто дашборд «баланс рахунку в кожного провайдера» **не є досяжним через API** для жодного з трьох провайдерів. Максимум, що технічно можливо додатково до власного обліку, — окремий фоновий job раз на день, що тягне `cost_report`/`costs` як **звірку** (ADR-012 вже згадує «щоденну звірку перші 2 тижні» вручну) — це звірка, а не заміна власного обліку, і вимагає нового адмін-ключа з підвищеними правами в кожного провайдера.

## Що вже надійно рахує застосунок (готово сьогодні)

Схема з S1-міграції (`supabase/migrations/20260926100000_s1_ai_router_costs_jobs.sql`) вже дає все потрібне для повноцінного дашборда **власних** витрат:

- `ai_calls` — кожен виклик: `role`, `provider`, `model`, `cost_usd`, `status`, `session_id`, `ref_table/ref_id`, `created_at`, `fallback_used`. Це вже точний, пооб'єктний облік (не оцінка «якось потім»).
- `spend_months` — `spent_usd`, `limit_usd`, `state` (`normal/warned/budget/hard_stop`), `safety_over_limit_usd`, `state_changed_at` — вже готова місячна агрегація й пороги 80/100/110 %.
- Примітка в ADR-012 (2026-09-27) вже визначила бракуючу деталізацію по уроку (SQL-в'ю `session_costs` по `session_id`) — не нова система, лише нове представлення.
- Немає лише: (1) розбивки по хвилинах живого голосу ElevenLabs окремо від LLM-частини «ШІ-друга» в UI (дані є в `ai_calls.role` і, за ADR-012, у voice-хвилинах з heartbeat); (2) графіка тренду по днях/тижнях; (3) фільтра по предмету/дитині (у MVP — одна дитина, тому нерелевантно поки немає кількох профілів, ADR-021).

## Рішення (рекомендація архітектора)

**Будувати дашборд на власних даних (`ai_calls` + `spend_months`), не на живому балансі провайдерів.** Позиціонувати Алексу як «скільки MИ витратили цього місяця за нашими підрахунками, з розбивкою» — не як «залишок на рахунку в Anthropic/OpenAI/ElevenLabs», бо останнє провайдери не віддають програмно.

### Що показуємо в v1 (дані вже є, лише UI/SQL-в'ю):
1. Витрачено цього місяця / ліміт / прогноз до кінця місяця (лінійна екстраполяція від денного темпу) — над існуючим треком 80/100/110 % з `docs/design/15-parent-budget-models.html`.
2. Розбивка по ролі (`indexing_structure`, `lesson_generation`, `passive_narration`, `voice_friend` тощо) і по провайдеру — сума `cost_usd` групована по `role`/`provider` за місяць.
3. Розбивка по уроку/сесії — `session_costs` в'ю по `session_id` (уже заплановано ADR-012, приміткою 2026-09-27).
4. Тренд по днях (спарклайн/графік) — `ai_calls.created_at` групований по днях за поточний місяць.
5. Хвилини живого голосу ElevenLabs: використано з пакета 275 хв / докупівля понад пакет (з `spend_months`/voice-лічильника, ADR-012).
6. Помилки/фолбеки — кількість `status='error'` і `fallback_used=true` за період (корисно й для налагодження, дешево показати, дані вже є).

### Що НЕ показуємо (без підтвердженої підтримки провайдера) і чому:
- «Поточний баланс рахунку в Anthropic/OpenAI» — не існує публічного API; показ довелось би або не робити, або підписувати недокументованим внутрішнім ендпоінтом OpenAI (ризик: зникне без попередження, вимагає org-рівня ключа з підвищеними правами — суперечить мінімізації секретів).
- «Платежі, що йдуть» / pending invoices — це concept способу оплати (картка), не концепт API використання; жоден з трьох провайдерів не публікує через API.
- Якщо Алекс все ж хоче наближену «скільки лишилось у пакеті ElevenLabs» — це можливо через `GET /v1/user/subscription` (символи/хвилини кварти, не гроші) як окрема невелика фіча, не частина основного бюджетного дашборда.

### Опційно, друга ітерація (не v1)
Щоденна фонова звірка `cost_report`/`costs` (Anthropic/OpenAI) проти власного `ai_calls`-обліку — виключно для перевірки точності оцінки (±10-15 %, вже згадано в наслідках ADR-012), не для показу Алексу в реальному часі. Вимагає:
- окремого Admin API key в Anthropic і org API key в OpenAI (нові секрети, `.env`, тільки сервер),
- фонового job (уже є механізм `pg_cron`/`jobs`, ADR-015) раз на добу,
- порівняльної таблиці «наша оцінка vs факт провайдера» — окремий невеликий екран, не для дитини й не терміновий.

## Оцінка обсягу для v1 (свій облік)

Помірна фіча звітності, що повністю перевикористовує наявні дані — не нова система збору даних:
- 1 SQL-в'ю (`session_costs`, group by `session_id`) + 1-2 запити-агрегатори (group by `role`/`provider`/день) — без нових таблиць, без нових прав RLS (уже є `ai_calls_select_parent`, `spend_months_select_parent`).
- Розширення вже спроєктованого макета `docs/design/15-parent-budget-models.html` (панелі розбивки, графік тренду) — дизайнерська й фронтенд-робота, не бекенд.
- Приблизно 1 короткий зріз бэклогу (кілька днів розробки + QA), не окремий спайк — оцінка орієнтовна, уточнить `product-manager`/`developer` у бэклозі.

## Альтернативи
| Варіант | Чому ні (для v1) |
|---|---|
| Живий баланс рахунку провайдера в дашборді | Не існує публічного API в жодного з трьох провайдерів (перевірено 2026-09-29) |
| Щоденна звірка через Admin/Cost API як основне джерело дашборда | Затримка, новий адмін-ключ з підвищеними правами на кожного провайдера, дублює вже надійний власний облік (той самий аргумент, що й в ADR-012 проти «опитування API витрат») |
| Показувати «оцінка ± похибка» без власного обліку | Гірше за те, що вже є: власний `ai_calls` точніший і миттєвий (ADR-012) |

## Наслідки
- Дашборд відповідає на «скільки я витратив і на що», не на «скільки лишилось у мене на рахунку в Anthropic» — очікування Алекса потребує калібрування саме в цей бік.
- Якщо провайдери колись відкриють ендпоінт балансу — легко додати як доповнення (не заміну) до наявного дашборда без переробки: власний облік лишається джерелом правди для бюджетного режиму (ADR-012), звірка — окремим, необов'язковим шаром.
- Ризик: недокументований OpenAI `credit_grants` може здатись спокусливим «швидким рішенням» — свідомо не використовуємо через нестабільність і потребу org-ключа.

## Відкриті питання до Алекса
1. Чи достатньо v1 «власний облік із розбивкою» (місяць/роль/провайдер/урок/тренд), чи важливо мати саме грошовий баланс рахунків провайдерів настільки, що варто витрачати час на недокументований API OpenAI (з ризиком, що він зникне)?
2. Чи потрібна вже в v1 щоденна звірка з Anthropic/OpenAI Cost API (друга ітерація вище), чи це можна відкласти після MVP?
3. Чи цікаво бачити відсоток використаної квоти ElevenLabs (символи/хвилини) окремим невеликим індикатором поруч із голосовим бюджетом?
