# ADR-031. Розширення джерел: DOCX, ручний імпорт готової структури, зображення/візуалізація в матеріалах і уроках

- **Статус:** запропоновано (2026-09-28) — дослідницький пакет `architect` за D-111 (п.2, п.3); п.1 (завантаження «не працює») — окремо, діагностична нотатка `docs/STATUS.md`, не ADR. **Частина 3 (2026-09-28, пізній вечір)** — готова до реалізації, PO надав реальні файли й хоче будувати негайно.
- **Вимоги:** D-110, D-111 (п.2, п.3); розширює E-2 (US-2.2, US-2.6, US-2.9); пов'язані ADR-008 (гібридний пошук/чанки), ADR-017 (модульний реєстр форматів/типів джерел), ADR-019 (модерація зображень — прецедент), ADR-020 (каталог ресурсів уроку, «модель дає лише ідентифікатор, ніколи саму картинку/код»), ADR-024 (Drive-конектор/синхронізація папки — перевикористовується для ZIP без змін механізму вибору файлу), ADR-029 (принцип «ніколи не приписувати мовчки», перевикористаний для QR/невідомого статусу), ADR-030 (`add_subject` RPC — перевикористовується для нових предметів `pryroda`/`zdorovia`)

## Контекст

PO 2026-09-28 (D-111): «(1) закачувати файли… (2) обробляти файли як мінімум декількох форматів; (3) вміти користуватись картинками та візуалізацією». Він же надав того ж вечора реальний приклад готового зовнішнього результату — `repetytor_6_klas_materialy.zip` (за описом задачі: `course_map.json` + маркдаун по параграфах + `pages.jsonl`, вихід стороннього інструмента з реальних підручників) — саме той матеріал, що вже підтвердив D-110 (наш поточний PDF-текстовий-шар гірший за очікування на двоколонковій верстці/поламаному кодуванні шрифту).

Поточний стан (перевірено кодом):
- `sourceExtractors` (`app/src/server/ingest/extractors.ts`) — реєстр формату → рядок «pdf» / «epub», кожен повертає уніфіковану `Extraction` (список `ExtractedUnit { page, locator, text }`) — саме той реєстр, що ADR-017 проєктував розширюваним («новий формат — новий рядок реєстру, конвеєр не змінюється»).
- Увесь конвеєр після екстракції (`chunkUnits`, `ingest.embed`, `ingest.structure`) працює **лише з текстом** `ExtractedUnit.text` — жодних зображень, QR-кодів, таблиць-як-зображень не зберігається і не передається структуруванню; це свідоме спрощення MVP (ADR-008), ніколи не переглядалось.
- `materials.format` має `check (format in ('pdf', 'epub'))` — жорстке обмеження на рівні БД, будь-який новий формат потребує міграції цього constraint.
- `ingest.structure` (`runStructure`) — один платний виклик LLM на книгу, що розпізнає розділи/теми/предмет/тип із уже вичавленого тексту сторінок (`buildOutline`). Це і є крок, що ламається на поганому вхідному тексті (D-110) — сам виклик не дорогий, дорога саме повторна спроба «полагодити» його точковими правками екстракції нескінченно.

## Частина 1. Формати файлів (п.2 запиту)

### Рішення: два незалежні доповнення, не одна фіча

**(А) DOCX — новий `SourceExtractor`, той самий конвеєр.**
- Бібліотека `mammoth` (MIT, чистий JS, вже стандарт для DOCX → HTML/текст у Node, не вимагає LibreOffice/системних залежностей на Vercel) конвертує `.docx` у текст із збереженням структури заголовків (`h1`…`h6`) через `convertToHtml`/власний `styleMap`.
- DOCX не має фіксованої пагінації (сторінки — артефакт друку/рендерера, не файлу) — на відміну від PDF, де `page` — точна, стабільна адреса для цитування. Рішення: як і EPUB (де `page` — номер розділу, а `locator` — назва розділу), для DOCX `ExtractedUnit.page` — порядковий номер розділу за заголовками верхнього рівня, `locator` — текст заголовка. Посилання дитині показує «розділ N, "Назва"» замість «сторінка N» — той самий патерн, що вже є для EPUB (`uk.parent.books` уже розрізняє «сторінка» / «розділ», зміни текстів не потрібні).
- `looksLikeScan`/OCR (D-54) не застосовується до DOCX — текстовий формат за визначенням, скану не буває.
- Обсяг: новий файл `extract-docx.ts` (~50–80 рядків, за зразком `extract-epub.ts`), рядок у `sourceExtractors`, розширення `check (format in (...))`, оновлення MIME-детекції (`formatOf` у `drive/google.ts` і `drive/upload.ts` — `application/vnd.openxmlformats-officedocument.wordprocessingml.document`), i18n «підтримувані формати». **Оцінка: ≈ 0,5–1 день розробника**, без нового провайдера, без нових коштів (сама екстракція без AI, як зараз у PDF/EPUB).
- Пріоритет DOCX: середній — корисний для власних/завантажених з інтернету матеріалів тата, але не вирішує D-110 (проблема не у форматі вхідного файлу, а в якості розпізнавання друкованого PDF).

**(Б) Ручний імпорт готової структури — найвигідніший, найдешевший і найнадійніший найближчий крок.**

Це **не** новий `SourceFormat` у сенсі «розпізнати байти файлу» — навпаки, весь сенс у тому, щоб **пропустити** і власну екстракцію тексту (`ingest.extract`), і платне структурування (`ingest.structure`) для матеріалу, який тато вже отримав готовим (зовнішній інструмент, чи власноруч підготований конспект). Це прямо знімає D-110 для будь-якого матеріалу, для якого в тата вже є чистий текст, а не перекладає нашу проблему розпізнавання на новий формат файлу.

**Прийнятий пакет (manual import package)** — ZIP-архів із трьома частинами, що навмисно **дуже близький** до вже наданого татом `repetytor_6_klas_materialy.zip` (менше тертя — «той самий файл, який у тебе вже є, з дрібним доповненням», а не новий незнайомий формат просити готувати):

```
manifest.json        # обов'язковий, нижче
pages.jsonl          # обов'язковий: по одному JSON-рядку на сторінку/розділ
sections/*.md        # необов'язкові: текст параграфа/розділу, якщо детальніший за pages.jsonl
```

`manifest.json` (нова, мінімальна схема — не обов'язково 1-в-1 з `course_map.json` тата, але легко мапиться конвертером на боці тата чи невеликим адаптером на нашому):
```json
{
  "title": "Історія України. Всесвітня історія, 6 клас",
  "subject_code": "history",
  "grade": 6,
  "sections": [
    { "title": "Розділ 1. Вступ до історії", "page_from": 6, "page_to": 24,
      "topics": [
        { "title": "§1. Лічба часу в історії", "page_from": 6, "page_to": 11 }
      ] }
  ]
}
```
`pages.jsonl`: `{"page": 6, "text": "..."}` на рядок (те саме, що `ExtractedUnit`, лише з диску тата, а не з нашого парсера).

**Мапування на існуючу схему (без нової таблиці для самого імпорту):**
1. Новий `materials.format = 'manual'` (розширення CHECK) — `drive_file_id` лишається (тато все одно кладе ZIP у Drive-папку «Мої книги»/«матеріали», той самий канонічний шлях зберігання, S1/S1b незмінний), `kind_manual = true`, `subject_manual = true` (тато вже вказав `subject_code` у маніфесті — жодного платного «вгадування», якщо код валідний).
2. **`ingest.extract` для формату `manual`** — новий, тривіальний `SourceExtractor`: розпаковує ZIP, валідує `manifest.json`/`pages.jsonl` (Zod-схема), повертає `ExtractedUnit[]` напряму з `pages.jsonl` — **без парсингу PDF, без AI, без `looksLikeScan`**. Той самий вихід `Extraction`, що і в PDF/EPUB → **решта конвеєра (`chunkUnits`, `ingest.embed`) не змінюється взагалі**.
3. **`ingest.structure` пропускається для `format = 'manual'`** — а не викликається з «підказкою» від маніфесту: секції/теми з `manifest.json` записуються напряму в `material_sections`/`topics` (той самий код `mergeByTitle`, який уже вміє зберігати ручні правки тата при повторному імпорті, — переюзаний, не новий) в окремій новій функції `applyManualStructure`, яка викликається одразу після `ingest.embed` замість `runStructure`. **$0 на структурування замість одного платного виклику LLM** — і, найважливіше, **нульовий ризик D-110** (структура вже готова й точна, а не вгадана моделлю з поганого тексту).
4. Валідація перед прийняттям: сума `page_from`/`page_to` секцій/тем повинна покривати діапазон сторінок `pages.jsonl` без різких розривів (м'яка перевірка — попередження в `status_detail`, не блокування, той самий дух, що вже є в `normalizeSections`); неоднозначні/биті рядки `pages.jsonl` (порожній `text`) — пропускаються з рахунком у `progress`, як порожні сторінки зараз.
5. Кабінет тата (`AddBookPanel`/«Мої книги»): той самий шлях «поклав файл у папку Drive → Перевірити папку» (US-2.7 КП-4) впізнає ZIP за наявністю `manifest.json` у корені й автоматично веде через `format = 'manual'` замість помилки «непідтримуваний тип» — тату **не треба** нічого обирати вручну, формат розпізнається вмістом архіву, як і зараз PDF/EPUB розпізнаються за MIME.

**Обсяг: ≈ 1,5–2 дні розробника** (Zod-схема маніфесту, розпакування ZIP — бібліотека `unzipit`/`fflate`, вже легка й без нативних залежностей, придатна для Vercel; `applyManualStructure`, розширення CHECK-констрейнтів, тести). **$0 нових поточних витрат** — навпаки, **економія**: жодного виклику `indexing_structure` для кожної такої книги (за прайсом ADR-005/`docs/03` ≈ $0.01–0.03/книга — малі гроші, але й малий ризик($0) при точному результаті куди цінніший за економію).

### Чому саме так, а не інакше
- Не будуємо «конвертер із будь-якого стороннього формату» — надто широко, невизначено, дорого підтримувати. Натомість фіксуємо **один простий, задокументований формат обміну**, під який тато (чи його зовнішній інструмент) підлаштовується один раз.
- Формат навмисно **дуже близький** до вже наданого зразка тата — мінімізує його додаткову роботу; якщо `course_map.json` тата не 1-в-1 збігається з `manifest.json` вище — потрібен лише маленький адаптер (ручний JS/Python-скрипт у тата чи невеликий `pages.jsonl`-конвертер із його інструменту), а не переписування нашої схеми під кожен зовнішній формат.
- Alternative «приймати сирий `course_map.json` тата 1-в-1» відкинуто: його README (за описом задачі) сам застерігає про двоколонкові сторінки й є форматом конкретного стороннього інструмента, не контрактом, який ми контролюємо, — тонка обгортка `manifest.json` навколо тієї самої ідеї дає нам стабільність за наступної версії його інструменту.

## Частина 2. Зображення та візуалізація (п.3 запиту) — дослідження й межі, не повна реалізація

### Що вже вирішено архітектурою і чому це важливо

ADR-020 **вже** закладає принцип для видимого дитині вмісту уроку: *«зображення/карти/схеми — лише з нашого каталогу ресурсів за ідентифікатором»* — модель ніколи не повертає саму картинку чи довільний URL, лише ключ із заздалегідь підготованого, довіреного каталогу. Це і є найважливіша рамка для п.3: **звідки береться зображення** (з підручника як є, з каталогу ресурсів застосунку, чи згенероване ШІ) визначає майже всю вартість і весь ризик безпеки нижче — і це продуктове рішення, не технічна деталь.

### (a) Витяг і зберігання зображень із джерела (PDF/EPUB)

Технічно нескладно й дешево:
- PDF: `pdf-lib`/`pdfjs-dist` (уже залежності проєкту — `extract-pdf.ts`, OCR-пайплайн) дають доступ до вбудованих зображень і растеризації сторінки цілком (рендер сторінки в PNG для QR-кодів/схем, вбудованих не як окремий об'єкт, а намальованих векторно).
- EPUB: зображення вже лежать окремими файлами всередині архіву (`.epub` = ZIP) — простіше за PDF, без растеризації.
- Зберігання: новий приватний бакет Supabase `material-images` (той самий патерн, що `tutor-avatars`, ADR-019), шлях `{material_id}/{page}_{n}.webp`, підписані посилання ≤ 10 хв за потреби показу; нова таблиця `material_images (id, material_id, page, section_id nullable, topic_id nullable, storage_path, width, height, caption_uk nullable, alt_text_uk nullable, created_at)`.
- Вартість: сховище — копійки (кілька МБ на книгу, Supabase Storage вже в тарифі `docs/03`); сам витяг — без виклику AI (растеризація/розпаковка — детерміновані, безкоштовні операції), якщо не потрібне розпізнавання змісту картинки (нижче).

### (b) Показ дитині в кроці уроку

Два різні шляхи, з дуже різною довірою:
1. **«Показати оригінальну ілюстрацію/схему підручника поруч із поясненням»** — крок `slide`/`step_reveal` отримує нове необов'язкове поле `visual.image_id`, що вказує на рядок `material_images` (не бере довільний URL — той самий принцип ADR-020: ідентифікатор із нашого каталогу, тут каталог = уже витягнуті й перевірені зображення конкретної книги тата). Практично корисно для географічних карт історії/природознавства, схем біології, ілюстрацій літератури — саме те, що PO, найімовірніше, має на увазі («картинки й візуалізація»), зважаючи на приклад із підручниками історії/літератури.
2. **«Модель генерує нову ілюстрацію»** — окремий, значно дорожчий і ризикованіший шлях (нижче, «Відкриті питання»).

### (c) Вартість і безпека — саме тут потрібне рішення PO, не здогад

| | Шлях (a)+(b)-1: відтворення оригіналу з підручника | Шлях (b)-2: ШІ генерує нову ілюстрацію |
|---|---|---|
| Вартість екстракції | $0 (детерміновано) | н/д |
| Вартість показу | $0 за показ (статичний файл) | ≈ $0.02–0.08/зображення (генерація), за кожен унікальний випадок — суттєво дорожче за поточний текстовий крок |
| Модерація/безпека | **Низький ризик** — зображення прийшло з підручника, який тато вже свідомо додав як джерело (та сама довіра, що вже є до тексту підручника, US-2.4/2.6); дитина 11 років, тато бачить додані книги. Автоматична модерація вмісту книг зараз відсутня і для тексту (той самий принцип, що ADR-019 п.9 для аватара — один користувач, тато контролює вхідні матеріали) | **Високий ризик** — модель без нагляду тата може згенерувати щось недоречне для дитячого інтерфейсу; за прецедентом ADR-019 (навіть для аватара, обраного самою дитиною, а не згенерованого «з нуля» системою, PO явно відмовився від автоматичної модерації, довірившись контролю тата — але там дитина сама обирає готову/свою картинку, тут модель САМА вирішувала б, що намалювати, без вибору дитини чи тата) — це якісно інша ситуація, що вимагає окремого рішення PO, не автоматичного поширення відмови від модерації ADR-019 на новий випадок |
| Відповідність NFR-SAFE | Узгоджується з наявним принципом «підручник — довірене джерело» | Потребує нового explicit рішення PO: чи прийнятна ШІ-генерація зображень для дитини **без** модерації/рецензії тата на кожне зображення (як ADR-019 для аватара) — чи навпаки, кожне згенероване зображення чекає на перегляд татом перед показом дитині (черга «на затвердження», за зразком «тато бачить кожну зміну аватара» ADR-019 п.4) |

### Відкриті питання до PO (не вирішуються тут — продуктовий вибір, не технічна деталь)

1. **Обсяг п.3 — що саме мається на увазі під «користуватись картинками та візуалізацією»?**
   - а) Показувати дитині оригінальні ілюстрації/схеми/карти з уже доданих підручників поруч із поясненням теми — дешево ($0 за показ), безпечно (довірене джерело), реалізовується найближчим зрізом як пряме продовження цього ADR.
   - б) Дозволити ШІ генерувати нові ілюстрації під час уроку (наприклад, власну схему до пояснення, якої немає в підручнику) — суттєво дорожче, вимагає окремого рішення про модерацію/рецензію тата, окремого ADR про вибір провайдера генерації зображень (новий тип витрат, нова роль у маршрутизаторі моделей).
   - в) Обидва, різними кроками (а — MVP, б — дорожня карта).
2. **Якщо (а) — чи достатньо статичного показу (зображення + підпис), чи потрібна інтерактивність** (наприклад, підписані ділянки карти — `diagram_hotspots`, уже в R2-плані ADR-020) **вже в першому зрізі, чи це окремий, пізніший крок?**
3. **Якщо (б) колись знадобиться — чи прийнятна для одної дитини 11 років (як і для тексту й аватара) відсутність автоматичної модерації згенерованих зображень за умови, що тато переглядає кожне перед показом** (черга «на затвердження»), **чи потрібна live-генерація без затримки на рецензію** (складніше й ризикованіше)?

**Рекомендація `architect`:** починати з (а) — технічно проста, дешева, безпечна, безпосередньо продовжує вже наданий татом приклад (підручники історії й літератури, де карти/ілюстрації — типовий і очікуваний вміст); (б) — окремий, явно новий ADR, коли/якщо PO підтвердить продуктову потребу саме в генерації нового візуального контенту, а не показі наявного.

## Частина 3. Пакетний ручний імпорт кількох предметів з одного ZIP (уточнення Частини 1(Б) під реальні файли, 2026-09-28 пізній вечір)

PO надав вночі два реальні ZIP-файли (не гіпотетичні) на своєму Google Drive і хоче зробити це сьогодні: обрати їх у застосунку, а потім однією командою розібрати й розкласти весь вміст по вже наявних шкільних предметах, з автоматичним визначенням приналежності. На відміну від Частини 1(Б) (один ZIP = один підручник, `manifest.json` у корені), реальні файли влаштовані інакше: **один ZIP містить одразу кілька предметних тек**. Цей розділ фіксує точний контракт під надану схему й уточнює механіку імпорту — не змінюючи жодного рішення Частини 1/2 вище.

### 3.1 Дві форми "ручного пакету" — розрізняються вмістом архіву, не вибором тата

(а) **Один підручник** — `manifest.json` у корені ZIP. Частина 1(Б) вище, без змін.

(б) **НОВЕ — пакетний імпорт**: у корені ZIP немає `manifest.json`, натомість кілька директорій верхнього рівня (реальні назви: `ukr_mova`, `ukr_literatura`, `zar_literatura`, `istoriia`, `geografiia`, `informatyka`, `pryroda`, `zdorovia`) плюс кореневий `README.md` (описовий, не парситься — лише для тата, хто читає ZIP вручну). Кожна тека містить:

```
<slug>/
  index.json               # обов'язковий — джерело правди для структури
  index.csv                # ігнорується імпортером: та сама інформація, що index.json, у CSV
  pages.jsonl               # обов'язковий — джерело правди для тексту сторінок
  lessons/*.md               # ігнорується імпортером: людяний рендер pages.jsonl+index.json, не нова інформація
  external_qr_topics.json    # необов'язковий (напр. ukr_mova) — та сама інформація, що вже є в status записів index.json; не читається окремо
```

Розпізнавання форми (а) чи (б) — за вмістом самого ZIP (наявність кореневого `manifest.json`), а не за вибором тата чи розширенням файлу — той самий принцип, що вже застосований для PDF/EPUB.

### 3.2 Точний контракт схеми (фіксується як наш формат обміну, за зразком тата)

`index.json` — масив записів:
```json
{ "id": "...", "section": "Розділ 1. ...", "title": "§3. ...", "printed_start": 18, "pdf_start": 22, "pdf_end": 24, "status": "text_in_pdf" }
```
`status` ∈ `text_in_pdf` (придатний текст) | `image_only` (скан без тексту — цей шлях імпорту НЕ застосовний) | `QR_external_check_pdf` (вміст параграфа посилається на зовнішній QR-матеріал, не є повним текстом у PDF).

`pages.jsonl` — один рядок на фізичну сторінку PDF: `{"pdf_page": 22, "printed_page": 18, "text": "..."}`.

### 3.3 Правила імпорту на рівні одного запису `index.json`

- `text_in_pdf` → імпортується як `topics`-рядок (3.5).
- `image_only`, **уся тека** (реальний випадок `geografiia`/`informatyka`) → **вся тека відхиляється** від цього шляху імпорту, жодного рядка `materials` не створюється; звіт тату: «ця тека — скановані сторінки без тексту, додайте оригінальний PDF окремо для розпізнавання (наявний OCR-конвеєр, D-54)». Півімпорт (структура без реального вмісту) свідомо заборонений — той самий принцип, що вже застосований у сесії до фабрикованого/порожнього вмісту (BUG-035/D-106): структура без тексту гірша за відсутність книги взагалі.
- `image_only`, **частина** записів теки (у реальних даних не спостережено, але можливий формат сторонього інструмента в майбутньому) → саме ці записи пропускаються (без теми, без чанків), решта теки імпортується нормально; лічильник «пропущено (скан)» у звіті.
- `QR_external_check_pdf` → запис **не** перетворюється на тему й на чанки взагалі (текст цього діапазону сторінок у `pages.jsonl` може бути посиланням на зовнішній матеріал, а не справжнім параграфом — імпортувати його як «текст підручника» означало б показати дитині щось хибно приписане джерелу, заборонено тим самим принципом NFR-LANG-3/ADR-029, що вже застосований у сесії до розпізнавання номерів завдань). Лічильник «потребує ручної перевірки (QR)» у звіті, з переліком назв/сторінок — тато бачить точно, що саме пропущено і чому, і може пізніше додати цей параграф вручну.
- Будь-який **незнайомий/новий** статус (майбутня версія стороннього інструмента тата) → трактується консервативно як «потребує ручної перевірки» (та сама група, що QR), **ніколи** не імпортується мовчки за замовчуванням як `text_in_pdf`.

### 3.4 Які сторінки `pages.jsonl` стають чанками

Лише сторінки, чий `pdf_page` потрапляє в діапазон `[pdf_start, pdf_end]` хоча б одного **імпортованого** (`text_in_pdf`) запису теки. Сторінки, що належать виключно відхиленим/пропущеним записам (image_only, QR, невідомий статус), у чанки не перетворюються — вони не засмічують пошук і не можуть бути помилково процитовані дитині як текст іншого, сусіднього параграфа.

### 3.5 Секції й теми з `index.json`

- `material_sections`: одна на унікальне значення `section` у теці (порядок — перша поява), `page_from`/`page_to` = min/max `pdf_start`/`pdf_end` серед своїх записів. Порожнє/відсутнє `section` → записи групуються у fallback-секцію «Без розділу» (той самий дух, що вже має `normalizeSections` для порожніх заголовків).
- `topics`: один рядок на кожен імпортований (`text_in_pdf`) запис; `title` = `entry.title`; `page_from`/`page_to` = `entry.pdf_start`/`entry.pdf_end` — **PDF-сторінки**, як і `chunks.page` (та сама конвенція, що вже усталена конвеєром: `page` — точна адреса в PDF-файлі, потрібна для `assign_chunk_structure`, який зіставляє `chunks.page` з діапазоном `topics.page_from/page_to`). `printed_start`/`printed_page` **не** йдуть у `page_from`/`page_to` — вони стають `chunks.locator` (людяна друкована сторінка, яку бачить дитина й тато в цитуванні — «стор. 18» замість технічного «PDF-сторінка 22»), той самий спосіб, що EPUB уже використовує `locator` для назви розділу замість номера сторінки.

### 3.6 Мапування на схему — нова колонка + перевикористання наявного коду

**Нова міграція** (одна, зворотно сумісна):
```sql
alter table public.materials
  add column if not exists source_subpath text not null default '';
alter table public.materials drop constraint if exists materials_owner_family_id_drive_file_id_key;
create unique index if not exists materials_owner_drive_subpath_uidx
  on public.materials (owner_family_id, drive_file_id, source_subpath)
  nulls not distinct;
```
Потрібна, бо один і той самий `drive_file_id` (сам ZIP) тепер породжує **кілька** рядків `materials` — по одному на предметну теку (`source_subpath` = назва теки, напр. `"ukr_mova"`; порожній рядок `''` — для звичайних PDF/EPUB і для одиночної книги Частини 1(Б), як і сьогодні).

**Один рядок `materials` на предметну теку**: `format='manual'`, `source_subpath=<slug>`, `drive_file_id=<id ZIP-файлу>`, `kind='textbook'`, `kind_manual=true` (тип відомий детерміновано — адаптований шкільний підручник, не вгаданий), `subject_id=<підтверджений татом предмет>`, `subject_manual=true`, `name` = `"<ім'я ZIP>/<slug>"`, `title` за замовчуванням = «<Назва предмета> — адаптовані матеріали» (тато редагує пізніше, як і будь-яку іншу книгу).

**Рефактор для розробника (не нова логіка, винесення наявної):** код злиття секцій/тем зі збереженням ручних правок (`mergeByTitle` + цикл insert/update/remove, сьогодні вбудований прямо в `runStructure`, `pipeline.ts` рядки ≈678–739) виноситься в окрему функцію `applyStructureRows(scope, familyId, materialId, sections: NormalizedSection[], meta: { subjectId, grade, curriculumVersion })`, яку викликають **обидва** шляхи:
- AI-шлях (`runStructure`): `answer → normalizeSections → applyStructureRows` — поведінка **не змінюється**, це чистий рефактор.
- Новий ручний шлях (`applyManualStructure`, і Частина 1(Б), і Частина 3): `manifest.json`/`index.json` → напряму в форму `NormalizedSection[]` (без жодного виклику AI, без `buildStructureSchema`) → та сама `applyStructureRows`.

`dependencies`/`related_topics`/`material_problems` (AI-специфічні поля `StructureAnswer`) для ручного шляху не застосовні — просто не викликаються; `assign_chunk_structure` (наявна RPC, без зміни) викликається так само, як і для AI-шляху.

**Чанки**: рядки `pages.jsonl` (відфільтровані за 3.4) → `ExtractedUnit[] { page: pdf_page, locator: printed_page != null ? String(printed_page) : null, text }` → `chunkUnits(units, DEFAULT_CHUNK_OPTIONS)` (той самий виклик, що й звичайний конвеєр) → та сама вставка в `chunks`, що вже робить `finishExtraction`. Далі — звичайний, без змін, `ingest.embed` (платний, копійки за книгу, ADR-008) і виклик `assign_chunk_structure`.

### 3.7 Визначення приналежності теки до предмета

Детермінована таблиця відомих слаґів → `subject_code` (константа в коді, не в БД):

| Слаг теки | `subject_code` | Є в `app/config/family-defaults.json` сьогодні? |
|---|---|---|
| `ukr_mova` | `ukrainian_language` | так |
| `ukr_literatura` | `ukrainian_literature` | так |
| `zar_literatura` | `foreign_literature` | так |
| `istoriia` | `history` | так |
| `geografiia` | `geography` | так (але тека `image_only` у реальних даних — відхиляється за 3.3 незалежно від мапи) |
| `informatyka` | — | **ні** (у списку 10 предметів «Інформатики» немає взагалі — лише заглушки «Мистецтво»/«Технології»; тека до того ж `image_only` — відхиляється за 3.3, мапа тут не знадобилась) |
| `pryroda` | — | **ні** — предмета «Природознавство»/«Пізнаємо природу» в сім'ї Алекса сьогодні не існує |
| `zdorovia` | — | **ні** — предмета «Здоров'я, безпека та добробут» сьогодні не існує |

**Важливий висновок, перевірений файлом, не здогад:** навіть без урахування `image_only`, для **двох** із шести текстових тек (`pryroda`, `zdorovia`) немає куди подіти вміст — предмета просто не існує. Екран підтвердження (нижче) мусить вміти не лише «підтвердити збіг», а й **створити новий предмет тут-таки**, інакше пакетний імпорт для цих двох тек неможливий у принципі.

**Екран підтвердження** (один раз, перед фактичним записом у БД) показує по одному рядку на теку:
- **Впевнений збіг** (слаг є в таблиці й предмет з таким `code` існує в сім'ї) → дропдаун з усіма `is_stub=false` предметами сім'ї, передвибраний на пропозицію; тато може змінити чи обрати «Не імпортувати цю теку».
- **Немає збігу** (слаг незнайомий, або є в мапі, але предмета з таким кодом ще нема — випадок `pryroda`/`zdorovia`) → дропдаун без передвибору + кнопка **«Створити новий предмет «‹назва›»»** (підказка назви — з невеликого allowlist-словника: `pryroda` → «Природознавство», `zdorovia` → «Здоров'я, безпека та добробут»; для зовсім незнайомого слага — назва теки як є, тато вводить свою), яка викликає вже наявний `add_subject` (ADR-030, `service_role`-only RPC через `requireParentAccess()`) прямо з цього екрана — **жодного нового RPC** для цього кроку.
- **`image_only` (уся тека)** → рядок одразу неактивний з поясненням (3.3), без дропдауна.

Тато підтверджує/редагує мапування одним екраном і натискає **«Імпортувати»** — це і є «одна команда» з його погляду (два кліки: «Розібрати архів» → перегляд/правка запропонованого → «Імпортувати»), а не автоматичне мовчазне приписування, яке заборонене прецедентом NFR-LANG-3/ADR-029 («ніколи не вгадувати неправильно й не приписувати мовчки»).

### 3.8 Як тато "обирає" ZIP і що саме запускає розбір

Перевірено кодом: в застосунку **немає** окремого файлового браузера Google Drive — `/parent/books/drive` (`AddBookPanel.tsx`) лише відкриває посилання на папку Google Drive тата в новій вкладці; сам вибір/додавання файлу відбувається в самому Google Drive UI, а застосунок лише сканує вже підключену папку (`syncDriveFolder`, ADR-024) і зіставляє MIME/розширення з підтримуваними форматами (`formatOf`, `drive/google.ts`). Для ZIP — **той самий шлях**, без винаходу нового способу «вибору» файлу: тато кладе ZIP у вже підключену папку («Мої книги» або папку матеріалів) і тисне наявну кнопку **«Я додав — перевірити папку»**.

Зміни в коді сканування:
- `formatOf`/`SUPPORTED_MIME` (`drive/google.ts`) отримують третій розпізнаваний формат — `zip`, за MIME (`application/zip`, `application/x-zip-compressed`) або розширенням `.zip` (той самий фолбек-патерн, що вже є для EPUB/octet-stream). `listFolderFiles`/`FolderFile.format` розширюється до `"pdf" | "epub" | "zip"`.
- На відміну від PDF/EPUB (1 файл = 1 рядок `materials`), ZIP не вставляється напряму в `materials` під час `syncDriveFolder` — один ZIP може стати 0 (жодної придатної теки), 1 (форма (а), одна книга) чи N рядків `materials` (форма (б), пакет). Тому — **нова легка таблиця** `manual_import_batches (id, owner_family_id, drive_file_id, name, drive_md5, status text check (status in ('pending_review','importing','done','error')), plan jsonb, created_at, updated_at)`; `syncDriveFolder` для `zip`-файлів лише вставляє/оновлює рядок цієї таблиці (RLS/грант — той самий патерн, що `materials`: `select`-only для тата, запис лише `service_role`), **не** запускає чергу індексації автоматично — розбір і мапування предметів потребують явного рішення тата, не фонового `pg_cron`.
- Новий job `ingest.manual_batch_preview` (негайний запуск, той самий патерн `kickJobs`, що ADR-024 §5): завантажує ZIP один раз, розпаковує в пам'яті (`fflate`/`unzipit`, уже узгоджені в Частині 1(Б); `unzipSync`-варіант із вибірковим фільтром файлів — не розпаковувати `lessons/*.md`/`index.csv`, вони не читаються імпортером узагалі, економія пам'яті/часу для великих ZIP), визначає форму (а)/(б) (3.1), для (б) — парсить кожен `index.json`, рахує статуси (3.3), підбирає мапу предмета (3.7), записує план у `manual_import_batches.plan` (jsonb), `status='pending_review'`. Кабінет тата (новий екран, наприклад `/parent/books/import/[batchId]` — конкретний макет вирішує `designer`) показує цей план і збирає підтверджене мапування.
- **Фактичний імпорт** — `POST /api/parent/books/manual-import/commit` (payload: `batchId`, і на кожну теку — `{ action: 'subject' | 'create_subject' | 'skip', subjectId?, newSubjectName? }`). Через чергу `ingest.manual_batch_commit` (той самий 300-секундний, resumable патерн, що решта конвеєра — до 8 тек в одному ZIP сумарно можуть перевищити безпечний час одного HTTP-запиту): для кожної підтвердженої теки — (за потреби) `add_subject`, вставка/оновлення рядка `materials` (`source_subpath`), вставка чанків (3.4/3.6), `applyManualStructure`/`applyStructureRows`, і чергування вже наявного `JOB.embed` (без нового worker-коду для цього кроку).
- Підсумковий звіт тату (одразу після коміту, і пізніше видимий у статусах створених `materials`): по кожній теці — «імпортовано» (N тем, M сторінок), «відхилено — скан без тексту, додайте оригінальний PDF для розпізнавання», «потребує ручної перевірки — K параграфів із QR-посиланням» (перелік назв), «пропущено — тато обрав «не імпортувати»».

### Ризики й припущення

1. Реальний розмір двох наданих ZIP не перевірений архітектором (файли лежать на Drive тата, недоступні цій сесії) — якщо `lessons/*.md`/`index.csv` суттєво роздувають архів, вибірковий розпаковувальний фільтр (вище) знижує цей ризик, не усуваючи його повністю; якщо після реалізації ZIP виявиться завеликим для одного job (>150 МБ, наявний `MAX_FILE_BYTES`), знадобиться той самий compromise, що вже є для великих сканів (ручне збільшення ліміту чи розбиття тატом ZIP на частини) — не вирішується наперед, фіксується як відомий ризик.
2. Запропоновані людські назви для нових предметів (`pryroda` → «Природознавство», `zdorovia` → «Здоров'я, безпека та добробут») — орієнтовні за програмою НУШ, підказка на екрані підтвердження, тато завжди може ввести іншу назву перед `add_subject`, вони ніколи не створюються без явного кліку тата.
3. Мапа слаг→код навмисно **невелика й статична** (лише 8 реальних значень + запасний `geografiia`), у коді, не в БД — новий сторонній ZIP з незнайомим слагом просто потрапляє у «немає збігу» (3.7), не в помилку; розширення мапи для майбутніх слагів — рядок коду, не міграція.

## Наслідки

- Розширення `materials.format` CHECK (`'pdf' | 'epub' | 'docx' | 'manual'`) — одна міграція, зворотно сумісна (нові значення, старі рядки не чіпаються).
- **(Частина 3)** нова колонка `materials.source_subpath` + заміна унікального індексу на `(owner_family_id, drive_file_id, source_subpath)` — одна зворотно сумісна міграція.
- **(Частина 3)** нова таблиця `manual_import_batches` (стан «ZIP очікує розбору/підтвердження/імпортується/готово»).
- **(Частина 3)** новий формат `zip` у `formatOf`/`SUPPORTED_MIME`/`listFolderFiles`/`FolderFile.format`.
- **(Частина 3)** рефактор `runStructure` → спільна `applyStructureRows` (перевикористовується AI- і ручним шляхом, без зміни поведінки AI-шляху) і нова `applyManualStructure` (обидві форми Частини 1(Б)/3, $0 AI-викликів).
- **(Частина 3)** два нові job: `ingest.manual_batch_preview` (розбір ZIP, підбір мапи предметів, без запису в `materials`) і `ingest.manual_batch_commit` (фактичний запис — по одному `materials`-рядку на підтверджену теку, чанки, структура, чергування `ingest.embed`).
- `sourceExtractors` отримує два нових ключі (`docx`, `manual`) — реєстр ADR-017 не змінює форму, конвеєр `ingest.extract → ingest.embed → ingest.structure` лишається на своєму місці для `docx`; для `manual` крок `ingest.structure` замінюється на новий, безоплатний `applyManualStructure` (та сама точка виклику в `pipeline.ts`, просто інша гілка за `format`).
- Нова таблиця `material_images` (частина (a) п.3) — потрібна незалежно від рішення по (б); саме зберігання зображень корисне навіть якщо PO обере «лише читати підручник», бо є передумовою для будь-якого майбутнього показу.
- Жодних нових зовнішніх акаунтів для DOCX і ручного імпорту; для зображень (шлях а) — жодних нових акаунтів, лише новий Storage-бакет (той самий проєкт Supabase); для шляху (б), якщо PO його обере, — новий провайдер генерації зображень і окремий ADR/оновлення `docs/03-resources-and-costs.md`.
- Ризик: формат `manifest.json`/`pages.jsonl` — наш власний контракт, не стандарт; якщо тато змінить зовнішній інструмент і той видасть інший формат — потрібен новий маленький адаптер (очікувано й прийнятно, дешевше за постійне патчення нашого PDF-парсера під кожне видавництво, що і є суттю D-110).

## Альтернативи

| Варіант | Чому ні (чи чому не зараз) |
|---|---|
| Одразу підтримати «будь-який» формат (RTF, ODT, HTML, звичайний .txt) | Розмиває зусилля без реального запиту PO на ці формати; DOCX і ручний імпорт закривають 95% реальних випадків тата (власні файли Word, готовий зовнішній результат) |
| Приймати сирий вивід стороннього інструмента (`course_map.json` тата) без власного `manifest.json`-контракту | Прив'язує нашу схему до формату чужого, неконтрольованого інструмента — крихко при його оновленні; тонка обгортка дешевша за довгострокову крихкість |
| LLM-«полагодження» поганого PDF-тексту замість ручного імпорту (дорожчий шлях, який сам PO випадково продемонстрував через зовнішній інструмент, D-110) | Саме та альтернатива, яку D-110 вже порівняв і відкинув як дорожчу за наш поточний підхід — ручний імпорт готового результату дешевший і надійніший, ніж імітувати роботу зовнішнього інструмента всередині нашого пайплайну |
| Одразу дозволити ШІ-генерацію ілюстрацій в уроці | Реальний, ще не підтверджений PO ризик і кошт (модерація дитячого візуального контенту); передчасно без явного рішення (див. відкриті питання) |
| Розпізнавання змісту зображень vision-моделлю для кожної картинки підручника (щоб агент міг «описати» картинку в голосовому уроці) | Не запитано явно PO; коштує додаткового виклику vision-моделі за кожне зображення (~$0.001–0.01) без підтвердженої потреби — почати з простого показу (а), додати опис лише якщо зʼявиться конкретний сценарій, що цього вимагає |
| **(Частина 3)** Один ZIP → один рядок `materials`, теки конкатенувати в один «псевдопідручник» | Ламає предметну модель («один предмет = один `subject_id`» на рядку `materials`) — довелося б вигадувати мульти-предметний рядок і множинну структуру всередині нього; окремий рядок на теку простіше, узгоджено з наявною схемою, і дає окремий, зрозумілий статус/звіт на кожен предмет |
| **(Частина 3)** Мовчки пропускати теки без відповідного предмета (`pryroda`, `zdorovia`) замість пропозиції створити новий | Прямо суперечить NFR-LANG-3/прецеденту ADR-029 («ніколи не вгадувати неправильно й не приховувати мовчки») — тато явно хотів «розкласти по предметах», а не «розкласти по тому, що вже є, решту тихо викинути»; додати сам предмет — один клік через уже наявний `add_subject` |
| **(Частина 3)** Розпаковувати весь ZIP і йти прямо в `materials` без окремого екрана підтвердження («повна автоматика») | Для 4 із 8 тек мапа однозначна, але для 2 предмета взагалі не існує (потрібне рішення тата), а 2 інші — скан без тексту (потрібне явне відхилення, не мовчазне створення порожньої структури) — «повна автоматика» неможлива без порушення принципу «ніколи не приписувати мовчки», лишається легкий двокроковий («Розібрати» → «Імпортувати») екран |
