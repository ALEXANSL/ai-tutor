# ADR-015. Фонові задачі: таблиця `jobs` у Postgres + `pg_cron`/`pg_net` замість окремої черги

- **Статус:** запропоновано (2026-09-25)
- **Вимоги:** A-P3 (без черг), US-2.2, 11.1, 11.2, 11.7 КП-3, 18.1, NFR-PERF-7

## Контекст
Потрібні: індексація підручників (хвилини), озвучка, ембединги повідомлень, щоденний/тижневий звіт (п'ятниця 18:00), архів 1-го числа 02:00–06:00, повтори сповіщень (3 за 5 хв), перевірка нових файлів у Drive. Vercel Hobby дозволяє cron лише раз на добу з неточністю в межах години.

## Рішення
- Таблиця **`jobs`** (`type`, `payload`, `status`, `attempts`, `run_after`, `locked_until`, `dedupe_key`).
- **`pg_cron`** у Supabase щохвилини викликає через **`pg_net`** захищений маршрут `/api/jobs/tick` (заголовок з `CRON_SECRET`). Обробник бере задачі з `FOR UPDATE SKIP LOCKED`, виконує в межах ~250 с, решту лишає на наступний тик.
- Розклади (тижневий звіт, архів, щоденна перевірка Drive) — окремі записи `pg_cron`, що створюють задачі (час за Europe/Kyiv).
- Термінові сповіщення **не чекають тику**: перша спроба — одразу в запиті (`after()`), тик лише для повторів.
- Довгі задачі діляться на кроки (напр., індексація: витяг → ембединги пакетами → структура).

## Наслідки
- $0; усе видно в одній базі (статуси задач — у кабінеті для помилок індексації/архіву).

## Примітка (S1, 2026-09-25)
`pg_cron`/`pg_net` — **необов'язкові** для роботи задач, не лише для демо. Задачі рухаються трьома
способами, які не потребують щохвилинного `pg_cron`: (1) `after()` одразу після дії тата запускає
тик у тому самому запиті; (2) поки відкрито сторінку з активною задачею (напр. «Мої книги» під час
індексації), клієнт опитує сервер і кожен виклик підштовхує чергу (`kickJobs()`); (3) щоденний
**Vercel Cron** (`/api/jobs/tick?sync=1`, Hobby, раз на добу) — підстраховка, якщо сторінку ніхто не
тримав відкритою. `pg_cron` лишається бажаним покращенням (секундна затримка для задач без відкритої
сторінки) і вмикається окремим кроком Алекса, коли буде потрібно.
