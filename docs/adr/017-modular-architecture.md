# ADR-017. Модульна архітектура: предмети, джерела матеріалів, навчальні модулі

- **Статус:** запропоновано (2026-09-25) — за стратегічним рішенням Алекса «модульність як ключовий принцип»
- **Вимоги:** NFR-PLAT-4, AR-17, US-2.1…2.5, US-3.4; розширює ADR-016
- **Пов'язані:** ADR-007 (оркестратор), ADR-004 (маршрутизатор), ADR-014 (бібліотека), ADR-018 (комерціалізація)

## Контекст
Алекс хоче, щоб застосунок ріс «модулями» без переробки ядра:
1. **нові предмети** (зараз 8 шкільних + заглушки);
2. **будь-які книги** з Drive (PDF/EPUB), не лише підручники: художні твори, довідники, робочі зошити, «просто цікаві книги»;
3. **навчальні модулі** поза шкільною програмою: «Додаткове навчання» (напр., програмування з практикою коду), модуль іспитів (R3).

Обмеження: MVP не повинен ускладнитися. Закладаємо лише **точки підключення** (місця з'єднання), а не самі модулі.

## Рішення

### Ядро (не змінюється при додаванні модулів)
`auth`, `router` (моделі, бюджет), `safety` (модерація — **завжди**, для будь-якого модуля), `orchestrator` (автомат сесії), `library` (кроки й озвучка), `knowledge` (карта знань), `chat`, `voice`, `jobs`, `notify`, `reports`. Модуль **не може** обійти модерацію, бюджет і облік: усі ШІ-виклики йдуть лише через `callModel(role, …)`.

### (а) Предмет = дані, а не код
- `subjects` отримує поле `config jsonb`: мова уроку (`uk` / двомовний `uk+en` / `uk+de`), дозволені типи кроків, профіль оцінювання (напр., «точна відповідь» для математики, «рубрика» для літератури), чи потрібна діагностика, голос агента (мовний режим).
- Промпти: загальний шаблон ролі + **необов'язковий** оверрайд `prompts/subjects/<code>/<role>.md`. Нема оверрайду — працює загальний.
- **Додати предмет** = рядок у `subjects` (з кабінету тата або міграцією) + файли в папці Drive. Код не змінюється.

### (б) Джерела матеріалів: універсальний конвеєр індексації
Один конвеєр `fetch → extract → chunk → embed → structure` (розд. 9.1 `docs/02`) з двома точками підключення:

| Точка | Інтерфейс | MVP | Потім (без зміни ядра) |
|---|---|---|---|
| **Формат** | `SourceExtractor` (`pdf`, `epub`) → сторінки/розділи з текстом і позицією | PDF (unpdf), EPUB | DOCX, Google Docs, OCR сканів (роль `vision_ocr`) |
| **Тип джерела** | `StructureStrategy` за `materials.kind` | `textbook` → розділи → теми → сторінки → залежності; `literary_work` → розділи/глави, без графа тем | `reference` / `general_book` → лише зміст і фрагменти для пошуку й цитат; `workbook` → вправи як кандидати в `library_steps` |

- `materials.kind` розширюється значеннями `workbook`, `reference`, `general_book` (MVP використовує `textbook`, `literary_work`, `test_fragment`); `materials.subject_id` — **необов'язковий** (книга може не належати предмету); `materials.format` (`pdf`/`epub`).
- Тип визначає ШІ під час індексації, тато може змінити в кабінеті (як US-2.5 КП-2).
- Чанки й ембединги однакові для всіх типів → пошук, цитування джерела й RAG працюють для будь-якої книги автоматично.
- **Підпапки Drive** (напр., `Математика/`, `Книги/`) — лише підказка для `subject_id`/`kind`, не обов'язкова структура.

### (в) Навчальні модулі
**Модуль** — пакет коду в `app/src/modules/<code>/`, який реєструється в ядрі й додає лише те, чого бракує:

| Що може додати модуль | Як підключається | Приклад |
|---|---|---|
| Режими сесії | обробник режиму в реєстрі оркестратора (`registerMode`) | `exam_prep`, `code_practice` |
| Типи кроків | запис у реєстрі кроків: клієнтський компонент + серверний `evaluator` | `code`, `mock_test_question` |
| Інтерактивні компоненти уроку | папка в реєстрі компонентів (Zod-схема, React-компонент, `evaluate`, `promptDoc`) — ADR-020 | `number_line`, `map` |
| ШІ-ролі | рядки `model_routes` з префіксом (`exam.planner`, `code.reviewer`) | — |
| Власні таблиці | окрема міграція з префіксом (`exam_*`, `code_*`), з `family_id` і RLS (ADR-018) | `exam_assessments` |
| Пункт меню / екран | реєстр навігації | «Додаткове навчання» |

**Що закладаємо в MVP (мінімум, ≈ 1 день роботи розробника):**
1. Таблиця `learning_modules` (`code`, `enabled`, `config jsonb`); у MVP один рядок `school` (шкільна програма). Тато вмикає/вимикає модулі в кабінеті (коли вони з'являться).
2. Колонка `module_code` (за замовчуванням `'school'`) у `lesson_sessions`, `library_items`, `chats`, `knowledge_state` — щоб звіти, пошук і облік витрат розрізняли модулі.
3. Реєстри в коді замість `switch`: режими оркестратора, типи кроків (`library_steps.type` + `evaluator`), типи джерел (`StructureStrategy`). Шкільний функціонал MVP — просто перші записи в цих реєстрах.
4. `model_routes.role` — рядок, а не enum БД (нові ролі без міграції схеми).

**Що свідомо НЕ робимо в MVP:** плагінів із завантаженням коду, окремих сервісів на модуль, конструктора модулів у UI, модуля програмування і модуля іспитів як таких.

### Модуль «Додаткове навчання: програмування» — як безпечно виконувати код дитини (на майбутнє)
Принцип: **код дитини ніколи не виконується на нашому сервері** (там ключі й дані).

| Варіант | Як | Безпека | Вартість | Коли |
|---|---|---|---|---|
| **1. У браузері планшета (рекомендовано першим)** | Python — **Pyodide** (WebAssembly) у **Web Worker**; JavaScript — у Web Worker / `iframe sandbox` без `allow-same-origin`; для молодшого віку — блоки (Blockly) | Код ізольований пісочницею браузера, без доступу до мережі (CSP `connect-src 'none'` у воркері), cookies і даних застосунку; таймаут — `worker.terminate()` через N секунд; ліміт виводу | **$0** | Старт модуля. Працює і офлайн |
| 2. Керована хмарна пісочниця | мікро-ВМ провайдера (напр., Vercel Sandbox, E2B, Judge0) через наш сервер: код → пісочниця → результат | Ізоляція на рівні ВМ, без секретів усередині, мережа вимкнена | оплата за секунди виконання; ціни перевірити при потребі | Лише якщо знадобляться інші мови, пакети, файли |
| 3. Власний контейнер на сервері | Docker/gVisor | Найбільше ризиків і адміністрування | — | **Не обираємо** (A-P3) |

Оцінювання: `evaluator` типу кроку `code` запускає тести в тій самій пісочниці (варіант 1 — у браузері, результат тестів надсилається на сервер), а ШІ-роль `code.reviewer` отримує код + результати тестів і пояснює помилки українською. Код і вивід дитини проходять модерацію як звичайний текст.

### Модуль іспитів (R3) — у цій схемі
Режим `exam_prep` + таблиця `exam_assessments` + `library_items.kind='mock_test'` (ADR-016); використовує карту знань і граф тем ядра без змін.

## Альтернативи
| Варіант | Чому ні |
|---|---|
| Нічого не закладати | Кожен новий модуль вимагав би правок оркестратора, схеми й звітів («розмазані» `if`) — саме те, чого Алекс хоче уникнути |
| Повноцінна плагін-система / мікросервіси на модуль | Передчасне ускладнення для 1 дитини (A-P3); реєстри в одному коді дають ту саму розширюваність |
| Окремий конвеєр індексації для кожного типу книги | Дублювання; один конвеєр зі стратегіями простіший |

## Наслідки
- MVP: +1 таблиця, +1 колонка в 4 таблицях, +2 поля (`subjects.config`, `materials.format`), 3 реєстри в коді. На вартість не впливає.
- Нові предмети й книги — без програміста (дані + папка Drive); нові модулі — робота програміста, але без переробки ядра.
- Ризик: реєстри можуть «розростися» без дисципліни → правило для `developer`: модуль імпортує ядро, ядро **не** імпортує модулі (лише через реєстр).
