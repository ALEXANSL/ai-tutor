# ADR-027. Голосова ВІДПОВІДЬ дитини (STT, «як у ChatGPT») — без живого діалогу

- **Статус:** запропоновано (2026-09-27) — рішення про запуск у поточному зрізі й вибір провайдера-фаворита (з двох рекомендованих) за PO
- **Вимоги:** D-97/D-98 (`docs/01-requirements.md`, розд. 12.21) — PO затвердив реалізацію простішого варіанту (STT → текст) як наступний пріоритетний крок, з явним підтвердженням, що повний живий голосовий діалог (ADR-006/D-57) лишається кінцевою метою для майбутнього зрізу S12/S13; NFR-VOICE-4, NFR-PRIV-1, NFR-PRIV-2 (мінімізація даних дитини)
- **Пов'язано:** ADR-025 (пасивна озвучка TTS — симетрична функція на виході; той самий стиль дослідження й той самий принцип «спершу вже підключені провайдери»), ADR-006 (жива розмова, S12/S13, кінцева мета), ADR-004 (маршрутизатор моделей — провайдер-адаптери)

## Контекст

TTS-озвучка (ADR-025, роль `passive_narration`) щойно запрацювала й підтверджена робочою. PO одразу запитав про зворотний напрям — голосову ВІДПОВІДЬ дитини на кроці уроку («чи можна, як у ChatGPT?»). Оркестратор одразу розділив запит на два різні за складністю рішення:

- **(а) проста одноразова голосова відповідь** — дитина записує репліку, сервер розпізнає її в текст (STT), текст іде в уже наявне текстове поле відповіді. Без живого з'єднання, без переривань, без Agents/WebRTC.
- **(б) повноцінна жива розмова** (переривання, миттєва реакція) — це вже задокументований і свідомо відкладений напрям (ADR-006/D-57, OpenAI Realtime API/ElevenLabs Agents/Gemini Live, окремий зріз S12/S13).

**D-98:** PO підтвердив — почати з (а) зараз; (б) залишається кінцевою метою «без обмежень, у рамках бюджетних лімітів», не факультативною ідеєю. Отже, план (а) має бути спроєктований так, щоб **не суперечити й не дублювати** роботу, яка знадобиться для (б) — компонент запису звуку в браузері й досвід «дитина говорить» мають бути перевикористовні.

**Де саме в інтерфейсі.** Єдине місце в поточному коді, де дитина вводить відкриту текстову відповідь — крок `step.type === "open"` в `app/src/components/lesson/LessonRunner.tsx` (текстове поле `<textarea>` + кнопка «Відповісти», що веде у вже наявний `submitStepAnswerAction` → `answer_evaluation`). Мікрофон додається **поруч** із цим полем, а не замість нього — дитина завжди може або говорити, або друкувати.

**Схема вже частково готова.** `step_attempts.channel` (`docs/02` розд. 8.2) уже має enum-значення `voice` — воно ще ніде не використовувалось (жоден наявний канал відповіді його не встановлює), саме для цього випадку: голосова відповідь, розпізнана в текст, позначається `channel = 'voice'`. **Схема БД не змінюється.**

**Висновок дослідження:** обидва вже підключені провайдери (OpenAI, Gemini) мають придатний шлях для розпізнавання короткої дитячої репліки; жодного нового акаунта, ключа чи рахунку не потрібно — **той самий принцип, що і в ADR-025** («спершу вже підключене, новий постачальник — лише якщо жодного немає»). Вартість в обох варіантах — **частки центів за одну відповідь** (типова відповідь дитини на крок уроку ≈ 5–20 с) — на порядок дешевше за будь-яку іншу статтю кошторису.

## Рішення

1. **Новий, окремий провайдер ролі `stt_answer`** у `model_routes` (за зразком `passive_narration`, розд. 7.4a ADR-025) — **не** заміна й не залежність від `voice_agent`/ADR-006. Основний провайдер — **OpenAI `gpt-4o-mini-transcribe`** (найдешевший, ключ уже є, офіційно підтверджена українська через базову модель Whisper); запасний/резервний — **Gemini `gemini-3.8-flash`** через уже наявний мультимодальний шлях (той самий провайдер і той самий виклик, що вже возить фото зошита, `vision_notebook`) — той самий принцип «резерв — інший провайдер» (US-13.1 КП-2), що й для решти ролей уроку.
2. **Роутер моделей (ADR-004):** новий тип провайдер-адаптера `transcribe` в `ProviderAdapters` (`app/src/server/ai/router.ts`), дзеркальний до вже наявного `audio` (TTS): `{ model, audioBase64/Blob, mimeType, params } → { text, usage }`. Нова функція `callTranscribe("stt_answer", { audio, mimeType }, ctx)`, аналогічна `callAudio`.
3. **Технічна реалізація запису в браузері (нова інфраструктура, з нуля):** у проєкті наразі немає жодного коду запису звуку (`MediaRecorder`, `getUserMedia`) — це очікувано, бо жива розмова (ADR-006) ще не реалізована. Новий клієнтський компонент **`VoiceAnswerRecorder`** (кнопка мікрофона поруч із `<textarea>` кроку `open` у `LessonRunner.tsx`):
   - `navigator.mediaDevices.getUserMedia({ audio: true })` → `MediaRecorder` (формат `audio/webm;codecs=opus` — підтримується Chrome на цільовому планшеті, Lenovo Yoga 11, розд. 7.4 плану спайку S13);
   - **жорсткий ліміт тривалості 60 с** (авто-стоп + м'яке повідомлення «Час вийшов, спробуй ще раз коротше» — той самий ліміт мовчання/сесії, що вже використовується для живого голосу, розд. 7.4, для узгодженості відчуття); дитина може зупинити раніше кнопкою «Стоп»;
   - індикатор запису (пульсуюче кільце навколо кнопки, таймер) — навмисно **той самий візуальний патерн**, що вже спроєктовано для `state: listening` у `SpeechBus`/`TutorPresenter` (розд. 7.6.5), щоб не створювати другий, несумісний стиль індикації голосу перед S12/S13;
   - по стопу — `Blob` одним запитом (`multipart/form-data`, без стрімінгу) на новий серверний маршрут `POST /api/lesson/voice-answer` з `sessionId`, `stepId`, `idempotencyKey` (той самий `idempotency_key`, що вже йде з кожною відповіддю кроку, розд. 5.2 — захищає від дублю при повторній відправці);
   - сервер: перевірка бюджету й ролі (як для `passive_narration`) → `callTranscribe("stt_answer", …)` → повертає `{ text }` → **аудіо-буфер ніде не записується на диск/у Storage — обробляється в пам'яті процесу й одразу відкидається** (розд. «Безпека/приватність» нижче);
   - клієнт підставляє розпізнаний текст у **те саме** поле `openAnswer` (той самий стан компонента, що і для друкованої відповіді) — дитина бачить текст, може виправити вручну чи натиснути «Відповісти» одразу; **далі — без жодної зміни** в `submitStepAnswerAction`/`answer_evaluation`/`safety_moderator` (розд. 5.1, `practice`-крок уже сьогодні прописаний як «відповідь: вибір/текст/голос/фото → оцінка», розд. 5.1 таблиця режимів);
   - `step_attempts.channel = 'voice'` встановлюється для цієї відповіді (готове enum-значення, розд. 8.2) — відрізняє від `text`/`choice`/`photo` в аналітиці (E-21, D-90/D-91) без жодної нової колонки;
   - **відмова/збій STT** (провайдер недоступний, розпізнаний текст порожній, бюджет `hard_stop`) → та сама м'яка деградація, що і в ADR-025 для TTS: поле лишається порожнім/незмінним, дитина продовжує друкувати — **жодного нового блокуючого стану**, немає регресії наявного текстового шляху.
4. **Безпека мовлення дитини не послаблюється:** розпізнаний текст проходить **той самий** `safety_moderator`, що й будь-яка інша репліка на кроці `practice` (розд. 5.1 таблиця режимів уже сьогодні описує «`safety_moderator` на кожну репліку» незалежно від каналу — голосова відповідь тут не виняток, лише новий спосіб отримати текст).
5. **Явний зв'язок і межа з S12/S13 (ADR-006, D-57):** ця функція **навмисно не будує** жодного «живого» стану (черга реплік, переривання, WebRTC, client tools) — лише «запис → один HTTP-запит → текст». Компонент запису (`VoiceAnswerRecorder`, `MediaRecorder`-обгортка, індикатор рівня сигналу) спроєктовано як **точку повторного використання**: коли S12/S13 реалізує живий діалог, потік аудіо з мікрофона піде тим самим низькорівневим шляхом захоплення звуку (той самий `getUserMedia`, той самий рівень гучності на `SpeechBus`), лише замість «записати → відправити один файл» стане «стрімити в WebRTC-з'єднання ElevenLabs». **Немає дубльованої роботи**, яку довелося б викинути при переході до живого голосу — S12/S13 додає новий транспорт (WebRTC) поверх уже освоєного дозволу мікрофона й UI-патерну, а не переписує його.

|---|---|

| Одразу робити живу розмову (ADR-006/S12/S13) замість простого STT | Прямо суперечить D-98 PO: «починаємо з простішого... але плануємо реалтайм» — послідовність явно визначена |
| Стрімити аудіо шматками (замість одного файлу після стопу) | Ускладнення без вигоди для короткої (≤ 60 с) репліки на кроці уроку; стрімінг має сенс лише для живого діалогу (S12/S13), де важлива затримка «кінець репліки → відповідь» |
| Зберігати аудіофайл відповіді в Storage (як для живого голосу, ADR-006) | Зайвий привілей доступу й зайва стаття сховища заради функції, де вже сьогодні достатньо тексту (той самий текст, що дитина набрала б); суперечить принципу мінімізації дитячих даних (розд. «Безпека/приватність») |

## Наслідки

- Новий тип провайдер-адаптера `transcribe` у `router.ts` (аналог `audio`), нова роль `stt_answer` у `model_routes` (сидить окремо у seed-міграції, як і `passive_narration`); без нових таблиць і колонок (`step_attempts.channel` уже має `voice`).
- Новий клієнтський компонент `VoiceAnswerRecorder` і серверний маршрут `POST /api/lesson/voice-answer`; `Permissions-Policy` для мікрофона на екрані уроку вже передбачена (розд. 8.3) — лише перевірити, що дозвіл поширюється і на цей крок, не тільки на майбутній живий голос.
- Оцінка вартості — `docs/03-resources-and-costs.md` розд. 2.2.3 (нова стаття, ≈ $0,05–0,30/міс при щоденному використанні — на порядок менше за будь-яку іншу статтю кошторису, у межах наявного бюджету $100 без коригувань).
- **Рекомендація з приватності:** аудіо голосової відповіді **не зберігається** — обробляється в пам'яті сервера й відразу відкидається після отримання транскрипту; зберігається лише сам транскрипт (як частина `step_attempts.answer`), так само, як зберігався б друкований текст. Це **суворіше**, ніж уже прийнятий підхід для живого голосу (ADR-006 зберігає аудіо розмови до архіву) — виправдано тим, що тут немає потреби в аудіо-доказі для розбору тривожної події в реальному часі (модерація вже спрацьовує на транскрипті синхронно, до показу результату дитині) і немає технічної залежності від аудіо після розпізнавання.
- **Winning-провайдер визначається коротким внутрішнім тестом** (аналог методики спайку S13, розд. 7.4 `docs/02`): 10–15 записаних реплік доньки українською (за згодою тата, ті самі умови, що вже узгоджені для S13) прогнати через `gpt-4o-mini-transcribe` і `gemini-3.8-flash`, порівняти WER на слух/вручну, обрати основний/резервний остаточно; **тестові записи видаляються одразу після порівняння**, у продукт не потрапляють.

**Відкриті питання до PO:**
1. Чи запускати цю функцію в поточному зрізі одразу (розробник має все необхідне — жодних нових акаунтів), чи прив'язати до конкретного номера зрізу в беклозі (рішення `product-manager`/PO при плануванні)?
2. Ліміт тривалості запису **60 с за замовчуванням** (як у пропозиції вище) — влаштовує, чи потрібне інше число (аналогічно до вже узгодженого 60 с тиші для живого голосу, розд. 7.4)?
3. Чи достатньо MVP-рекомендації «аудіо не зберігається взагалі» (розд. «Наслідки») — чи PO хоче короткого (напр. 24–48 год) технічного кешу аудіо на період перших тижнів використання для ручної перевірки якості розпізнавання (вимикається пізніше)? Архітектор рекомендує **не зберігати** навіть тимчасово (простіше, менше поверхні ризику), але це рішення PO, не блокує розробку.
