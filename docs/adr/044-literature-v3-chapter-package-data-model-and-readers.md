# ADR-044. Пакети уроків v2.0.0 «текст твору + квіз»: модель даних `literature_v3_*`, переглядач `flow[]`, позиція читання, віртуальна книга (AR-29 пп.1, 3, 4, 5)

- **Статус:** прийнято
- **Вимоги:** E-31 (US-31.1…31.3, `docs/01-requirements.md` §6), S45 (`docs/05-backlog.md`), AR-29 (§11.2); довідковий `schema/INTEGRATION.md` пакета v2.0.0 (наданий PO для аналізу, поза репозиторієм — прочитано, не виконано жодного коду з нього)
- **Пов'язані:** ADR-043 (спільний інтерфейс «активний урок» — відкладена уніфікація); S35-міграція `20261017100000_s35_math_course_v2.sql` (`course_v2_*` — буквально реюзується для квізів); S36-міграція `20261020100000_s36_literature_course_v2.sql` (`literature_v2_*` — паралельна, НЕ зачіпається); `docs/02-architecture.md` розд. 18

## Контекст

PO самостійно підготував (через власний ЖПТ-проєкт) значно повніший пакет для «Українська література, 6 клас»: `flow[]` — явна впорядкована послідовність кроків (`screen`/`biography`/`reading`/`quiz`), новий файл `readings.json` з повними/чесно позначеними скороченими текстами 37 творів, 214 посторінкових фрагментів і 26 біографій, завдання `single_choice` замість відкритих, об'єктні (не масиви) `assets.json`/`task_tables.json`, і малий (~5 стор.) PDF на кожен урок (`lesson_pdf`) з власним `page_map`. AR-29 вимагає: (1) модель даних, (2) див. ADR-043, (3) чи новий компонент перегляду чи розширення наявного, (4) дизайн «віртуальної книги» зі склеєних малих PDF (ідея PO 2026-10-14), (5) оцінка обсягу сховища.

## Рішення

### 1. Модель даних — нове сімейство `literature_v3_*`

Назва: **не** `literature_v2_*` (уже зайнято іншим, активним, паралельним пакетом S36 з принципово іншим контрактом завдань — відкриті, а не `single_choice`) і не буквально «v2.0.0» (номер версії пакета ≠ номер версії нашого внутрішнього сімейства таблиць — та сама плутанина, якої вдалося уникнути іменуванням S35 `course_v2_*` для пакета, що сам себе так не називав). `literature_v3_*` — наступне число в уже заведеній послідовності (`literature_lessons` → `literature_v2_*` → `literature_v3_*`).

Нові таблиці (повний опис і причини — `docs/02-architecture.md` §18.1):

- `literature_v3_packages`, `literature_v3_lessons` (з `flow jsonb` — упорядкований масив `{kind, ref_id}}`, той самий патерн, що вже є для `screen_ids`/`task_ids` в інших сімействах, без окремої таблиці для самого `flow`), `literature_v3_screens`, `literature_v3_works`, `literature_v3_reading_items`, `literature_v3_biographies`, `literature_v3_assets` (ілюстрації + `lesson_pdf` з `page_map`), `literature_v3_pages` (зворотний індекс сторінка→асет, основа §4 нижче).
- `catalog/task_tables.json` — завжди порожній у цій версії пакета; таблиця для нього НЕ створюється.

**Квізи — буквальний реюз `course_v2_questions`/`course_v2_question_keys`/`course_v2_quizzes`/`course_v2_quiz_items` (S35), не нова таблиця.** Додаткова, зворотно сумісна колонка на вже живих таблицях:

```sql
alter table public.course_v2_questions
  alter column lesson_id drop not null,
  add column literature_v3_lesson_id uuid references public.literature_v3_lessons (id) on delete cascade,
  add constraint course_v2_questions_exactly_one_lesson check (num_nonnulls(lesson_id, literature_v3_lesson_id) = 1);
-- той самий патерн для course_v2_quizzes; course_v2_question_keys/quiz_items/question_attempts — БЕЗ ЗМІН
-- (прив'язані до question_id/quiz_id, не напряму до таблиці уроку)
```

RLS `*_select_child`-політики `course_v2_questions`/`course_v2_quizzes` отримують додаткову `or exists (... literature_v3_lessons ... status = 'active')`-гілку. Жодної зміни в `course_v2_question_keys` (і далі жодної `select`-політики нікому — лише service-role, той самий принцип безпеки). `submitQuestionAnswerAction` — без зміни коду (приймає лише `questionId`).

**TTS-кеш** — `course_v2_narration_cache` уже спроєктований generic (`ref_table`+`ref_id`+`field`, без FK — власний коментар міграції S35) — реюзиться literature_v3-таблицями без жодної зміни схеми.

**Позиція читання (US-31.2 КП-2)** — нове nullable поле `lesson_sessions.reading_position jsonb` (`{kind, ref_id, offset_codepoints}`), не нова таблиця, не `localStorage`. За `docs/00-product-brief.md` дитина користується одним пристроєм («режим тата» — PIN на тому самому планшеті, не окремий пристрій) — отже класичний аргумент «потрібна синхронізація між пристроями» тут не застосовний; рішення на боці БД усе одно обране, бо воно продовжує вже дану гарантію «Продовжити» (US-6.5, NFR-RES-1/3), яку кожен інший крок уроку вже має через серверний стан сесії — вибіркова `localStorage`-реалізація лише для читання порушила б цю гарантію непослідовно (втрата позиції при очищенні кешу браузера). Зсув — у Unicode-код-поінтах `tts.text` (пряма вимога `INTEGRATION.md`), не в JS `string.length`/`substring`-індексі (UTF-16 code units) — явно позначено для `developer`.

### 2. Спільний інтерфейс «активний урок» — див. ADR-043 (відкладена схемна уніфікація, хелпер зараз)

### 3. Переглядач `flow[]` — новий компонент, не розширення наявного

**`LiteratureV3LessonView.tsx`** (`app/src/components/course-v2/`, та сама конвенція «один компонент перегляду на сімейство пакета», що вже є для `LiteratureV2LessonView.tsx`/`MathCourseV2LessonView.tsx`). Не розширення `LiteratureV2LessonView.tsx`: та модель — лінійна «екрани → завдання», а `flow[]` — явна послідовність РІЗНОТИПНИХ кроків у довільному, визначеному пакетом порядку; підлаштування наявного компонента означало б розгалуження майже кожної його функції за прапорцем формату.

Перевикористовується буквально:
- **`QuestionCard`** — сьогодні приватний компонент усередині `MathCourseV2LessonView.tsx`; виноситься у спільний файл (`app/src/components/course-v2/QuestionCard.tsx`), бо квізи `literature_v3` — буквально рядки `course_v2_questions` (§1) — жодної нової розмітки квізу.
- Навігаційний каркас уроку (US-6.16) і хуки голос/текст, авто-прогрес — ті самі, що вже є в `MathCourseV2LessonView.tsx`.

Нове: рендерер `flow[]`, що вибирає підкомпонент за `kind` — наявний `ScreenStep`-патерн, новий `BiographyStep` (пасивний, не оцінюється), новий `ReadingStep` (текст твору, play/pause/«Повторити», пише `reading_position` при паузі/виході), і спільний `QuestionCard` для `quiz`. Поля `explanation`/`definitions`/`worked_example` з `course.json` **не рендеряться** цим переглядачем (пряма вимога `INTEGRATION.md` — уже представлені в `flow`).

### 4. «Віртуальна книга» зі склеєних per-lesson PDF — новий компонент, нова колонка page-mapping

Два шляхи «подивитись підручник» лишаються окремими (PO-ідея 2026-10-14, дослівно збережена):

- **«Відкрити весь підручник»** (з екрана предмета) — наявний `BookReader.tsx` + `/api/book/[materialId]/file` (Drive, Range-стрімінг PR #79) — **без змін**.
- **«📖 Подивитись у підручнику»** (з кроку уроку v2.0.0) — новий **`VirtualBookReader.tsx`** + новий роут `app/src/app/api/book/lesson-pdf/[assetId]/file/route.ts` (стрімить `literature_v3_assets.storage_path` напряму з приватного Supabase Storage) — **нуль звернень до Drive**.

Чому новий компонент, а не проп на `BookReader.tsx`: внутрішня модель `BookReader.tsx` зав'язана на ОДИН документ (`pdfDocCache` по одному `materialId`, пошук — по одному `/api/book/[materialId]/search`, межі сторінок — від одного `pageCount`); підміна на список документів зачепила б майже кожну внутрішню функцію й змішала б у одному пропі дві різні серверні підсистеми (Drive-проксі проти Storage-проксі).

Перевикористовується буквально: низькорівнева, уже кілька разів виправлена pdf.js-логіка `BookReader.tsx` (кеш документа по ключу, `cleanup()` попередньої сторінки, скасування рендеру в льоту) виноситься у спільний модуль **`app/src/components/child/pdfEngine.ts`**; `BookReader.tsx` переходить на нього без зміни поведінки, `VirtualBookReader.tsx` використовує той самий модуль для кожного маленького PDF.

Механіка: серверний компонент сторінки уроку передає `VirtualBookReader` пре-фетчений page-index з `literature_v3_pages` (`{absolute_page, asset_id, bundle_pdf_page}}`, SSR-пропс-патерн, як і `initialPageCount` у `BookReader.tsx`). Кнопка відкриває одразу потрібний маленький PDF (через `page_bundle_asset_id` кроку); гортання за межу поточного шматка шукає сусідній `asset_id` у page-index і лінивого довантажує його документ (той самий кеш-патерн, ключ тепер `assetId`) — дитина бачить лише безперервні «Назад»/«Далі».

Пошук по тексту в цій історії **не реалізується** (поза обсягом US-31.3 — лише пряме відкриття на потрібній сторінці); лишається привілеєм шляху «Відкрити весь підручник».

### 5. Обсяг сховища

≈40–55 МБ на типовий предмет (46 × ~800 КБ `lesson_pdf` ≈ 37 МБ + ілюстрації ≈5–14 МБ + текст/jsonb ≈1–2 МБ, не бінарники). У межах `MAX_COURSE_ZIP_BYTES`/`course_import_staging`-ліміту (300 МБ, запас ×6–7) і сукупного Supabase Storage (Pro, 100 ГБ) — **жодної зміни лімітів не потрібно**. Деталі — `docs/02-architecture.md` §18.5.

## Що НЕ змінюється (успадковано без змін)

- `lesson_review`/`content_qa` (ADR-022/ADR-034) не застосовні — увесь контент оригінальний, не згенерований ШІ.
- Нуль нових рядків `model_routes` — нуль ШІ-викликів на імпорт/показ.
- `literature_v2_*` (S36, зарубіжна література) — не зачіпається жодною мірою (ВП-78, D-127: лишається як є, без міграції на новий формат).

## Наслідки/ризики

- **Регресійний ризик додаткової колонки на живій `course_v2_questions`/`course_v2_quizzes`** (AR-R24, `docs/02-architecture.md` §16): міграція — лише `add column`+`check`, без зміни існуючих рядків; обов'язковий regression-прогін наявних автотестів `math-course-v2` перед закриттям зрізу.
- Нова таблиця `literature_v3_pages` і колонка `page_map` на `literature_v3_assets` — єдина нова інфраструктура, специфічна для §4 (віртуальна книга); решта — максимальний реюз наявного.

## Уточнення 2026-10-21: спільний контракт і необов'язкові медіа

На пряме доручення PO нові предмети використовують чинний chapter-package контракт. Назви таблиць `literature_v3_*` залишаються внутрішніми; нового сімейства таблиць на кожний предмет не створюємо. Маніфест `subject-tutor-package` підходить усім предметам, наявні `<subject>-tutor-package` зберігають сумісність.

У формі імпорту обов'язкові лише package/course/readings/teacher JSON. Відсутні assets/pages/task_tables трактуються як порожні каталоги. Два ZIP необов'язкові: ілюстрації/повний пакет і окремі PDF-уроки. Основне зіставлення — точний шлях із каталогу; для PDF допускаються `lessons`/`lesson_pdfs` та коренева назва в окремому PDF ZIP лише за однозначної назви. Неоднозначні архіви відхиляються.

Повторний імпорт без бінарної заміни зберігає старий файл, його фактичні hash/size/type та карту PDF. Завантажені PDF з власною картою сторінок мають пріоритет над новим зворотним індексом, щоб текстовий повторний імпорт не переозначив сторінки збережених байтів. Бінарні заміни записуються за шляхом із SHA256; старий об'єкт не перезаписується. Текстовий імпорт без медіа лишається робочим, невирішені посилання на файли явно показуються батькові.

Канонічний промпт генерації та приклади: [`app/public/content-package-prompt.md`](../../app/public/content-package-prompt.md), доступні в батьківській формі імпорту. Контракт квізу наразі `single_choice`; розширення на нові види завдань потребує окремої реалізації, а не вигаданої структури пакета.
