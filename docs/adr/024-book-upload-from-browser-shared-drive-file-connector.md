# ADR-024. Завантаження книги з комп'ютера — спільний OAuth `drive.file`-конектор для архіву й нової папки завантажень

- **Статус:** запропоновано (2026-09-26)
- **Вимоги:** US-2.6, US-2.7 КП-5 (PM-20), D-41, D-47, NFR-PRIV-7; пов'язані ADR-003 (доступ до Drive), ADR-013 (медіа й архів), ADR-015 (фонові задачі), ADR-023 (негайний запуск задачі)

## Контекст

PO вночі поставив питання: чи можна дати татові завантажити файл підручника **прямо з браузера кабінету** («Мої книги»), а застосунок сам покладе цей файл на Google Drive і пропустить через наявний конвеєр індексації (S1/S1b), а не лише збереже в Supabase Storage.

Це питання вже частково передбачене вимогами: `docs/01-requirements.md` PM-20 позначає «Завантаження файлу прямо з кабінету в папку» як **Could**, за умови, що `architect` підтвердить — це **не розширює доступи застосунку до Drive тата**. Наявний MVP-шлях («Мої книги», S1) — панель з кнопками «Відкрити папку в Google Drive» → «Я додав — перевірити папку» (`AddBookPanel.tsx`), без прямого вивантаження.

Окремо, `docs/02-architecture.md` розд. 10.2/ADR-003 уже планує **OAuth `drive.file` тата** — але поки що лише для запису щомісячного архіву (ADR-013, зріз S17, ще **не реалізовано** — станом на `docs/STATUS.md` код дійшов лише до S4-S5). Google Cloud OAuth consent screen для скоупу `drive.file` **вже налаштований** у чеклісті (`docs/03-resources-and-costs.md` розд. 1.5, крок 4) — окремого узгодження в консолі Google не потрібно.

Обмеження Google (ті самі, що в ADR-003):
- сервісний акаунт (сьогоднішній читач папки матеріалів) не має квоти сховища й не може писати в особистий «Мій диск» — розширювати його права до запису неможливо технічно;
- `drive.file` — не чутливий скоуп, але покриває **лише** файли/папки, **створені самим застосунком** (або явно вибрані користувачем через Google Picker) — токен `drive.file`, виданий татом, **не** автоматично отримує доступ до наявної папки матеріалів `GOOGLE_DRIVE_FOLDER_ID`, бо той доступ сервісний акаунт отримав через ручне «Поділитися» в Drive UI, поза OAuth-згодою застосунку.

## Рішення

1. **Не розширюємо** доступ сервісного акаунта (лишається read-only на `GOOGLE_DRIVE_FOLDER_ID`, без змін).
2. **Один спільний OAuth `drive.file`-конектор** («Підключити Google Drive», один клік і один consent-екран тата) обслуговує **дві** мети: (а) архів (ADR-013, зріз S17) і (б) нова приватна папка **«ШІ-Репетитор — Мої книги»** — обидві **створює сам застосунок** у «Мій диск» тата, тому доступні під `drive.file` без Google Picker і без жодної додаткової згоди. Практично — конектор із S17 виконується раніше й трохи ширше (створює одразу дві папки замість однієї), а не окремою повторною авторизацією.
3. Одразу після створення папки завантажень застосунок тим самим OAuth-токеном (тато — власник новоствореної папки, може нею ділитися) викликає Drive API `permissions.create()`, надаючи read-доступ сервісному акаунту `ai-tutor-drive-reader` на цю нову папку — **програмно**, без ручного кроку «Поділитися» від тата.
4. Синхронізація/індексація (`docs/02-architecture.md` розд. 9.1) розширюється на **два** `folder_id` замість одного: наявна `GOOGLE_DRIVE_FOLDER_ID` (як і зараз — «Перевірити папку») і нова `GOOGLE_DRIVE_UPLOADS_FOLDER_ID` — конвеєр `ingest.extract → ingest.embed → ingest.structure` **не змінюється**.
5. Оскільки сервер сам щойно створив файл через Drive API у відповідь на завантаження з браузера, він уже знає `drive_file_id`/`name`/`mime`/`modified_time` з відповіді `files.create` — рядок `materials` вставляється й `ingest.extract` ставиться в чергу з **негайним запуском** (`kickJobs()`, той самий патерн, що вже є для «холодного» відкриття теми, ADR-015/023), не чекаючи ні наступного ручного «Перевірити папку», ні щохвилинного `pg_cron`.
6. **Практичний ліміт прямого вивантаження з браузера — ≈ 50 МБ** (нижче за `MAX_FILE_BYTES = 150 МБ`, який захищає лише завантаження **з** Drive під час індексації, BUG-003) — через обмеження розміру тіла запиту й тривалості serverless-функцій Vercel при подвійному транзиті клієнт → Vercel → Drive. Ендпойнт вивантаження **стрімить** тіло напряму в Drive (resumable upload), рахуючи байти на льоту — той самий інженерний патерн, що вже виправив BUG-003, застосований у зворотному напрямку — і відмовляє одразу після перевищення ліміту, не буферизуючи весь файл у пам'яті функції.
7. Файли, що не влазять у 50 МБ (скани у високій роздільності), лишаються на наявному шляху «покласти в папку Drive вручну» (без цього ліміту, лише `MAX_FILE_BYTES=150 МБ` на боці індексації) — панель «Додати книгу» показує **обидва** варіанти: нову кнопку «Завантажити файл» як зручний варіант за замовчуванням і наявний «Відкрити папку в Google Drive» для великих/масових випадків.
8. Файл зберігається **лише на Drive**, без дублювання в Supabase Storage — на відміну від D-67/ADR-013 (де генерований медіаконтент і чати живуть насамперед у Storage, а Drive — лише щомісячна архів-копія). Конвеєр S1/S1b і так вважає Drive канонічним джерелом підручника (`materials.drive_file_id`); файли, завантажені з браузера, не мають ставати винятком.
9. Сервер валідує MIME (лише PDF/EPUB), розмір і що цільова папка створення — саме `GOOGLE_DRIVE_UPLOADS_FOLDER_ID` (захист від помилкового запису в чужу папку/«confused deputy»); перевірка публічності нової папки — той самий механізм, що вже є для архіву (ADR-003 10.2): будь-який дозвіл `anyone` → застереження/блокування.

## Альтернативи

| Варіант | Чому ні |
|---|---|
| Писати прямо в наявну папку матеріалів `GOOGLE_DRIVE_FOLDER_ID` через `drive.file` + Google Picker (тато один раз обирає саму папку в Picker) | Технічно можливо, але це **додатковий** консент-крок понад звичайну OAuth-згоду («оберіть ту саму папку в іншому вікні») — ADR-003 вже відхилив подібний UX («Picker для кожного підручника») як незручний; одноразовий вибір папки менш незручний, але все ще зайвий і плутає («навіщо вибирати папку, яку я і так відкрив у Drive») порівняно з варіантом без Picker узагалі |
| Зберігати файл лише в Supabase Storage, без Drive | Не виконує пряме побажання PO «застосунок сам кладе файл на Google Drive»; розриває конвеєр S1/S1b, що очікує `drive_file_id`; довелося б переробляти `downloadFile`/ingest на два джерела книги |
| Дублювати і в Storage, і в Drive (як D-67 для медіа) | Зайве сховище й ризик розбіжності версій; книги — не генерований медіаконтент сесій, для якого важливий швидкий підписаний доступ з чату; Drive і так канонічне джерело з S1 |
| Розширити доступ сервісного акаунта до запису | Неможливо технічно — сервісні акаунти не мають квоти сховища в особистому «Мій диск» (ADR-003) |
| Просити тата авторизувати чутливий скоуп `drive`/`drive.readonly` для запису будь-де | Потребує перевірки застосунку Google (verification) — довше й складніше, ніж потрібно (той самий висновок, що й ADR-003) |
| Дозволити вивантаження без практичного ліміту (аж до 150 МБ) через браузер | Ризик таймауту/OOM serverless-функції при подвійному транзиті клієнт→сервер→Drive на типовому домашньому каналі; для рідкісних великих файлів наявний ручний шлях без цього ліміту й так є |

## Наслідки

- Новий env `GOOGLE_DRIVE_UPLOADS_FOLDER_ID` (за зразком `GOOGLE_DRIVE_ARCHIVE_FOLDER_ID`); розширення `integration_status` статусом підключення й публічності нової папки.
- Один OAuth-консент тата покриває і архів (S17), і завантаження книг — тому цю можливість варто реалізувати **раніше** за повний S17 (взяти з майбутнього S17 лише сам конектор і виклик `permissions.create`, без місячного архівного циклу — архівний cron лишається окремим, пізнішим шматком S17).
- Середній за розміром зріз розробки (≈ 4–5 днів): спільний OAuth-конектор, автостворення й автоshare нової папки, стрімінговий upload-ендпойнт з практичним лімітом і індикатором прогресу, кнопка «Завантажити файл» в `AddBookPanel`, тести (стрімінг великого файлу без буферизації — за аналогією з `drive.test.ts` BUG-003).
- Жодної нової фази «погодження акаунтів» від тата — Google Cloud консоль уже налаштована (розд. 1.5 `docs/03`); лише один клік «Підключити Google Drive» в самому застосунку, коли фіча буде готова.
- **Відкриті питання до PO** (див. фінальний звіт архітектора): (1) чи прийнятний практичний ліміт ≈50 МБ для прямого завантаження, чи важливіше зняти цей ліміт ціною ризику таймауту для рідкісних великих сканів; (2) чи варто зробити цю фічу окремим найближчим зрізом (позаплановим, поза S27/S28) — і хто (product-manager) додасть її в `docs/05-backlog.md`; (3) чи влаштовує назва нової папки «ШІ-Репетитор — Мої книги» (видима тату в його «Мій диск»).
