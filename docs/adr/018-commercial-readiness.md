# ADR-018. Готовність до можливої комерціалізації: що закладаємо зараз, що відкладаємо

- **Статус:** запропоновано (2026-09-25) — за стратегічним рішенням Алекса «можлива комерціалізація в майбутньому»
- **Вимоги:** D-21 (інші користувачі), NFR-PRIV-4 (RLS), NFR-PLAT-4
- **Пов'язані:** ADR-001 (стек), ADR-002 (вхід), ADR-012 (облік витрат), ADR-017 (модульність)

## Контекст
Зараз — одна сім'я (тато + донька). Можливо, пізніше — продукт для інших сімей. Треба відрізнити:
- **дешеве зараз і дуже дороге потім** (закладаємо в MVP);
- **дороге зараз і не потрібне для однієї сім'ї** (свідомо відкладаємо).

Найдорожча переробка в SaaS — додати «сім'ю-орендаря» (tenant) у вже заповнену базу і переписати всі правила доступу. Тому цей шов закладаємо одразу.

## Рішення — закладаємо в MVP (оцінка: +0,5–1 день розробника, $0 на місяць)
| # | Що | Як |
|---|---|---|
| К-1 | **Сім'я як орендар** | Таблиця `families` (`id`, `created_at`, `timezone` = `Europe/Kyiv`, `locale` = `uk`); колонка **`family_id` (NOT NULL, індекс)** у всіх таблицях з даними сім'ї (користувачі, профіль, сесії, чати, повідомлення, карта знань, звіти, бали, витрати, медіа, налаштування, `jobs`). У MVP — один рядок `families`. |
| К-2 | **RLS за сім'єю** | Функції `app_family_id()` і `app_role()` за `auth.uid()`; кожна політика: `family_id = app_family_id() AND <правило ролі>`. Серверні маршрути з `service_role` **завжди** фільтрують за `family_id` поточного користувача (хелпер `forFamily(ctx)`), автотест `qa-tester`: «дані іншої сім'ї невидимі». |
| К-3 | **Спільний vs сімейний контент** | Навчальний контент (`subjects`, `topics`, `library_items`, `library_steps`, `audio_assets`) має `owner_family_id` **nullable**: `null` = спільний, інакше — сімейний. У MVP усе сімейне. Бібліотека без персональних даних (ADR-014) — потенційно найцінніший спільний актив. |
| К-4 | **Конфігурація замість хардкоду** | Ліміти, тривалості, пороги, моделі, ціни, предмети, модулі, регіон тривог, часовий пояс — у БД (`parent_settings`, `child_profile`, `model_routes`, `model_prices`, `subjects.config`, `learning_modules`), а не в коді. Більшість уже так (розд. 6, 8 `docs/02`). |
| К-5 | **Інтеграції через функцію, а не прямо з env** | ID папок Drive, Telegram, e-mail сповіщень у MVP лежать у змінних середовища (чекліст `docs/03` не змінюється), але код читає їх **лише** через `getFamilyIntegration(familyId, kind)`. Для SaaS реалізація переходить на таблицю + Supabase Vault без змін у решті коду. |
| К-6 | **Облік витрат по сім'ї** | `ai_calls.family_id`, `spend_months` з ключем (`family_id`, `month`) — основа для тарифів і рахунків у майбутньому. |
| К-7 | **Тексти інтерфейсу — у словнику** | Усі рядки UI — в одному файлі `uk` (без мультимовної бібліотеки на старті); промпти — у `prompts/` з версіями. Переклад потім — без пошуку рядків по коду. |
| К-8 | **Вхід — у БД, не лише allowlist** | Allowlist з env лишається «воротами» в MVP, але зв'язок «користувач → сім'я → роль» зберігається в `app_users` (`family_id`, `role`). Для SaaS allowlist замінюється запрошеннями без зміни схеми. |

## Свідомо відкладаємо (до окремого рішення про комерціалізацію)
| Що | Чому відкладаємо / що знадобиться |
|---|---|
| Оплати, тарифи, підписки (Stripe тощо) | Не потрібні одній сім'ї; облік по `family_id` уже є |
| Самостійна реєстрація, онбординг сімей, адмін-панель | Для однієї сім'ї — allowlist |
| **Тарифи провайдерів для комерції** | **Vercel Hobby — лише некомерційне використання** → Vercel Pro; Resend безкоштовний відправник — лише на адресу власника → власний домен; перевірка OAuth-застосунку Google (брендинг) |
| Юридичне: політика приватності, згода батьків, обробка даних дітей (законодавство України, GDPR для ЄС), договори обробки даних з провайдерами ШІ | Обов'язково **до** першого чужого користувача; зараз дані лише власної сім'ї |
| **Авторські права на підручники й книги** | Спільна бібліотека уроків, згенерована з чужих підручників, може потребувати ліцензій — окреме юридичне питання; тому в MVP контент сімейний (К-3) |
| Масштабування (черги, окремі воркери, кеш) | `jobs` + `pg_cron` вистачить на десятки сімей; переглянути при зростанні |
| Мультимовність UI і промптів | Словник (К-7) робить це дешевим пізніше |

## Альтернативи
| Варіант | Чому ні |
|---|---|
| Не закладати `family_id` | Економія ≈ пів дня зараз; при комерціалізації — міграція всіх таблиць, переписування всіх RLS-політик і аудит кожного запиту (тижні + ризик витоку даних між сім'ями) |
| Окрема база/проєкт Supabase на кожну сім'ю | Ізоляція сильніша, але дорого ($25+/міс на сім'ю) і складно в оновленнях; можливо лише для великих клієнтів |
| Одразу повна SaaS-архітектура | Передчасно (A-P3); жодної користі для доньки |

## Наслідки
- Кожна нова таблиця (включно з модулями ADR-017) — з `family_id` і RLS за шаблоном; це правило в `docs/02` розд. 8.3.
- Невелике ускладнення запитів (додатковий фільтр) — компенсується хелпером і тестом.
- Рішення про комерціалізацію в майбутньому потребуватиме окремої фази (юридичне, тарифи, оплати), але **не** переробки ядра й моделі даних.
