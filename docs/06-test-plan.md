## Дослідницьке тестування — деталі

### Allowlist і ролі (`allowlist.ts`, `session.ts`)
- Порожній allowlist → `not_configured`, а не «доступ дозволено». ✅ (код + `resolveRole` логіка)
- Один e-mail в обох списках (`ALLOWLIST_PARENT_EMAILS` і `ALLOWLIST_CHILD_EMAILS`) → `ambiguous`,
  доступ відхилено (не типова помилка, свідомий захист від помилки конфігурації). ✅ рев'ю коду.
- Зміна ролі в env (e-mail переїхав зі списку дитини в список тата) → на наступному запиті
  `resolveRole` поверне нову роль, але `app_users.role` у БД лишиться старою → `session.ts`
  трактує це як `unregistered` (не автоескалація) → `register_app_user` при наступному вході
  оновить роль. Поведінка безпечна (немає миттєвої непроконтрольованої ескалації в межах
  активної сесії), але **не перевірено e2e** (потребує реальної БД зі зміненим станом) — 👁.

### PIN і блокування
- Формат: приймає 4–6 цифр, відхиляє менше/більше, нечислові символи, `null`, число замість
  рядка. ✅ `pin.test.ts`.
- 5 неправильних поспіль → блокування на 15 хв, лічильник скидається після успіху. ✅.
- PIN-хеш не читається через API навіть роллю «тато» (column-level grant без `pin_hash`). ✅
  `rls.test.ts`.
- Cookie `parent_mode` підписана й прив'язана до конкретного пристрою (`device_id`) і дитини
  (`uid`/`fam`) — підміна токена з іншого пристрою/сім'ї не пройде перевірку підпису чи
  прив'язки. ✅ рев'ю `parent-mode-token.ts` (HMAC-SHA256, `timingSafeEqual`).

### Валідація нікнейму й імені репетитора (`validation.ts`, `validation.test.ts`)
Перевірено дуже широкий набір обходів, усі проходять коректно:
- Латиниця замість кирилиці (омогліфи `a/в/с/е/н/і/к/м/о/р/т/х/у`) → `мaмa` розпізнається як
  «мама». ✅
- Пробіли (кілька поспіль, на краях) → нормалізуються. ✅
- Емодзі → рахуються як 1 символ (Unicode code point), а не байти. ✅
- Дуже довгі рядки → `too_long` (> 20 code points), окремо перевірено, що обрізання не ламає
  підрахунок для суто емодзі-нікнейму. ✅
- Посилання/@ у нікнеймі → відхилено (кілька доменних зон, `www.`, голий домен). ✅
- Довгі цифрові послідовності (у т.ч. розділені пробілами/дефісами — номер телефону) →
  відхилено; до 4 цифр поспіль — дозволено (дати типу «2026»). ✅
- Спорідненість і «найкращий друг» — і як окреме слово, і як частина фрази, і не хибно
  спрацьовує на підрядку («Тамара», «Мамай», «Братислава» — приймаються). ✅
- Ім'я репетитора = нікнейм (без урахування регістру/пробілів) → відхилено. ✅

**Не покрито тестом (низький пріоритет, шкоди дитині немає):** нікнейм повністю з керуючих/
невидимих Unicode-символів (напр. лише RTL-override) — фільтр `\p{Cc}\p{Cf}` це ловить, але
немає явного тесту; рекомендація — додати 1-2 кейси в `validation.test.ts`, коли буде час
(не блокує реліз, тому в `docs/bugs/` не заведено).

  середовища в текстах для тата (на відміну від `PIN_PEPPER`, де для тата в
  «Налаштуваннях» саме ім'я змінної доречне й потрібне для дії — контекст різний, обидва
  підходи узгоджені з принципом «не розкривати значення»). ✅ рев'ю `i18n/uk.ts`.

### Великий файл без `Content-Length` (BUG-003, регресія)
- `readBounded()` читає `res.body.getReader()` чанками з накопичувальним лічильником
  байтів; щойно `total > MAX_FILE_BYTES` — `reader.cancel()` і кидається `DriveError(...,
  "too_large")` **до** того, як увесь файл потрапив у пам'ять; для відповідей без `body`
  (деякі тестові мок-`fetch`) — фолбек на буферизоване читання з тим самим пост-чеком
  розміру. ✅ `drive.test.ts` («BUG-003: aborts a streamed download…» — симулює потік без
  заголовка `content-length` і без реального виділення 150+ МБ у тесті), рев'ю коду.

### Новий дефект: атомарність вибору поточної теми (BUG-006)
`setCurrentTopicAction` виконує «зняти поточну → поставити нову → активувати предмет» як
**три окремі**, не транзакційні виклики PostgREST (`forFamily(...).update(...)` не підтримує
транзакцій — рев'ю `family-scope.ts`), а схема `topics` не має обмеження «не більше однієї
поточної теми на предмет» (немає часткового унікального індексу). Новий регресійний тест
`app/tests/db/s2-subjects.test.ts` підтверджує на рівні бази, що два рядки `topics` одного
`subject_id` можуть одночасно мати `is_current = true`. Деталі, наслідки й конкретне
завдання — `docs/bugs/BUG-006-current-topic-not-atomic.md` (**Major**, блокує злиття до
виправлення — прямо порушує критерій прийняття US-3.1 КП-1 під реалістичним мережевим
збоєм/подвійним сабмітом, саме той клас сценаріїв стійкості, який QA зобов'язана
перевіряти для кожного зрізу).
