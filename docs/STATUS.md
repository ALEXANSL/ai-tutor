## BUG-019 (Critical, Fixed) + BUG-020 (Major, Fixed) — 2026-09-26, гілка `claude/intelligent-carson-6exmc1`

**BUG-019 — правильні відповіді оцінювались як «Майже».** Дві незалежні причини: (1) `drag_sort`/будь-який `interactive` крок — `LessonRunner.tsx` надсилав на сервер обгорнутий об'єкт `{ component, answer, correct }` замість самої відповіді, яку очікує `evaluateAnswer`, тож сервер завжди оцінював не ту форму й повертав `incorrect`; (2) відкриті відповіді — оцінювач порівнював зі «зразком» буквально, тому відповідь просто цифрою («2») чи переліком («а)/б)/в)») не зараховувалась, хоча по суті правильна. Фікс: клієнт надсилає сиру відповідь без обгортки; новий детермінований `matchesExpectedBySubstance`-етап у `evaluateAnswer` + переписаний промпт оцінювача, що явно оцінює суть, а не формат; фронтенд більше не показує однаковий текст «Майже» і для `partial`, і для `incorrect`. BUG-013 (safety-override для тривожних повідомлень) не зачеплено — тести на нього пройшли без змін. Детальніше й повний список тестів — `docs/bugs/BUG-019-correct-answers-marked-almost.md`. **Свідомо поза обсягом (D-74, US-6.15, майбутній зріз):** повний цикл «пояснити помилку → дати ще одне закріплювальне завдання → тоді далі» — зараз, як і раніше, лише коротке пояснення + «Спробуй ще раз».

**BUG-020 — не було кнопки виходу з уроку/чату.** Додано «Вийти з уроку» в `LessonRunner.tsx` (з підтвердженням), що зберігає прогрес через уже наявний механізм паузи/резюме (BUG-008) з новою причиною паузи `manual_exit` — `current_step_id` не чіпається, урок продовжується з того самого кроку. Кнопка повернення в чаті зі ШІ-другом (`FriendChatScreen.tsx`) вже існувала — перевірено, працює. Деталі — `docs/bugs/BUG-020-no-exit-lesson-or-chat-navigation.md`.

**Перевірки:** typecheck, 585 юніт-тестів (7 нових), 58 e2e, білд і перевірка клієнтського бандла на секрети — усе зелене (без урахування відомого нестабільного `tests/db/s1-materials.test.ts`, не пов'язаного з цим фіксом).

## BUG-017 + BUG-018 (2026-09-26, гілка `claude/intelligent-carson-6exmc1`, знайдено в реальних продакшн-логах Vercel)

**BUG-017 (Critical, Fixed) — «Functions cannot be passed directly to Client Components» на КОЖНОМУ відкритті `/lesson/[sessionId]`.**
Причина: `(child)/lesson/[sessionId]/page.tsx` (сервер) передавав `uk.child.lesson` цілим об'єктом
як пропс `labels` у клієнтський `LessonRunner` — а в цьому неймспейсі є дві функції-форматери
(`sourceRef`, `stepOf`), які React не може серіалізувати через межу сервер→клієнт. Фікс:
`LessonRunner` (і той самий патерн у `FriendChatScreen`/`friend/page.tsx`) тепер сам імпортує
`uk` як значення (це вже клієнтський модуль) замість того, щоб отримувати його пропсом. Деталі,
корінь і тест, що реально відтворює точну помилку через `react-server-dom-webpack` Next.js (не
мок) — `docs/bugs/BUG-017-lesson-page-passes-function-props-to-client.md`,
`src/i18n/uk.rsc-props.test.ts`.

**BUG-018 (Major, Fixed) — задовгий (але змістовно правильний) `goalUk` валив усю генерацію уроку.**
Причина: схема `lesson_planning` (`planSchema.goalUk`) обмежувала поле 200 символами; Anthropic
SDK валідує відповідь моделі проти цієї схеми до того, як код проєкту її побачить, тож будь-яке
речення трохи довше межі кидало помилку валідації й ронило весь `startLessonAction`. Фікс:
ліміт піднято до 400 символів (запас для реального одноречникового опису) + промпт тепер явно
просить ≤150 символів із прикладом. Деталі й тест на межовий випадок (201 символ — саме та
довжина, що падала раніше) —
`docs/bugs/BUG-018-lesson-planning-goaluk-too-long.md`, `src/server/lessons/schema.test.ts`.

Перевірено: `lint`, `typecheck`, `test` (578/578), `build` (webpack) і `check:bundle`
(`NODE_USE_ENV_PROXY=1`, 0 leaks), e2e (`NODE_USE_ENV_PROXY=1`, 58/58) — усе зелене. Живе демо
на реальному уроці з реальним Anthropic API — лишається за Алексом; сама поверхня обох багів
(RSC-серіалізація функції-пропса, Zod-межа схеми) вже перевірена автотестами, що напряму
відтворюють умови з логів.

## D-65 + два термінові демо-фікси (2026-09-26, гілка `claude/intelligent-carson-6exmc1`)

**D-65 (docs/01-requirements.md 12.13): дитина обирає БУДЬ-ЯКУ тему предмета, не лише «поточну».**
- `/subject/[id]` (дитячий екран) тепер показує повний список тем підручника (`getSubjectDetail`
  уже повертав `topics[]` — використано без змін запиту), кожна клікабельна →
  `ChildStartLessonButton(subjectId, topicId цієї теми)`; тема, позначена `is_current`, має
  бейдж «Пріоритет» (не блокує вибір інших). Порожня структура тем — той самий `emptyPlanBody`,
  що й раніше.
- `startLessonSession`/`chooseStartBlock`/`generate.ts` **вже** приймали довільний `topicId` у
  межах предмета — жодного обмеження на `is_current` не було в коді, тож зміна суто UI-рівнева.
- Кабінет тата (US-3.1/3.2, вибір «поточної» теми — `set_current_topic`) **не змінено**: та сама
  «поточна тема» лишається підказкою пріоритету для прогноз-плану.
- Тести: `server/subjects/queries.test.ts` (новий юніт — `getSubjectDetail` повертає весь список
  тем, не лише поточну), `tests/e2e/specs/s4-safety-surface.spec.ts` (новий е2е-кейс: неправильний
  UUID у `/subject/[id]` дає 404 ще до перевірки сесії — єдине, що можна перевірити без акаунтів у
  цьому середовищі; повний інтерактивний прохід — уручну на демо, чекліст нижче).

**Термінове (до D-65, знайдено на живому демо): «Почати» на дитячому екрані зависало.**
Причина: `startLessonAction` (і, дешевше, `chooseStartBlockAction`) синхронно виконує весь
педагогічний конвеєр (`lesson_planning`+`lesson_generation` на Claude, потім `lesson_review`,
можливо доопрацювання) — це регулярно перевищує стандартний ліміт часу серверної функції
(Vercel), запит обривався без помилки. **Важливо:** `actions/lesson.ts` — файл `"use server"` —
у цій версії Next.js **не може** сам експортувати `maxDuration` (білд падає: «Only async
functions are allowed to be exported in a "use server" file»), тож `export const maxDuration =
300` додано на кожній сторінці, що може викликати ці дії:
`(child)/subject/[id]/page.tsx`, `parent/subjects/[id]/page.tsx`, `(child)/lesson/[sessionId]/page.tsx`
(той самий бюджет, що вже був у `parent/books/*`/`api/jobs/tick`). Кнопка «Почати»
(`ChildStartLessonButton`) тепер показує «Готуємо урок…» замість застиглого вигляду під час
генерації першого уроку теми (може тривати 20–90+ с). Тест: `actions/lesson.maxduration.test.ts`
(статично перевіряє літеральний експорт ≥120с на всіх трьох сторінках і що самого `lesson.ts`
серед них немає).
*Залишок на майбутнє (не зроблено зараз, свідомо — щоб не розширювати обсяг):* синхронний старт
першого уроку теми — кандидат на job+polling патерн, як у «Мої книги» (черга + індикатор
прогресу), замість одного довгого запиту в межах `maxDuration`. Поки що просто `maxDuration=300`
+ видимий спінер достатньо для демо; якщо перший урок теми колись перевищить навіть 300 с —
заводити окремий баг.

**BUG-016 (Critical, Fixed, знайдено на тому ж демо): клік на запропонований блок уроку
показував технічну сторінку Next.js.** Деталі, корінь і фікс —
`docs/bugs/BUG-016-choose-block-crashes-generic-error.md`. Коротко: `activateBlock`
(`orchestrator.ts`) не перевіряв помилку двох записів у БД (тепер перевіряє й кидає конкретний
`Error`); `chooseStartBlockAction` тепер обгорнутий у `try/catch`, як `startLessonAction`; і —
головний захист — новий `app/(child)/lesson/[sessionId]/error.tsx` (route-segment межа помилки
Next.js): дитина відтепер побачить «Щось пішло не так» + «Спробувати ще раз»/«← До «Сьогодні»»
замість технічної сторінки незалежно від того, де саме в рендері цього екрана станеться виняток.
Тест: `orchestrator.test.ts` → `chooseStartBlock (BUG-016…)` — реалістичний багатокроковий блок
(усі 4 типи кроку, реальні `sourceRefs`), підтверджує відсутність кидка в нормальному кейсі й
конкретну перехоплювану помилку при відхиленому записі.

**Перевірки:** lint, typecheck, юніт-тести (563), e2e (58, `NODE_USE_ENV_PROXY=1`), build +
`check:bundle` (`NODE_USE_ENV_PROXY=1`) — усе зелене. **`test:db` — не повністю зелений, але це
підтверджена середовищна проблема, не пов'язана з цими змінами:** `tests/db/s1-materials.test.ts`

відпрацювати послідовно (`fileParallelism: false`) — перевірено: той самий результат на `git

  пишеться (стовпець `severity` там навмисно без «none»), тож зовнішня e-mail/Telegram доставка

`recordSafetyEvent` тепер шле татові окрему кабінетну подію `safety_moderation_unavailable`
(`severity: "urgent"`), навіть коли сама репліка не «flagged» — дитині відповідь як і раніше
приходить без затримки/блокування (UX не погіршено), рядок у `safety_events` не пишеться (там немає
категорії «none» — конструкт таблиці навмисно приймає лише `severity in ('normal','urgent')`), тож
зовнішня e-mail/Telegram доставка для цього конкретного випадку **не** запускається (лише кабінет) —
свідомий мінімальний компроміс, а не повна відповідність ADR-010; якщо це виявиться недостатнім на

## S1b «Скановані книги (OCR)» — рішення PO D-54 — код готовий (2026-09-26)
**Що зроблено** (US-2.2 «статус розпізнавання», US-2.6; беклог S1b; ADR-008 примітка):
- **Маршрутизатор:** нова роль `ocr_page` — **Claude Sonnet 5** (не Opus 5.5: розпізнавання
  друкованого тексту — задача сприйняття, ціна масштабується з кількістю сторінок підручника, тому
  дешевша модель за `indexing_structure`/`lesson_generation` виправдана; докладно — ADR-008,
  `docs/03` 3.9б). Маршрутизатор отримав новий вид виклику `callVisionStructured`/провайдер `vision`
  (сторінки як PDF-документ у content, офіційний Anthropic SDK) — поряд з наявним `callStructured`,
  без зміни інтерфейсу ролі й обліку вартості (ADR-004 не змінюється).
- **Конвеєр (docs/02 9.1, ADR-008):** сторінка PDF без текстового шару (увесь скан або частина
  сторінок змішаної книги — детектор посторінковий, той самий поріг, що й раніше для «скан без
  тексту») іде через нову задачу `ingest.ocr` — пакети по 6 сторінок, відновлювана після збою (як
  `ingest.embed`); прогрес у «Мої книги» — «Розпізнається: сторінка N з M»; кожен виклик записує
  вартість в `ai_calls` як і будь-який виклик ролі. Розпізнаний текст зливається зі звичайним
  текстовим шаром **до** фрагментації — подальший конвеєр (ембединги, `indexing_structure`) не
  відрізняє розпізнаний текст від витягнутого. Повторна індексація того самого файлу (`content_hash`
  не змінився) не запускає OCR вдруге — той самий механізм, що вже пропускав повторний витяг тексту.
- **Оцінка перед великим сканом (D-54):** малий скан (≤ `parent_settings.ocr_confirm_above_pages`,
  за замовчуванням 20 стор.) розпізнається автоматично; більший — показує оцінку вартості (з
  поточної ціни ролі `ocr_page`) і чекає кнопки тата «🔎 Розпізнати» (новий статус
  `scan_awaiting_ocr`) — жодних витрат без згоди тата.
- **Не вдалося розпізнати:** якщо після OCR не залишилось жодного придатного тексту (порожні/
  пошкоджені сторінки) — зрозумілий статус «Скан не вдалося розпізнати» (`scan_no_text` /
  `status_detail: scan_unreadable`), відмінний від «сканованих сторінок не знайдено».
- **Режим бюджету:** роль `ocr_page` має `budget_policy: "defer"` — як і `indexing_structure`,
  розпізнавання відкладається до збільшення ліміту/нового місяця (US-11.5 КП-6).
- **Промпт** — `app/prompts/ocr_page.md` (окремий файл, редагує Алекс); моделі передається лише
  зображення сторінок книги, жодних даних доньки (NFR-PRIV-2).

**Новий SQL-файл (виконати в Supabase SQL Editor, після трьох файлів S0 і двох файлів S1):**
`supabase/migrations/20260929100000_s1b_ocr_scanned_books.sql` — `parent_settings.ocr_confirm_above_pages`
(за замовчуванням 20), нові поля `materials` (`ocr_pages_total`, `ocr_pages_done`,

маршруту `ocr_page` для кожної сім'ї. Повторний запуск безпечний (перевірено `test:db`). **Нових
змінних Vercel не потрібно** — використовує ключі S1 (`ANTHROPIC_API_KEY`).

**Оцінка вартості OCR на підручник 200 сторінок (docs/03 3.9б, до звірки на реальному скані):**
розпізнавання (Sonnet 5, ≈ 1600 вх. + 700 вих. токенів/сторінку) ≈ **$2,0**; подальша структура
(Opus 5.5, той самий крок, що й для текстового PDF) ≈ $1–1,5 → **разом ≈ $3–3,5** на скан-підручник
(разово, як і звичайна індексація). Для порівняння: текстовий PDF того самого обсягу — ≈ $1–1,5, тож
скан дорожчий приблизно вдвічі-втричі, але лишається разовою витратою на книгу.

## S3 «Перший урок» + педагогічний конвеєр (D-55, ADR-022) + BUG-007…012 — код готовий (2026-09-30)
**Додатково зроблено 2026-09-30 (друга хвиля QA, BUG-011/BUG-012):**
- **BUG-011 (Major, виправлено):** якщо жоден блок теми не пройшов рецензію — ні через
  `needs_review` (рецензент попрацював, але жодна з `MAX_REVISIONS + 1` спроб не отримала
  `approved`), ні через недоступного рецензента (`AiNotConfiguredError`, напр. не задано

### Деталі реалізації S0
**Що зроблено (код у `app/`, міграції в `supabase/migrations/`):**

- Режим тата на планшеті: PIN (argon2id + `PIN_PEPPER`), блокування після 5 спроб на 15 хв + подія тату, підписаний httpOnly-cookie з прив'язкою до пристрою, автовихід після 5 хв без дій, постійна позначка «Режим тата».

**Технічні рішення в межах документів:** ключ підпису cookie `parent_mode` виводиться з `PIN_PEPPER` (окремий «ярлик»), тож нової змінної середовища не потрібно; PIN задає/змінює лише тато зі свого акаунта (не з режиму тата на планшеті); «Сьогодні» → плитка «Ще модулі» нічого не відкриває (US-11.8 КП-3 має пріоритет над підказкою в макеті).

**Не перевірено (немає акаунтів):** реальний вхід Google, вхід акаунтом доньки (R-5, D-29 — чекліст `docs/02` 10.1), застосування міграцій на Supabase, встановлення PWA на Lenovo Yoga 11, вигляд на пристроях.

**Чоловічі імена-підказки (BUG-001, попередні — Алекс може змінити):** «Мирон» (спокійний і уважний), «Остап» (веселий і енергійний), «Ярема» (терплячий і дружній) — у `app/config/family-defaults.json`; після першого входу список змінюється в кабінеті / БД (`parent_settings.tutor_name_options`).
